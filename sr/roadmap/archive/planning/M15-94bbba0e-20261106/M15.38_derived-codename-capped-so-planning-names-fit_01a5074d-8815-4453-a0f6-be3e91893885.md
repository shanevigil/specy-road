## Intent

`add-node` with a long title and no `--codename` derives the codename from the whole title, with no length limit. The planning sheet is named `<id>_<codename>_<node_key>.md`, so a long enough title gives a file name longer than the OS limit, and the write fails with `OSError: [Errno 36] File name too long`. This leaf caps derived codenames and refuses explicit ones that are too long (rc4 fix, maintainer 2026-11-05). M15.39 makes the failed write leave nothing behind.

## Approach

- Root cause: `roadmap_edit_fields.title_to_codename` joins every title word, and `roadmap_crud_prepare.ensure_codename_for_new_node` passes `max_words=None` for add-node. `planning_artifacts.planning_filename_for_node` uses the result as it is. `AtomicWritePlan.write` also adds a `.<name>.tmp-<32 hex>` prefix to the name, which makes it longer still.
- Add `CODENAME_MAX_CHARS = 64` and a cap helper beside `title_to_codename`, and use it in every derivation path. Leave `title_to_codename` uncapped, so `validate_unique_title_slugs` does not start finding new collisions between long titles with the same opening words.
- `codename_was_derived` must accept the capped form too. Otherwise a capped codename looks hand-picked and a later title edit would keep it.
- With a cap of 64, a planning file name is at most about id + 106 bytes, well under 255. The NAME_MAX check in `planning_filename_for_node` guards against any other cause.
