## Intent

`worker usage` badly undercounts long Cursor turns. In an adopter's run, a 6,092 s turn that changed about 5,800 lines in 28 files reported 10,136 output tokens and $1.55, while shorter turns reported 17k–73k. Probably only the last segment or result event of the turn is counted. M15.19 (landed) fixed the display-name cost mismatch; this is a separate counting bug.

## Approach

- First, find a long Cursor turn's raw stream in a worker log (`work/.workers/<id>.log`, `worker_runner.log_path`) or record one, and reduce it to a fixture with only `type`, `subtype`, `session_id` and the usage fields. Write down what the stream shows before changing the parser.
- `worker_adapter_cursor.CursorAgent.parse` reads usage only from the `result` line today. Depending on the fixture, read usage from the other line types too, and either emit per-segment usage (the runner appends one usage event per `Parsed.usage`, and `worker usage` sums them) or accumulate and emit once. Use `worker_usage_delta.turn_usage` if a count is a running total.
- `worker_runner.py` is at 396 lines: do not grow it.
- New `specy_road/worker_usage_plausibility.py`: constants and `possible_undercount(turn_events)`; `worker_cli_render.usage` (230) marks the turn and adds the JSON key. Turn duration comes from the turn's start event to its usage event.
- Overlap: M8.3 (claimed) and M15.9 list `worker_adapter_cursor.py`; keep changes inside `parse`.
