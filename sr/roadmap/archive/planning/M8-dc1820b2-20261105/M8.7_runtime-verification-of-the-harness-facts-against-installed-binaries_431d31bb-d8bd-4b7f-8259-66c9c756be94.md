## Intent

Runtime verification of the harness facts against installed binaries. Done when:
- The verification guide from the research (versions and help, denial behaviour and exit codes, commit-when-asked from a nested subdirectory, create and resume by id from a sibling worktree, instruction sentinels versus the meter, Cursor -p with and without --force, Claude usage-limit events with the watchdog, forbidden-commit hook test, sibling-worktree concurrency) is run in a scratch repository and its results recorded with dates
- Every unverified label in the harness facts fixture is replaced by a runtime result or an explicit still-unknown

## Approach

Maintainer decision (2026-11-02): the coordinator's agent runs this on this machine, where Claude Code, Codex CLI and the Cursor agent are installed (Copilot CLI and Antigravity are not: record those as still-unknown). Take the runtime verification guide from the harness-capabilities research prompt (sr/research/prompts/harness-capabilities.md, section 'Runtime verification guide') and run it in a scratch git repository under a temporary directory: versions and help output, a denied action's report and exit code, a commit requested from a nested subdirectory, creating a session and resuming it by id from a sibling worktree, instruction-file sentinels versus the context meter, Cursor -p with and without --force, a usage-limit event if one can be observed, a hook that blocks a forbidden commit, and two sessions in sibling worktrees. Keep each model call tiny (one-line prompts) and the total under about 40 calls. Replace each `unverified` label in the harness-facts fixture (M8.1) with a `runtime` result citing the command, version and date, or an explicit still-unknown with the reason; never guess. Write the checklist results as a design note under docs/design-notes/. Verify with the harness-facts tests, refresh-profiles --check and file-limits.
