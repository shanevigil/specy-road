# PRELIMINARY: Let surviving mutants, not coverage, judge agent tests

> **PRELIMINARY.** This report was produced by an automated multi-agent web research pass on 2026-11-16. It was **not** produced by the deep-research tool that `sr/research/prompts/agentic-unit-testing.md` names, **no tool was run on the specy-road suite**, and **every cost figure below is an unmeasured estimate**. The maintainer may run the full deep-research prompt afterwards; where that run disagrees with this one, prefer the run that measured something. Source-quality marks used throughout: **[peer-reviewed]**, **[preprint]**, **[primary]** (a tool's own docs or PyPI page), **[practice]** (industrial guidance, not a controlled study), **[vendor-only]** (a tool author's or seller's own claim), **[weak]** (small, student or low-tier venue), **[secondary]** (figure seen only through a summary, not checked against the source), **[unverified]** (could not be traced to a source).

For an agent-written suite, **coverage tells you a line ran; only mutation tells you a line was checked**, and the published evidence says the dominant defect of agent-written tests is exactly that gap: 80.2% of 86,156 test patches in agent-authored pull requests carry weak or no oracle ([Banik et al., arXiv 2606.18168, 2026-06](https://arxiv.org/abs/2606.18168)) [preprint]. specy-road's existing floor (coverage TOTAL at least 90, branch arcs included, set from a 90.57% baseline in `pyproject.toml`) already sits at Google's "exemplary" band, so raising it buys little; the signal it lacks is a check on assertion strength and a check that new code is executed at all. The recommendation for roadmap leaf M16.7.8 is **Option B**: keep the total floor, add a deterministic changed-line coverage gate and a static test-coupling gate on every PR, and add a **mutation score on a named list of core modules** that runs nightly as a report and becomes a no-decrease ratchet once a baseline exists. Option B wins over the coverage-only Option A because the planned dedupe leaves (M16.7.1 to M16.7.5) preserve arcs by construction, so a coverage floor cannot see them delete a real oracle while a core-module mutation score can. It wins over the Google-style diff-mutation Option C because 464 CLI tests still run in subprocesses that mutation tools and per-test coverage contexts probably cannot see, so per-PR survivors would be noisy until M16.7.8 itself moves those tests in process. Before committing, run a **half-day pilot on one core module** to measure mutants per module, seconds per mutant, verdict stability across two runs and the false-survivor rate from subprocess-reached code.

## Three options for M16.7.8, and why the middle one fits

M16.7.8's acceptance requires the maintainer to name measures, thresholds and modules in an `A1:` line, and its A5 line compares each measure at the leaf's merge base and head "with the same settings" (`sr/planning/M16.7.8_*.md`). That shapes the options: every measure must produce a number that can be recomputed at two commits on one machine and in GitHub Actions, and a later close-out leaf re-checks the recorded values, so they must stay cheap enough to rerun. A changed-line measure has no meaningful merge-base value, so in each option it applies to the leaf's own diff as a head-only check. The three options below are cumulative in capability but are offered as alternatives; each is internally consistent.

**Pick Option B.** Three findings decide it. First, the strongest evidence that any suite measure tracks real faults belongs to mutation: 73% of 357 real Java faults were coupled to simple mutants, and mutant detection correlated with real-fault detection more strongly than statement coverage and independently of it ([Just et al., FSE 2014](https://homes.cs.washington.edu/%7Emernst/pubs/mutation-effectiveness-fse2014.pdf)) [peer-reviewed]; a Defects4J 2.0 revisit put the coupled share at 80.7% ([Mutation 2022 workshop at ICST](https://icst2022.vrain.upv.es/details/mutation-2022-papers/1/Re-visiting-the-coupling-between-mutants-and-real-faults-with-Defects4J-2-0)) [peer-reviewed]. Second, **coverage-preserving test reduction still loses fault detection** ([Shi et al., FSE 2014](https://mir.cs.illinois.edu/gyori/pubs/fse14reduction.pdf)) [peer-reviewed], and at Meta 277 of 571 accepted mutation-guided tests added no line coverage at all ([Foster et al., arXiv 2501.12862, 2025-01](https://arxiv.org/html/2501.12862v1)) [vendor-only: tool authors' own deployment]. M16.7.1's worklists group tests by identical arcs and Jaccard at least 0.95, so the dedupe leaves are invisible to Option A's floor by design; a core-module mutation score that drops after a dedupe leaf is the one signal that the removal took a real oracle with it. Third, Option C's design is Google's, and it works there, but it needs mutants to reach the code that tests exercise, and in this repo a large share of that code is reached through `specy-road` children. M16.7.8 is the leaf that fixes that, so Option C becomes the natural follow-up once it lands, not the measure that judges it.

The A1 line Option B implies would read, in substance: coverage TOTAL at or above `fail_under` 90 on every PR; changed-line and arc coverage of each diff at least 90% on every PR; zero new private-name imports or patches on every PR with message-text assertions reported; a fail-to-pass record for every fix-labelled change; and a mutation score over the named core modules with a fixed operator set, timeouts inconclusive, reported nightly and per release, then held at no decrease beyond the pilot's measured spread. For A5, the comparable values at merge base and head are coverage TOTAL, branch percentage, the coupling counts and the core-module mutation score; the changed-line check applies to the leaf's own diff. One caution belongs in the record: because M16.7.8 moves CLI tests in process, the head's mutation score will likely rise partly because mutants become visible, not because tests got stronger, so A5's "head not below base" is a valid floor but a rise is not evidence of improvement on its own.

### A half-day pilot should settle buy versus build before A1 is written

The buy-versus-build margin between an in-house runner (34 of 42) and the best tools (Cosmic Ray 31, mutmut 29) rests on analyst judgement, and the one fact that would flip it is unknown: whether a tool's mutants reach code run in CLI subprocesses. The pilot takes one core module whose tests run in process (a validator or registry module) and one module reached mostly through the CLI. On a scratch branch it first enables `dynamic_context = test_function` for one full run under `-n auto` and records the overhead, the data-file size and how many covered lines land in the empty context, which is where subprocess-run lines are expected to go ([coverage.py contexts](https://coverage.readthedocs.io/en/latest/contexts.html)) [primary]. It then runs mutmut 3.8.1 with `mutate_only_covered_lines = true` on both modules, twice, recording mutants per module, seconds per mutant, survivors, timeouts and any verdict that changed between runs ([mutmut docs](https://mutmut.readthedocs.io/en/latest/)) [primary]. A hand-read of 20 to 30 survivors sorts them into equivalent, arid, real gap and false survivor (a mutant on a line only a CLI child executes). If time remains, pytest-gremlins runs on the same in-process module for a speed cross-check, and Cosmic Ray with `cr-filter-git` times a full-test-command run on a small diff. The decision rule is simple: if a tool's verdicts are stable and its false-survivor rate on the CLI-reached module is low, integrate it optionally and skip the build; if subprocess-reached lines produce false survivors, restrict the nightly module list to in-process-tested modules until M16.7.8 lands; if verdicts flip between identical runs, Option B stays report-only and the tolerance comes from the measured spread.

### Repo-specific risks the pilot must check

The repository's coverage configuration sets `patch = ["subprocess"]` so that pytest-xdist workers and the 464 `specy-road` CLI children are measured. That keeps the TOTAL honest but hides those children from every per-test tool. mutmut 3 runs the suite in-process to collect "stats", then forks one child per mutant from a mutated copy under `mutants/` ([mutmut README](https://github.com/boxed/mutmut)) [primary]; a CLI child that imports the installed package rather than that copy would never execute the mutant, so mutants on CLI-only paths would show up as **false survivors**, and the stats phase cannot attribute functions run in a child to the parent test, so others would show as "no tests" (inference from the documented execution model; compare the `sys.path` problems in [mutmut issue #336](https://github.com/boxed/mutmut/issues/336)) [unverified on this suite]. pytest-gremlins' environment-variable mutation switch has the same exposure if a child does not inherit the instrumented import [unverified]. Per-test coverage contexts have the parallel problem: a child starts its own coverage with no pytest frame, so its lines most likely land in the empty-string context with **no per-test attribution** ([coverage.py contexts](https://coverage.readthedocs.io/en/latest/contexts.html); [coverage.py subprocess](https://coverage.readthedocs.io/en/latest/subprocess.html)) [primary; the child-context behaviour itself is unverified], which also weakens M16.7.1's arc-similarity worklists, as that sheet already anticipates. Smaller risks round this out. mutmut's timeout is documented as "unstable config", and every tool's timeout handling is the main source of flaky verdicts, so a gate must treat timeouts as inconclusive, never as survived ([mutmut docs](https://mutmut.readthedocs.io/en/latest/)) [primary]. mutmut needs `fork`, which suits Linux, macOS and GitHub's Ubuntu runners but excludes native Windows ([mutmut docs](https://mutmut.readthedocs.io/en/latest/)) [primary]. A PR check that relies on restoring mutmut's `mutants/` cache from CI makes the result depend on cache state, which cuts against constraint 6. Finally, the notes counted about 458 `test_*.py` files and about 84k lines under `specy_road/` in the current checkout, against the prompt's 393 files and 65k lines from 2026-11-05, so the cost estimates scale up accordingly.

## Agent tests reproduce structure, rarely the spec: rules and a checklist

The 2026 studies of real agent pull requests agree on the failure mode. Agents add tests readily but the tests check little: 80.2% of agent test patches had weak or no oracle signal, and PRs with strong oracles were more likely to merge (odds ratio 1.28) ([Banik et al., arXiv 2606.18168, 2026-06](https://arxiv.org/abs/2606.18168)) [preprint, abstract only, no human baseline]. In 4,882 agent PRs, 50.4% of PRs that changed code under test changed no test; in Python PRs that added tests without raising diff coverage, **74.8% added tests that missed the agent's own changed lines**, error paths were the least tested (82.3% of `raise` lines and 81.0% of `try/except` lines missed), and in Java agents deleted 82 tests while adding 31 ([Dipongkor et al., arXiv 2607.18057, 2026-07](https://arxiv.org/html/2607.18057)) [preprint]. Agent commits add mocks more often than other commits, 36% against 26% ([Hora & Robbes, arXiv 2602.00409, 2026-01, MSR 2026](https://arxiv.org/abs/2602.00409)) [peer-reviewed]. LLM oracles "mainly capture the actual program behavior", and intent-revealing test names improved oracle quality by up to 16.10% ([Konstantinou et al., arXiv 2410.21136, 2024-10](https://arxiv.org/abs/2410.21136v1)) [preprint; secondary, abstract via summary]. When the code under test is buggy, coverage and mutation score "no longer serve as reliable indicators" of LLM-suite effectiveness ([Zhao et al., arXiv 2607.22880, 2026-07](https://arxiv.org/abs/2607.22880)) [preprint]. Tests that contradict the spec invite cheating, and making tests read-only plus an explicit "stop if the tests are flawed" instruction suppressed it ([ImpossibleBench, arXiv 2510.20270, 2025-10](https://arxiv.org/pdf/2510.20270)) [preprint; secondary, exact figures vary between summaries].

The steelman deserves space. A single-author preprint scoring Claude-written Python tests against Django and Pandas tests found per-commit kill rates of 53.2% against 48.0% and 45.0%, and rare coupling problems in the AI corpus; its dominant AI-test defect was still weak-value or loose-bound oracles, and low-kill-rate tests were the defective ones, so it recommends scoring individual tests by kill rate rather than whole suites ([Leith, arXiv 2608.15188, 2026-08](https://arxiv.org/html/2608.15188)) [preprint, author's own project as the corpus, small counts]. The same paper found that "fails when the change is reverted" rated 95-98% of tests effective with 50-67% false positives, which matters for how red-green records are read. The honest synthesis is that agent tests are not uniformly worse, but their typical defect is the one coverage cannot see.

The rules below turn that evidence into instructions for executors (prompt-side, for the toolkit's generated briefs and agent instructions) and into process checks. The checklist number in the last column points to the reviewer checklist that follows.

| Rule for agent-written tests | Side | Evidence | Checklist |
|---|---|---|---|
| Derive the test list from the leaf's acceptance lines before reading the implementation; name each test for the behaviour, not the function, bug id or review round | prompt | intent names +16.10% oracle quality [preprint] | 11 |
| A test added for a fix must fail on the parent commit and pass on head, and the summary records both runs | process | SWT-Bench fail-to-pass definition ([Mündler et al., arXiv 2406.12952, 2024](https://arxiv.org/html/2406.12952v2)) [peer-reviewed, NeurIPS 2024] | 1 |
| Added tests must execute the added lines, explicitly including `raise` and `except` paths | prompt and process | 74.8% missed own lines; error paths 81-82% missed [preprint] | 2 |
| Assert a value, an exception type, or a file or state effect; never "runs without error" or `is not None` alone; message text only where it is an allowlisted output contract | prompt | 80.2% weak oracles [preprint]; Assertion Roulette and Useless Test smells ([Ouédraogo et al., arXiv 2410.10628, 2024-10](https://arxiv.org/html/2410.10628v2)) [preprint, secondary] | 4, 8 |
| Test through the public interface; no `_`-prefixed import or patch target (already an `AGENTS.md` rule); mock only at process, network or clock boundaries; assert state, not call order or counts | prompt and script | [SWE at Google ch. 12](https://abseil.io/resources/swe-book/html/ch12.html) [practice]; over-mocking 36% vs 26% [peer-reviewed] | 5, 6 |
| Never delete, skip, `xfail` or loosen an existing test in the same change as a fix unless the commit names the test that covers it; tests outside the leaf's zones are read-only; if a test looks wrong, stop and report rather than special-case the code | prompt and process | agents deleted 2.6x what they added in Java [preprint]; ImpossibleBench read-only tests [preprint] | 10 |
| One behaviour, one parametrized table: extend the existing table instead of adding a single-input test | prompt | near-duplicate and repeated-assertion findings only ([arXiv 2503.17998](https://arxiv.org/pdf/2503.17998); [arXiv 2312.08826](https://arxiv.org/pdf/2312.08826)) [secondary; practice, no LLM trial] | 9 |
| Where an invariant exists (round trip, idempotence, ordering, schema validity, "only documented errors"), write a Hypothesis property, not N examples | prompt | property tests kill ~50x the mutants of an average unit test ([Ravi & Coblenz, OOPSLA 2025](https://2025.splashcon.org/details/OOPSLA/102)) [peer-reviewed] | 12 |
| When survivors are reported on changed lines, kill each one or mark it with a reasoned `# pragma: no mutate`; the suppressed share is capped (pytest-gremlins caps pardons at 5% by default) | process | Google diff mutation ([Petrovic et al., arXiv 2102.11378, 2021](https://ar5iv.labs.arxiv.org/html/2102.11378)) [peer-reviewed, TSE]; [pytest-gremlins PyPI](https://pypi.org/project/pytest-gremlins/) [primary] | 3 |
| No wall-clock sleeps or real-time dependence; use events, fakes or a frozen clock | prompt and script | async wait ~45% of fixed flaky tests ([Luo et al., FSE 2014](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf)) [peer-reviewed; figure not re-checked this pass] | 7 |

The reviewer checklist applies to each added or changed test in a diff. **"Yes"** means a local script can decide it with pytest, coverage.py and git, no LLM; **"Partly"** means a script can flag candidates and a reviewer decides; **"No"** means judgement only. The scripted items fit constraint 5: the toolkit computes them and hands the judgement items to the user's own agent as a generated review prompt.

| # | Reviewer question | Script? | How a script checks it |
|---|---|---|---|
| 1 | Does it fail on the parent commit (or with the new code stubbed out for a feature) and pass on head? | **Yes** | Check out the parent's package source, keep the new tests, run `pytest <new node ids>`, require a failure that is not a collection error |
| 2 | Does it execute the lines the diff added, including `raise`/`except` lines? | **Yes** | coverage.py per-test contexts intersected with `git diff -U0` added lines |
| 3 | Does it add checking power no existing test has: a mutant on changed lines only it kills (fallback: an arc only it covers)? | **Yes, at a cost** | arc uniqueness from contexts is cheap; unique kills need a diff-scoped mutation run |
| 4 | Is the oracle strong: a value, exception type or state effect, and does the expected value come from the spec rather than current output? | **Partly** | AST flags tests with no `assert`/`pytest.raises`, `assert True`, or only truthiness and `is not None` checks; spec-fidelity is judgement |
| 5 | Does it import or patch no `_`-prefixed name? | **Yes** | AST scan of imports, attribute access, `monkeypatch.setattr` and `mock.patch` target strings |
| 6 | Are mocks only at real boundaries, and does it assert state rather than interactions? | **Partly** | flag `assert_called*`, `call_count`, `mock_calls` and new in-package patch targets; boundary justification is judgement |
| 7 | Is it free of wall-clock sleeps and real-time dependence? | **Yes** | AST/grep for `time.sleep`, `asyncio.sleep(>0)`, `datetime.now()`; optionally rerun new tests N times |
| 8 | Does it avoid asserting long free text unless the text is the contract? | **Partly** | detect 12+ character literals in assertions and `match=`; the contract allowlist is judgement |
| 9 | Is it not a near-duplicate that should be a row in an existing parametrized table? | **Partly** | normalised-AST similarity plus identical arc sets flag candidates; LLM dedup flags ran ~30% false positives ([arXiv 2412.03693](https://arxiv.org/pdf/2412.03693)) [secondary], so merges stay a decision |
| 10 | Does the change delete, skip or weaken no existing test, or name the covering test when it does? | **Yes** | diff for removed `def test_`, removed asserts, added `skip`/`xfail`, `==` loosened to `in`; require a covering-test line in the commit |
| 11 | Is it named for the behaviour? | **Partly** | flag `test_<function>` only, `test_fix_*`, `test_issue_*` and review-round names |
| 12 | Should this be a Hypothesis property? | **No** | a script can only hint ("N parametrized cases on one function") |

The order that keeps cost low is static checks first (5, 7, 8, 10, 4-AST, 11), then one coverage run with contexts (2, and arc uniqueness for 3 and 9), then the parent-commit run (1), with diff-scoped mutation for 3 only where Option C is adopted. No published checklist targets agent-written tests; this one is a synthesis whose rules have not been evaluated together.

## Seven open questions, answered against the evidence

### 1. What to measure: mutation for checking, coverage for execution, coupling for trust

Coverage is a reliable detector of code nobody runs and an unreliable predictor of fault detection. On large Java programs its correlation with effectiveness drops to low-to-moderate once suite size is controlled, and stronger criteria added little over statement coverage ([Inozemtseva & Holmes, ICSE 2014](https://cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)) [peer-reviewed]; with real faults, higher statement, branch and weak-mutation coverage had little or no effect on fault revelation while strong mutation showed threshold behaviour and the highest fault revelation ([Chekam et al., ICSE 2017](https://discovery.ucl.ac.uk/10058915/7/Chekam_ICSE17.pdf)) [peer-reviewed]. Mutation is not a perfect number either: correlations with real-fault detection are weak once size is controlled, yet suites ranked high by mutation score detect significantly more faults than random suites of the same size, so mutants "give good guidance" ([Papadakis et al., ICSE 2018](https://core.ac.uk/download/154760839.pdf)) [peer-reviewed; methodology contested in ASE 2020 slides by Chen et al., not read in full]. Google concluded the same in practice and shows developers surviving mutants, never a score ([Petrovic et al., arXiv 2102.11378, 2021](https://ar5iv.labs.arxiv.org/html/2102.11378)) [peer-reviewed]. Flake rate cannot be gated at useful confidence: about 170 reruns are needed to be 95% sure a passing Python test is not flaky, and order dependence causes 59% of Python flakiness ([Gruber et al., ICST 2021](https://arxiv.org/pdf/2101.09077)) [peer-reviewed]. The profile per measure follows; costs are inferences for this suite.

| Measure | Detects | Misses | Cost here (unmeasured) | Flakiness | Fit |
|---|---|---|---|---|---|
| Line plus branch coverage, total | code never executed; untaken branches | whether anything is checked | already paid | low | CI gate (existing) |
| Changed-line/arc coverage | new code shipped with no test running it | weak assertions on new code | seconds on the existing run | low | CI gate |
| Per-test coverage (dynamic contexts) | who tests what; unique arcs; selection input | checking strength; subprocess lines unattributed | unknown overhead, much larger SQLite file | low | nightly input to other reports |
| Mutation score, whole package | weak oracles and pseudo-tested code everywhere | 19-27% of real faults uncoupled to simple mutants | likely hours | medium | per-release report |
| Mutation score, named core modules | the same, where consequences are highest | faults elsewhere | tens of minutes nightly | medium | nightly report, later a ratchet |
| Mutation, changed lines only | weak or missing assertions on exactly what changed | untouched code | minutes per PR | medium | non-blocking review aid |
| Red-green record per fix | that each fix has a test that would have caught it | suite adequacy; reverts give 50-67% false positives as a quality score | one targeted run | low | CI check on fix-labelled PRs |
| Historical bug reintroduction / fault seeding | whether past real bugs are still caught | bugs not in history | scales with recorded bugs | low-medium | per-release report |
| Flake rate (shuffled reruns) | order-dependent and nondeterministic tests | fault detection | ~10 x 72 s nightly | it is the flake measure | nightly report, quarantine list |
| Coupling: private imports and patch targets | brittleness on refactor | fault detection | seconds (stdlib `ast`) | none | CI gate on new violations |
| Coupling: message-text assertions | breakage on wording change | legitimate output contracts look identical | seconds | none | report only |
| Duplicates: arc Jaccard, unique coverage, assertion overlap | candidate redundant tests | same arcs, different oracles | needs contexts; ~12.5M pairs, feasible with bucketing | low | review aid; never auto-delete |

For an agent-written suite the three measures with the most signal are therefore **mutation on a bounded scope**, **changed-line coverage** (its precondition: an uncovered line yields a mutant that always survives) and **static coupling** (which measures brittleness, not detection, but protects every other gate from false failures on refactor). Pseudo-tested methods, where deleting a whole body fails no test, exist in every project studied ([Niedermayr et al., arXiv 1611.07163, 2016](https://arxiv.org/pdf/1611.07163)) [peer-reviewed], and an "extreme mutation" pass is a cheap first cut of the same idea.

### 2. Mutation testing in Python: three live tools, none implements Google's design

Only three tools are both maintained and permissive in late 2026. **mutmut 3.8.1** (BSD-3-Clause, released 2026-10-28) forks one child per mutant, runs only relevant tests, can restrict mutation to covered lines and caches results so that only functions whose source changed are re-tested; it has one maintainer and no release provenance ([PyPI](https://pypi.org/project/mutmut/#history); [docs](https://mutmut.readthedocs.io/en/latest/)) [primary]. **Cosmic Ray 8.9.0** (MIT, 2026-11-10) has two maintainers, Trusted Publishing with attestations since 8.4.1, an SQLite session with resume, and the only documented line-level git-diff filter (`cr-filter-git`); it runs the whole configured test command per mutant, with no coverage-based selection, and its local distributor is serial ([PyPI](https://pypi.org/project/cosmic-ray/#history); [concepts](https://cosmic-ray.readthedocs.io/en/latest/concepts.html); [filters](https://cosmic-ray.readthedocs.io/en/latest/how-tos/filters.html)) [primary]. **pytest-gremlins 1.14.1** (MIT, first release 2026-01-27) instruments once and switches mutants by environment variable, selects covering tests, caches by content hash and caps suppressions with `max-pardons-pct`; its sources contradict each other on pytest-xdist and its speed claims are the author's own ([PyPI](https://pypi.org/project/pytest-gremlins/); [docs](https://pytest-gremlins.readthedocs.io/); [v1.3.0 announcement](https://dev.to/mikelane/announcing-pytest-gremlins-v130-53ka)) [primary; benchmarks vendor-only]. **mutatest** (last release 2022-02-20, Python 3.7-3.8) and **MutPy** (2019-11-17, Python 3.4-3.7) are effectively abandoned, and a 2025 comparison could not run either ([NSF PAR 10573281](https://par.nsf.gov/biblio/10573281-analysis-comparison-mutation-testing-tools-python)) [weak]. The best-known new entrant, mutahunter, is LLM-based and AGPL-3.0 ([GitHub](https://github.com/codeintegrity-ai/mutahunter)) [primary].

No surveyed tool documents using pytest-xdist together with coverage.py contexts to choose each mutant's covering tests; mutmut and pytest-gremlins each bring their own selection and parallelism. No tool detects equivalent mutants; all rely on pragmas or operator filters. Timeouts differ: mutmut scales them from the baseline but calls the setting unstable, and Cosmic Ray uses fixed seconds and marks the mutant "incompetent". For thresholds, mature practice either shows no score (Google) or uses a ratchet set just below the current score; StrykerJS ships `high: 80, low: 60, break: null`, so by default it never fails a build ([StrykerJS configuration](https://stryker-mutator.io/docs/stryker-js/configuration/)) [primary, JavaScript ecosystem]. No peer-reviewed source reports a team-wide gated mutation threshold and its outcome, and no Python-specific threshold survey exists.

Google's scale evidence is the reference design. Whole-program mutation was rejected; mutants go only on changed lines with coverage, at most one per line, with more than 100 "arid node" suppression rules; the median change ends up with 7 mutants and 2 survivors; 87.5% of generated mutants are killed by existing tests; and the share of surfaced mutants developers rated productive rose from 15% to 89%, with Python at 70.6% against Java's 87.2% ([Petrovic et al., arXiv 2102.11378, 2021](https://ar5iv.labs.arxiv.org/html/2102.11378)) [peer-reviewed]. Developers exposed to mutants wrote more tests, and mutants were coupled with past high-priority bugs ([Petrovic et al., ICSE 2021, arXiv 2103.07189](https://arxiv.org/abs/2103.07189v1)) [peer-reviewed; no effect sizes in the abstract]. An earlier Google report described 1.1 million mutants over more than 70,000 diffs yielding 150,000 actionable findings ([State of Mutation Testing at Google, ICSE-SEIP 2018](https://research.google/pubs/state-of-mutation-testing-at-google/)) [peer-reviewed]. None of the Python tools implements this design fully; an in-house runner over coverage contexts can copy it (changed core-module lines, a fixed operator set of comparison flip, boolean negation, `and`/`or` swap, return-constant, statement deletion and numeric off-by-one, per-line cap, arid skips for logging, docstrings and `__repr__`, timeouts inconclusive, deterministic report order). No study measures mutation-to-real-fault coupling for Python specifically; all large correlation studies are Java or C.

### 3. Keeping agent-written tests effective: oracles, red-green, and mutation feedback

The section above gives the evidence on how agent tests differ. The mitigations with the strongest support are fail-to-pass checks, mutation-guided writing and acceptance, execution feedback that checks added tests run added lines, and properties from invariants. Mutation feedback in the prompt loop (MuTAP) reported a 93.57% mutation score and 28% more real bugs found than Pynguin ([survey, arXiv 2511.21382, 2025-11](https://arxiv.org/html/2511.21382v1)) [preprint survey; primary not re-read]; Meta's ACH had 73% of its mutation-guided tests accepted by engineers ([arXiv 2501.12862](https://arxiv.org/html/2501.12862v1)) [vendor-only]. Generate-validate-repair loops lift LLM test pass rates from roughly 24-34% raw to above 70% ([arXiv 2511.21382](https://arxiv.org/html/2511.21382v1)) [preprint], but a pass rate is not oracle correctness: a test repaired until it passes tends to encode current behaviour, which is why fail-before-fix matters more than pass-after-fix. An agent that writes Hypothesis tests from type annotations, docstrings and names found genuine bugs in NumPy, SciPy and pandas ([Maaz et al., arXiv 2510.09907, NeurIPS 2025](https://arxiv.org/abs/2510.09907v1); [author-affiliated write-up, 2026-01-14](https://red.anthropic.com/2026/property-based-testing)) [peer-reviewed; the "56% valid bug reports" figure is secondary]. "Test via public APIs" and "test state, not interactions" rest on long industrial practice, not on controlled LLM trials ([SWE at Google ch. 12](https://abseil.io/resources/swe-book/html/ch12.html); [Testing on the Toilet, 2015-01](https://testing.googleblog.com/2015/01/testing-on-toilet-prefer-testing-public.html)) [practice]. No controlled study compares prompt rules such as "no private imports" or "parametrize" against a baseline. Two widely repeated claims stay out of the evidence: that AI tests score "40-55% mutation vs 70-90% hand-written" ([Augment Code guide](https://www.augmentcode.com/guides/mutation-testing-ai-generated-code)) [vendor-only, unverified], and practitioner reports of 28-72% redundancy in AI-written suites ([DEV post](https://dev.to/kirankotari/how-i-reduced-my-test-suite-by-72-using-testiq-3ff2)) [anecdotal].

### 4. Test review rules: twelve items, eight of them scriptable in whole or part

The checklist above is the answer. Its evidence is strongest for items 1 (fail-to-pass), 2 (execute the added lines), 3 (unique checking power) and 10 (no silent test deletion), moderate for 4, 6 and 11, and practice-only for 5, 8 and 9. Items 1, 2, 3, 5, 7 and 10 can be decided by a script; 4, 6, 8, 9 and 11 can be flagged by one; only 12 is pure judgement. What stays with a human or the user's agent is the core of the oracle problem: whether the expected value came from the specification.

### 5. Suite structure: pick the cheapest real boundary, cap the CLI lane

A test's lane follows the cheapest real boundary it needs. In-memory behaviour goes to `tests/unit`. A real git repository, a working tree or several files interacting goes to `tests/flows`, in process with `tmp_path`. Only claims about the process boundary itself (console entry point, argv to exit code, stdout and stderr formats other tools consume, `python -m`, installed resources) go to `tests/cli` as subprocesses, capped at about 50. FastAPI behaviour through TestClient goes to `tests/gui`, and consistency of tracked files to `tests/repo`. Anything checking a flag's effect rather than its parsing calls `main(argv)` in process. Google aims for about 80% narrow, 15% integration and 5% end-to-end tests, warns of the "hourglass" (many unit and end-to-end tests, few integration tests) and says tests lose value as flakiness approaches 1% ([SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)) [practice]. For a single-process CLI, a cap of 50 of about 5,400 items (about 1% end-to-end) is defensible because the end-to-end risk is mostly argv wiring and packaging; no CLI-specific ratio was found. Shared fixtures stay out of a private library when they live in the narrowest `conftest.py`, are small factories with explicit parameters rather than deep chains, are never imported across lanes, hold no assertions, and are reviewed as public API once a second lane uses them (inference from the coupling and hourglass guidance, not a cited rule). A non-blocking shuffled-order run surfaces state leaking between tests, which matters more once CLI tests share one process.

### 6. Property-based testing: the highest signal per test in the toolkit's reach

In a 40-project mutation study, each property-based test found about **50 times as many mutations** as the average unit test, properties checking exceptions, membership and types were more than 19 times more effective than other properties, and 76% of the mutations found were found within the first 20 inputs ([Ravi & Coblenz, OOPSLA 2025](https://2025.splashcon.org/details/OOPSLA/102)) [peer-reviewed]. For this toolkit the payoff ranks as follows: registry, roadmap and planning front-matter round trips (`load(dump(x)) == x`); "parsers and validators raise only the documented validation error" on arbitrary or mutated input, the 19x class; graph-edit invariants after generated add, move, re-parent and delete sequences (no cycles, unique ids, dependencies resolve, validate-export-reload stable); idempotent manifest migration; and a `RuleBasedStateMachine` over the registry and edit lifecycle against a plain-dict model, run in `flows` with one repository per example created in `@initialize` ([Hypothesis stateful docs](https://hypothesis.readthedocs.io/en/latest/stateful.html)) [primary]. Determinism comes from profiles: Hypothesis activates a built-in `ci` profile when `CI` is set, with `derandomize=True`, `deadline=None`, `database=None` and `print_blob=True` ([Hypothesis API reference](https://hypothesis.readthedocs.io/en/latest/reference/api.html)) [primary]. Registering that profile explicitly lets a developer reproduce CI locally, a "nightly" profile (`derandomize=False`, about 1,000 examples) runs non-blocking, and any nightly find becomes a permanent `@example(...)` rather than a version-bound `@reproduce_failure`. Because derandomized examples hash the test function, results do not depend on the xdist worker; because they depend on the Hypothesis version, a pin bump can surface a new failure, attributable to that bump. Generated data stays in process: spawning the CLI per example would break the smoke-lane budget. No source quantified the payoff of round-trip or stateful properties specifically.

### 7. Cost and speed: the in-process move is the one speed change that raises effectiveness

Speed work splits cleanly. Moving about 414 subprocess CLI tests to in-process `main(argv)` calls cuts most of the 32% CPU share and also makes those tests visible to per-test coverage contexts and to in-process mutation tools, which is why M16.7.8 serves effectiveness and not only speed. Coverage contexts give a who-tests-what map for redundancy reports and per-mutant selection. Hypothesis at the default 100 examples in the gate keeps most of the signal, given the 76%-in-20-inputs finding. Pure speed work stays out of the blocking gate: pytest-testmon is forced into no-collect mode whenever it runs under coverage and does not track data files such as the toolkit's YAML, JSON and Markdown templates ([testmon.org](https://testmon.org/)) [primary]; pytest-impacted needs manual mappings for non-Python files and is in beta ([README](https://github.com/promptromp/pytest-impacted)) [primary]; sharding with pytest-split adds nothing xdist does not already give one machine. pytest-rerunfailures inside the gate turns flaky failures green, the opposite of what a flake measure needs ([README](https://github.com/pytest-dev/pytest-rerunfailures)) [primary]. No published figure exists for coverage-context overhead or in-process versus subprocess runtime at this suite's size.

## Adopters need a stdlib default and an opt-in mutation lane

Projects whose code and tests specy-road's agents write face the same failure mode, so the toolkit's default should be Option A's measures, computed by bundled stdlib scripts that read files the adopter's tools already produce. That keeps constraint 1 intact: the toolkit never imports coverage.py, because `coverage json` output parses with `json` and a contexts data file opens with `sqlite3`. A sensible default set is a changed-line and arc coverage report against a configurable floor (90% follows Google's per-commit lower bound and 60/75/90 project bands ([Google Testing Blog, 2020-08](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)) [practice]), the static coupling and hygiene scan with a committed allowlist, a detector for deleted, skipped or loosened tests in a diff, and a fail-on-parent check for changes the roadmap marks as fixes. Each fits the toolkit's existing review flow: the scripts produce findings, and the toolkit renders the judgement items (oracle versus spec, mock justification, contract text, merges) into the review prompt the adopter's own agent runs, so the toolkit still never calls an LLM.

Adopters should opt into three things. A mutation lane detects mutmut or Cosmic Ray if installed and runs on a module list the adopter names, reports survivors per line, never fails on timeouts and offers a ratchet only after a baseline exists. A Hypothesis profile template supplies explicit `ci` and `nightly` profiles and the "convert finds to `@example`" rule. A non-blocking shuffled-order lane uses pytest-randomly or a conftest shuffle with a logged seed. The generated agent instructions should carry the prompt-side rules from the table above, chiefly derive tests from acceptance lines, name for behaviour, assert values and state, stop rather than edit tests, and prefer properties for invariants, because those are cheap and two of them have direct LLM evidence. The toolkit should not ship a gate on whole-package mutation score, on flake rate or on arc-similarity deletions for adopters: each is either too expensive, too statistical or proven to drop fault detection.

## Where the evidence pushes back on the plan

**Retiring tests on zero unique arc coverage overstates what is safe to delete.** The prompt's figures (76% of items cover no unique arc; a greedy 31% reproduces all arcs; the slimming estimate of 30-35% of functions removable "with no coverage loss") measure what is removable without losing coverage, not without losing detection. Coverage-preserving reduction loses fault detection ([Shi et al., FSE 2014](https://mir.cs.illinois.edu/gyori/pubs/fse14reduction.pdf)) [peer-reviewed], and nearly half of Meta's mutation-justified tests added no coverage ([arXiv 2501.12862](https://arxiv.org/html/2501.12862v1)) [vendor-only]. M16.7.1 already improves on a pure arc rule by naming the surviving assertion for each removal and excluding unattributed subprocess tests, and that is the right direction. The evidence supports a stricter criterion where data exists: no unique arc **and** no unique killed mutant **and** an equal or stronger oracle elsewhere. At minimum, the core-module mutation score from Option B should be measured before and after each dedupe leaf.

**"Checks something no existing test checks" should be measured by unique mutant kills, not unique arcs.** The planned review-finding rule is right in spirit. Measured by arcs it over-flags, because two tests on identical arcs with different assertions are not duplicates.

**"Must fail before the fix" is the best-supported rule in the plan, but it is not a quality score.** It is SWT-Bench's fail-to-pass definition and immune to "asserts current behaviour". Yet as a suite-level quality measure, revert-based checks gave 50-67% false positives ([Leith, arXiv 2608.15188](https://arxiv.org/html/2608.15188)) [preprint], and pass-then-invert generation shows agents can satisfy it with tautological oracles ([AssertFlip, arXiv 2507.17542](https://arxiv.org/html/2507.17542v1)) [preprint, secondary]. Pair it with the oracle-strength check.

**The message-text rule should be report-only, not a ban.** No study links message-text assertions to lower fault detection or more false failures, and some CLI wording is a user-facing contract. The 1,496 count is a lead for review with an allowlist, as the planned rule's "structured results" wording already implies.

**The planned rules miss three evidence-backed items:** forbid deleting, skipping or loosening tests in the same change as a fix without naming the covering test; require added tests to execute added lines, error paths included; and prefer real collaborators over in-package mocks. Each has 2026 agent-PR evidence behind it.

**Raising the coverage floor is not the next step.** The current 90 floor, set from a 90.57% baseline, already sits at Google's "exemplary" band, with logarithmic returns above it ([Google Testing Blog, 2020-08](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html)) [practice]; a changed-line floor catches the thin spots (milestone rollup, the 0% migration module) that a total floor averages away.

**M16.7.8's in-process move adds flake risk the plan should measure.** With 59% of Python flakiness caused by order dependence ([Gruber et al., ICST 2021](https://arxiv.org/pdf/2101.09077)) [peer-reviewed], moving hundreds of CLI tests into one process raises exactly that risk. The leaf's "Done but wrong" check (same results under `-n 0`, `-n auto` and per file) is right; a shuffled-order run belongs beside it.

**The rest agrees.** The plan's other points match the evidence: "coverage proves execution, not checking", the ~50-item smoke lane, the five Hypothesis properties and "speed is the wrong goal". The evidence strengthens the first (even mutation weakens on buggy code, per Zhao et al.) and suggests the properties should lead with the "only documented errors" class.

## Conclusion

The question the maintainer posed, which measure says the suite catches regressions, has a sharper answer for an agent-written suite than for a human one: the documented defect is assertions that check too little, so the measure must perturb the code and see whether anything notices. Coverage stays as a cheap, deterministic precondition and changed-line coverage closes its averaging blind spot, but neither can judge the dedupe and consolidation work M16 is about to do, because that work preserves arcs by design. A bounded mutation score is the only proposed measure that sees an oracle disappear.

The sequencing matters as much as the choice. Mutation tools, per-test contexts and test-impact analysis all assume tests run in the measured process, and today a third of the suite's CPU goes to children those tools likely cannot see. M16.7.8 therefore both adopts the measure and is the change that makes the measure trustworthy, which argues for Option B now, with Option C's per-PR survivors as the step after in-process conversion, and for letting a half-day pilot, not this report's estimates, set the module list, the tolerance and the buy-or-build call.
