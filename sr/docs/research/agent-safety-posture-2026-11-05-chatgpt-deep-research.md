# Executive Summary  
- **Signed reviews:** Enforcing cryptographically signed approvals ensures full commit history integrity.  For high-assurance projects (e.g. SLSA L3+), require signing by default; for small teams, keep it optional but warn if disabled, and use hardware or isolated key storage (YubiKey/OS keychain) to keep keys out of the executor’s reach.  
- **Harness capability matrix:** Claude Code and Codex CLI both sandbox file and command access. Claude Code permission rules parse commands and can block unsafe constructs (e.g. `eval`), but only the **Bash sandbox** (via bubblewrap on Linux or sandbox-exec on macOS) and container/VM isolation actually confine file/network access.  Codex CLI’s default “workspace-write” mode forbids writes outside the repo and blocks network access unless enabled; it also marks `~/.git`, `~/.codex` and `~/.aws` read-only.  Cursor CLI lets you define `permissions.allow`/`deny` lists and an interactive sandbox in Auto or Allowlist modes.  None can enforce all controls (e.g. subagents or eval hacks can bypass parsing), so rely on OS or CI policies for isolation.  
- **Isolation:** For a single dev, the lowest-friction sandbox is Claude’s built‑in or Anthropic’s **sandbox-runtime** (uses bubblewrap/sandbox-exec) or Cursor’s terminal sandbox – these confine shell commands and basic I/O with minimal setup.  For stronger isolation, use **Dev Containers** or Docker/Podman (rootless if possible), gVisor, or a microVM (Firecracker/QEMU).  Devcontainers or rootless Docker require installing Docker CLI (License: Apache-2), but offer good separation.  gVisor adds kernel-level enforcement (Google-maintained, Apache-2) at higher overhead.  Firecracker (Rust, Apache-2) provides strong VM isolation but requires virtualization support (high friction).  The toolkit can **detect** container environments via cgroups or special files (e.g. `/proc/self/cgroup` entries for Docker, presence of `.dockerenv`), and verify VM vs host via low-level checks (e.g. CPUID or filesystem markers).  
- **Destructive ops:** Static filters (e.g. denying `git push --force`, `terraform destroy`, `kubectl delete`, or DDL without WHERE) catch obvious cases but have many false positives and bypasses (aliases, scripts, or injection of variables).  In practice, platform controls are safer: use branch protection to disable force-push, minimal IAM roles to forbid deletes, and database safe-mode options (e.g. MySQL `sql_safe_updates`, migration scripts that require explicit migration review).  We suggest building a short “dangerous commands” blacklist (for warning) but relying on **least privilege and policy** (e.g. cloud IAM, DB privileges, protected branches) for enforcement.  
- **First slice:** (1) Compile and codify each harness’s sandbox/permission capabilities (see matrix) so users can choose safe defaults. (2) Define posture levels and related guardrails (e.g. “Prototype vs. Production” table below). (3) Implement key-management patterns: e.g. detect if reviewer has a hardware-protected GPG/SSH key, or is a separate OS user, and warn if not. (4) Integrate static scans (gitleaks/TruffleHog) for secrets and simple command blacklists into the toolkit. (5) Build the “advisor” prompt and deterministic output format to review policy attestation.

## Answers to Open Questions

### 1. Signed reviews by default? 
Signed commits/reviews **strongly reinforce integrity**: a signature on the branch tip vouches for the entire history.  Supply-chain frameworks (e.g. SLSA Level 3/4) effectively require tamper-evident commits, implying signing is expected in production contexts. However, requiring it by default imposes friction (key management, onboarding) on small teams.  A balanced approach is recommended: **default off with advisory** for non-sensitive projects, but **default on for high-stakes/internal/production projects**.  Compare guidance: the OpenSSF Scorecard’s *Code-Review* check encourages human review (not necessarily signing), but *Signed-Releases* (even for tags) scores high for authenticity.  Best practice is to keep reviewer keys off the agent machine (e.g. separate OS user or HSM).  For example, run the agent as an unprivileged user `agentuser` with its own SSH/GPG key, or use a YubiKey/GPG card so the private key never leaves the device.  Combined with branch protection (no force-push, require PR review), this ensures the agent cannot approve its own changes.  

### 2. Harness permission/sandbox capabilities  
The capability matrix above summarizes current status.  In brief:

- **Claude Code CLI (late 2026):** Uses an AST-based permission system.  Every shell command is parsed against rules, defaulting to prompt or deny if not explicitly allowed.  It has a built-in *sandboxed Bash* mode (`/sandbox`) that confines Bash/PowerShell commands to an OS sandbox (bubblewrap on Linux, `sandbox-exec` on macOS); however, Claude’s built-in file and git tools (MCP servers, file I/O) still run on the host unless you run the *whole process* inside a VM or container.  The CLI has flags like `--restricted` (disables almost all commands) and `--dangerously-skip-permissions` (auto-approve mode, which must be paired with an isolation boundary).  **Gaps:** Some constructs (`eval`, complex scripts) always prompt; the limited “critical-path” checks on `rm` do not catch all harmful cases.  
- **OpenAI Codex CLI:** Enforces an OS-level sandbox by default.  In “workspace-write” mode, Codex may write to files in the repo and run commands there automatically. It *forbids* writing to protected dirs (`.git`, `.codex`, `.aws`) and disallows network unless explicitly turned on in `codex.json`.  The *approval policy* (Auto/On-Request/Never) governs whether actions outside that sandbox (e.g. writing outside workspace, network calls, or destructive commands from apps) must be approved.  **Gaps:** The “danger-full-access” mode drops all sandboxes/approvals (explicitly warned against). Legacy `untrusted` mode is broken. Network proxies only filter if enabled.  Without proper rule config, scripts could bypass e.g. cloud delete tools.  
- **Cursor CLI:** Uses explicit allowlists (`permissions.allow`) and denylists in its config.  Commands not on the allowlist will run in a sandbox when “sandboxing” is enabled (Auto-review or Allowlist modes). The sandbox denies unauthorized file reads/writes and blocks network by default (only domains on the Org’s allowlist are reachable).  If sandboxing is turned off (Run-Everything mode, or `agent sandbox disable`), the agent gets full access. The CLI flags `--force`/`--yolo` skip prompts (still obey deny rules). **Gaps:** Historically, Cursor’s headless mode had bugs ignoring sandbox config. Its `.cursorignore` is not applied to output of terminal commands outside sandbox (so secret files might leak via shell commands).  Complex shells or environment tricks could slip past the rudimentary sandbox.  

Where these tools fall short, rely on OS/CI: e.g. use Linux containers or VMs to isolate network/filesystem, enforce branch protections to prevent dangerous pushes, and use cloud IAM or DB privileges for destructive actions. 

### 3. Destructive-operation protection  
Static command filters can spot many red flags (e.g. pattern-match `rm -rf /`, `git push --force`, `terraform destroy`) but are brittle. For example, `terraform destroy` could be evaded by aliasing it or editing the Terraform config to an empty state, and SQL filters (`DELETE` without `WHERE`) often block legitimate bulk updates. In practice, **platform controls** are more reliable: require non-administrative cloud roles (so no IAM user can delete production buckets), enable resource-level protection (DB triggers that refuse drop without confirmation), and enforce *immutable* version control (protected branches to disallow force-push, mandatory PR reviews). Some specific defenses:
- **Git:** Enable branch-protection rules (disable force-push, require status checks and reviews) on main branches. This prevents most push-based attacks.
- **Terraform/K8s:** Avoid agent calling `destroy` or `delete`; instead enforce managed IaC pipelines. If needed, use server-side locks or Multi-Factor Authentication for destruction. HashiCorp’s docs note that `terraform destroy` should only be used with caution (prefer manual `destroy -target=`).  
- **SQL:** Use safe-update modes (MySQL `sql_safe_updates`) or tools like `pg_safeupdate` to forbid blind DELETE/UPDATE. Training devs on safe migrations (using diff-based migration frameworks) is often better than trying to parse SQL strings.  
Because deterministic filters have **high false positives and bypasses**, the toolkit should treat them as *advisory warnings* and point users to “hard” platform mitigations (least-privileged IAM, backups, fail-safe policies) as the ultimate protection.  

### 4. Isolation options for a local developer  
Options (ranked low→high friction / weak→strong isolation):
- **Internal CLI sandboxes:** 
  - *Claude’s built-in sandboxed Bash:* minimal setup (`claude /sandbox`); blocks shell commands outside allowed ones and basic network. (Weak, since file I/O tools are unconfined.)  
  - *Cursor’s sandbox:* enabled per Run Mode; restricts file/network but only in some modes. 
- **Dev Containers / Docker / Podman:**  Requires Docker/Podman installed. Spinning up a devcontainer isolates the entire IDE environment in Linux namespaces. Friction: medium (must write a Dockerfile or use standard image). Strength: high (almost full OS sandbox, but same kernel).  
- **Rootless containers:** e.g. Podman or rootless Docker. Harder initial setup, but no sudo needed. Friction: medium. Isolation: similar to above.  
- **gVisor:** Runs containers through a user-space kernel. Setup requires installing gVisor (runsc). Friction: high. Isolation: stronger kernel emulation (better syscall filtering).  
- **MicroVM (Firecracker/QEMU):** Firecracker requires KVM support; QEMU needs KVM or slower emulation. Friction: very high (must manage VM images, virtualization). Isolation: very strong (separate VM kernel).  
- **Separate VM (VirtualBox, VMWare):** Friction: very high (full VM management). Isolation: very strong, but heavy.  

**Detection:** The toolkit can *verify* container isolation by checking cgroups (e.g. `/proc/1/cgroup` contains "docker" or "libpod"), or files like `/.dockerenv`. For DevContainers, one can check environment vars like `DEVCONTAINER=true` or well-known filesystem roots. For VM vs host, check virtualization flags (e.g. output of `lscpu` or `/sys/class/dmi/id/product_name` for “KVM” or “Firecracker”). *Attestation* is hard for a user-only tool; the user may need to confirm manually what isolation they are using. 

### 5. Posture model and default  
We propose posture levels (in order of increasing trust/data-sensitivity): **Prototype → Internal → Production → Sensitive**.  Each level ups the guardrails: 

- **Prototype:** Ad hoc development. No production credentials accessible. Agent auto-prompts everything; minimal sandbox (allow basic workspace write, interactive). *Protections:* no auto-approve; optional sandbox; minimal gating.  
- **Internal:** Shared team use. Code is vetted but not public. Use branch protection (no force-push), one human reviewer. Use sandbox or limited write mode by default. *Protections:* require PR review, sign commits, scan for secrets; network off by default.  
- **Production:** Customer-facing infrastructure or critical data. Strict isolation, audited CI. *Protections:* signed commits enforced; full sandbox/container; `--dangerously-skip-permissions` disallowed; auto-scan (gitleaks); DB and cloud roles locked down; destructive ops disabled.  
- **Sensitive:** Highest risk (PII, financial). Beyond production: no local secrets, can run agent only in VM/hardware-isolated environment. *Protections:* every external call must be whitelisted; multi-person code approvals; cryptographic attestations of builds (in-toto/SLSA L3+); continuous monitoring.  

These map to frameworks as follows: NIST AI RMF emphasizes risk-based controls (governance, dynamic risk management), so higher posture levels require stronger “govern” and “manage” activities. OWASP LLM Top 10 (2026) highlights excessive agency (LLM03) and sensitive data leakage (LLM02) – higher posture must strictly limit agent permissions and ensure data access is vetted. SLSA levels suggest internal projects use automated builds and provenance (Level 2), while production demands two-person review and attestation (Level 3/4).  For **unconfirmed posture** (no explicit tier set), default to a safe middle-ground: treat it like Internal-level (require one review, use sandbox) until the user upgrades the posture. 

### 6. Advisor prompt design  
The advisor prompt should: (a) load the project’s governance docs (constitution, policies) but scrub any user-provided metadata to avoid prompt injection (e.g. remove code fences, URLs). (b) Explicitly instruct the agent to produce a *structured* posture recommendation with citations to those docs (for evidence). (c) Use a fixed template and deterministic rules (no randomness) so changes are diffable. For example, prompt the assistant as: *“Given the following governance rules [insert sanitized text], classify this project’s risk and recommend posture level (Prototype/Internal/Production/Sensitive). Cite the relevant rules by name. Ensure output format is stable JSON or YAML.”*  Key is isolation: do not let the agent “update” its own prompt. If the docs contain malicious instructions, the system should parse them as data (e.g. via tokenizer filtering) or use a verification model to ignore contradictory instructions. Determinism can be improved by specifying exact phraseology for levels and requiring numbered lists.  

### Disagreements with prior runs  
Our findings largely **agree**: use least privilege and isolation over just pattern-blocking, and enforce branch protections and dual reviews. Where we differ: the previous runs leaned toward turning on signed reviews only internally. We suggest a more data-driven stance: enforce signing and hardened controls by default for any project handling sensitive or production assets (in line with SLSA3 guidance). Conversely, we recognize that for “prototype” or small open-source projects, the cost may outweigh benefits, so a warning (rather than hard-on) is acceptable. We also emphasize verifying the actual sandbox environment (e.g. cgroup checks) more strongly, whereas prior runs focused on configuration defaults.
