# Critique of the M16 plan (Grok)

Read-only review of the M16 phase sheet, the 35 leaves in `sr/roadmap/phases/M16*.json`, and the slimming analyses. No cycles in the graph. The phase sheet's parallel lanes are not what the edges and touch zones allow.

## Changes (priority order)

1. **M16.0, M16.1, M16.11, M16.15, M16.16, M16.17, M16.7 — harness does not cover the moves that can change behaviour.** Severity: **high.**
   - Problem: M16.0 is `--help` goldens, one happy-path loop (init → add-node → scaffold → pickup → ready → two reviews → gate → finish, merge and PR, offline), `upgrade --dry-run`, and dogfood validate/export/digest. M16.1 is the review-policy table. The phase sheet says every later leaf stays behind that harness. These leaves are outside it:
     - M16.7 drops the child interpreter (`python -m`, six `ROOT = Path.cwd()` globals, nested `doctor` → `registry_prune` and `mark-implementation-reviewed` → `cli`). Help text and one loop do not catch cwd/env leakage or a nested exit code.
     - M16.11 collapses five cleanup paths that the code report says each have their own merged/live rule. Acceptance checks a deprecation line, not which branches, worktrees, registry rows, or stashes are selected.
     - M16.17 replaces five eligibility copies with `check_assignment`. A new table does not prove the five agreed. Divergence is the bug the leaf exists to remove.
     - M16.15–M16.16 move the worker runtime and add an `orphaned` claim class. The loop never launches a worker, takes a lease, or reconciles. "Worker test suites unchanged in behaviour" does not name a corpus.
   - Proposed change: Before those leaves, add frozen corpora and make the leaf fail if behaviour moves: (1) M16.7 — one process runs two commands and a nested doctor/mark-reviewed call; stdout, stderr, and exit codes match a subprocess capture taken at pickup. (2) M16.11 — one fixture, four old commands' dry-run action lists, and `doctor --prune --kind …` must match each list. (3) M16.17 — same inputs through the five current functions and `check_assignment`; rule id must match, and message text must match where a test already asserts it. (4) M16.15 — a claim/worker/worktree/review fixture table (live, clean exit, failed exit, no worker and no review, review and no worker, worktree and no worker) with an expected status per row. (5) M16.16 — existing worker tests pass with only import paths and patch targets edited.

M16.3, M16.4, M16.5, M16.9, and M16.10 also list `tests/` and do not depend on each other. Touch-zone locking serialises them; ignoring it makes them conflict on merge.    - Proposed change: Code leaves do not edit tests except a path list the test lane consumes. Start M16.23 only after the code lane through M16.22, or give each code leaf a named test glob and remove `tests/` from M16.23 until those globs are idle. Make M16.25 depend on M16.27. Make M16.26 depend on M16.10 (`llm_client.py`), M16.16 (`worker_process.py`), and M16.18 (guard tests). Make M16.27 depend on M16.9 and M16.24.

5. **M16.6 — one leaf, two subsystems, and an SCC cap the code report does not ask for.** Severity: **high.**
   - Problem: Zone is `specy_road/`, `bundled_scripts/`, and `tests/`: 102 library modules, a 45-module cycle, and a 25-module cycle. That is more than one executor plus two reviews. Acceptance says no strongly connected component exceeds 10 modules. `01-code.md` §8.2 asks for a shrink-only baseline.    - Proposed change: Four leaves: move the named 29 modules; break the 45-cycle; break the 25-cycle plus `nested_repos` (or leave that cycle to M16.9); add the shrink-only layering gate. Replace "no component exceeds 10" with "the 45- and 25-module components are gone from the baseline, and CI fails if any component grows".

6. **M16.25 — arc-set equality plus "or kept with a reason" is the open review loop, aimed at 2,200.** Severity: **high.**

Review checks that the rows were applied. Drop 2,200 as a pass/fail. Forbid deleting a test whose assertion is not named on the surviving test. Split by subsystem (review gate, guard, worker, pickup/finish, the rest), each leaf keeping that subsystem's arc set. Optional mutation check stays optional and off the acceptance line.

## Verdict

The programme matches the maintainer's rulings: workers stay in core, rc4 is the fix window, rc5 is this refactor, aliases last one release, the file cap is already 1,000, and M16.22 is the post-fix rule made into a gate. Pass 0, interface-before-move, and shrink-only line width are the right shape.

It is not safe to pick up as registered. The parity harness does not see cleanup, eligibility, workers, or in-process dispatch, which are the leaves that can drop behaviour. Touch zones put the test lane and several "parallel" pairs on the same files. M16.4 and M16.5 cannot satisfy their own greps inside their zones. M16.6's cap of 10 fights D1. The line budgets add up to about 61k source lines, not 52–56k, and ≤50 commands is not implied by the renames that are actually listed. 2,200 tests and 35 s repeat the analysis headlines with the safety criterion the analysis said not to use.

Fix items 1–11 before pickup. After that the critical path is about eleven serial code leaves (M16.2 → M16.4/M16.5 → M16.6 → M16.7 and M16.15 → M16.16 → M16.17 → M16.13 → M16.21 → M16.22 → M16.33), with docs joining at M16.32 and tests joining at M16.28. Wall time sits on M16.6, M16.16, and M16.25, which is why those three have to be split first.
