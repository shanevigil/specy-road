# Effective unit testing when agents write the code and the tests

Research report for specy-road · 2026-11-06 · Codex

## 1. Executive recommendation

Adopt three complementary measures: **branch coverage by subsystem, targeted mutation effectiveness, and historical regression detection**. Coverage identifies missing execution; mutation analysis probes whether assertions distinguish faulty behavior; historical bugs test whether the suite catches failures that actually mattered. None establishes that the specification itself is correct. Review the source of expected results independently of the implementation.

Keep suite runtime and test count as operational context. Neither is an effectiveness target. Do not set a deletion quota, a test-to-production-lines ratio, or a target percentage of tests with unique coverage.

The following are proposed starting policies for the maintainer to choose, not changes to repository configuration. Thresholds and cost budgets are engineering judgments, explicitly distinguished from research results. This research did not execute the suite or benchmark candidate tools. The supplied suite measurements are accepted as the baseline; the earlier per-test snapshot is not treated as a current measurement.

| Measure | Definition and scope | Starting policy | Cadence and expected cost |
| --- | --- | --- | --- |
| Structural coverage | Report executed statements and taken branch destinations separately for the whole package and each named core subsystem. Preserve the existing coverage.py combined `fail_under` gate. | Keep the configured floor unchanged. Report separate branch percentages and missing branches. Initially report changed executable-line coverage against a **90% proposed target**; gate only after validating attribution and explicit exceptions. Do not substitute 90% for the existing floor. | Every PR, with complete ordinary test lanes. Coverage adds instrumentation overhead; measure it on CI. Reporting from existing data costs seconds rather than another suite run. |
| Targeted mutation effectiveness | Report confirmed behavioral kills among valid, non-exempt mutants in named core modules; separately report uncovered sites, unresolved survivors, timeouts and analysis completeness. Use changed functions for PR feedback and a fixed subsystem population for trends. | **Report only initially.** No whole-package score gate. Triage a bounded PR batch, proposed maximum 50 mutants. After calibration, require continued kills for a small, reviewed set of essential mutants; retain human review for new survivors. | Optional PR report; nightly rotation through core modules; release summary of a completed sweep. Pilot budget: 10–20 minutes per PR batch, 30–60 minutes per nightly batch. These are budgets, not predicted completion times. |
| Historical regression detection | Fraction of executable, curated historical bug reintroductions that produce the intended behavioral failure in today's tests while the clean code passes. Pair this with red/green evidence for new fixes. | Start with **20–30 representative bugs**, report only during corpus construction. A stabilized mandatory corpus should retain **100% detection** of its applicable cases. Report unexecutable and obsolete cases separately, never as successes. | Red/green record on each applicable fix; replay affected corpus cases per PR after stabilization, full corpus nightly and before release. Initial budget 15–30 minutes per full replay; actual time depends on isolation and selected tests. |

Treat **flake incidence** as a reliability requirement across all three measures: ordinary PR tests do not gain a passing status from retries. Measure first-attempt failures and same-revision outcome variability. Randomized discovery runs belong in an advisory lane until each discovered failure has a reproducible case. Static coupling and duplicate-test reports are review aids, not quality scores.

Suggested first mutation scope: milestone rollup (`finish_ancestor_rollup.py`, `milestone_rollup_git.py`), outline edits (`bundled_scripts/roadmap_outline_ops.py`, `roadmap_outline_group.py`, `roadmap_outline_renumber.py`), and stable-key migration (`bundled_scripts/migrate_stable_node_keys.py`). These are proposed targets, not claims that each file corresponds exactly to the earlier coverage snapshot. Include the migration module identified by that analysis even if its current name differs. Add a small set of review/claim state-transition functions because their consequences are high, while avoiding another broad test-writing campaign over already heavily tested worker flows.

**Purchasing decision:** retain coverage.py and the already approved Hypothesis; prefer a pinned, isolated mutmut lane as the first mutation implementation. Use Cosmic Ray as an optional alternative if its git filters or execution model solve a demonstrated problem. Add pytest-randomly as a test-only dependency if the maintainer accepts a separate discovery lane. Keep pytest-testmon optional for local iteration. Build only small reporting and policy scripts over existing pytest/coverage data, not another mutation engine. The full weighted assessment appears in section 8.

Sources below are primary research papers, official documentation, registries, source repositories and maintainers' issue reports, accessed **2026-11-06**. Publication/release dates are given where available; undated living documentation is identified by access date. Peer-reviewed research is stronger evidence than vendor claims, but results from Java, Kotlin, Elixir or synthetic benchmarks do not supply a Python-toolkit effect size. Recent preprints receive lower confidence. A maintainer's bug report establishes a reported tool limitation, not its incidence in specy-road.

Two checkout observations supplement the supplied context: the existing [weekly mutation workflow](../../../.github/workflows/mutation.yml) and the repository's [dependency-verification policy](../../../docs/supply-chain-security.md), both inspected 2026-11-06. These support the integration cautions in sections 8 and 11; they are not new suite measurements.

The distinction between execution and checking has empirical support. Inozemtseva and Holmes studied 31,000 suites across five Java systems and found only low-to-moderate coverage/effectiveness correlation after controlling suite size. Stronger coverage criteria did not remove the limitation. That supports using branch coverage to locate gaps, not interpreting a higher percentage as a direct estimate of regression protection. [ICSE paper, 2014](https://cs.uwaterloo.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf).

## 2. What to measure and how to interpret it

### 2.1 Comparison of candidate measures

Cost descriptions concern this approximately 5,400-item suite. They are relative estimates; the supplied 72-second result on 32 CPUs does not predict GitHub Actions time, serial time, coverage overhead or mutation throughput.

| Measure | Detects | Misses and likely failure modes | Cost and variability | Appropriate use |
| --- | --- | --- | --- | --- |
| Statement/line coverage | Unexecuted executable statements, untouched modules and missing execution paths that include new lines. | Whether any assertion depends on execution; wrong expected results; most data partitions; both outcomes of a fully covered conditional. | One instrumented suite run. Low metric variability with isolated tests and identical environments. Missing subprocess data can create systematic error. | Preserve whole-package gate; per-file/subsystem report; changed-lines review aid or calibrated gate. |
| Branch coverage | Untaken destinations of conditionals and loop exits, including paths hidden by full line coverage. | Path combinations, condition independence, semantic partitions within one branch, concurrency schedules and assertion correctness. It is not MC/DC or exhaustive path coverage. | Same instrumented run with branch collection; usually more data and overhead than statements alone. Structurally reproducible with pinned interpreter and exclusions. | PR report by subsystem; retain existing combined gate. Explicit core branch targets only after baseline review. |
| Per-test context coverage | Which collected item/phase executed which code; incidental fan-out; candidates for consolidation; tests potentially affected by a mutation. | Which assertions inspect that code. Shared setup, teardown and subprocess attribution can dominate similarity. | One context-instrumented run plus a larger database. Pairwise similarity needs care at this scale. Data attribution is less stable than aggregate coverage. | Periodic report and review/navigation aid. Never gate on minimum unique arcs per test. |
| Whole-package mutation score | Assertion insensitivity across the chosen operators and whole mutation scope. | Specification errors, missing functionality, unrepresented fault classes; equivalent mutations and irrelevant operators distort interpretation. | Potentially thousands to tens of thousands of test executions; timeouts and tool incompatibilities complicate results. No reliable extrapolation from suite item count alone. | Occasional completed audit or release experiment, not the first PR gate. |
| Named-core mutation score | The same sensitivity question, localized to important logic, with survivors reviewers can understand. | Unscoped code and omitted operators; score inflation if only covered sites are counted. | Bounded population, selected tests, outer parallelism; manageable pilot/nightly work. Low variability only after baseline, selection and timeout checks. | Best initial mutation report; later gate a stable set of essential behaviors or mutants. |
| Changed-code mutation | Assertion weaknesses in a PR's changed functions or executable lines. | Unchanged callers, interactions, deleted code and newly missing requirements; line mapping can miss adjacent guards. | Small PR batches often practical, large refactors may exceed a budget. Sampling creates incompleteness, not proof of adequacy. | PR review aid; narrowly calibrated gate after a pilot. Periodic wider mutation prevents neglect of old thin areas. |
| Historical bug replay | Whether the present suite detects a reintroduced, meaningful historical fault. | Future fault classes, bugs absent from the curated corpus and invalid modern ports of old fixes. | One isolated faulty-code trial per case plus clean controls; selection can reduce test execution. Patch drift is a maintenance cost. | High-value periodic report; small validated corpus can be a deterministic gate. |
| Deliberate fault seeding | Detection of specified risks such as omitted rollback, stale review acceptance or dropped graph edges. | Seeds chosen to suit existing tests; unrealistic faults; correlated agent-generated seeds and oracles. | Similar to a small mutation campaign, with more author/reviewer effort. | Review aid and periodic complement to historical cases. Label seeded and historical results separately. |
| Red/green fix records | Evidence a particular assertion distinguishes a known faulty revision from its fix. | Whether other tests already checked it; future protection after refactoring; correct specification. | Usually two focused runs; failures before collection or due to missing APIs are not valid behavioral evidence. | Review requirement for applicable fixes, supported by reproducible records. |
| Flake incidence | Unreliable pass/fail signals, state pollution and scheduling-sensitive tests. | Rare events not sampled; pass-only repetitions cannot establish zero flakiness. | Ordinary-run telemetry is cheap; repeated fresh-process trials cost up to the repetitions times lane runtime. | Ongoing reliability report; deterministic known regressions gate normally. Never gate on a noisy rolling-rate threshold. |
| Test/code coupling | Private imports, private patch targets, production call-count assertions, brittle output matching, cross-test imports and source-text checks. | Whether a dependency or message is a legitimate public contract; dynamic aliases and indirect patch targets. | AST/text scan over about 74k test lines is cheap relative to suite execution. Low execution noise, semantic false positives. | Diff review aid; gate exact policy violations with narrow scope and reviewed exceptions. |
| Arc-set similarity | Tests traversing almost identical execution; incidental coverage; candidate groups for review. | Different expected values, data partitions, environment/process behavior and concurrency interleavings on the same arcs. | One context run. Naive all-pairs comparison of 5,408 items has 14,620,528 pairs, potentially expensive with large sets. | Periodic candidate report within subsystems; no deletion or deduplication gate. |
| Assertion overlap | Copy/paste assertions and near-identical arrange/act/assert structures. | Semantically equivalent assertions with different syntax; shared helpers; distinct inputs that make identical assertions valuable. | Linear AST normalization then indexed grouping is cheap; semantic interpretation remains manual. | Review aid, combined with behavior tables and fault-detection evidence. |

Coverage.py's combined percentage counts statement opportunities and branch destinations together. Keep separate line and branch totals in reports so an improvement in easy statement coverage cannot conceal a decline in important branch coverage. Branch totals and execution arcs are also different populations: not every recorded arc represents a branching decision. [Official branch measurement documentation, accessed 2026-11-06](https://coverage.readthedocs.io/en/latest/branch.html).

### 2.2 Operational definitions that prevent misleading scores

**Coverage:** compute line coverage as executed executable statements divided by executable statements, and branch coverage as taken possible branch destinations divided by possible destinations. Use the same interpreter, source scope and exclusions in comparisons. A file with no branches has branch coverage **N/A**, not an invented 100%. Review exclusion changes in the diff. Publish numerators and denominators, especially for small modules.

**Mutation:** publish at least generated, excluded, invalid, uncovered/no-selected-test, executed, confirmed behavior-killed, survived, timed-out, infrastructure-error and pending counts. A confirmed behavioral kill can be an assertion failure or a contract-relevant unexpected error caused by the mutant; record which. Do not discard a real regression merely because the test encounters the wrong exception before reaching its final assertion. State whether an import-time failure is a valid behavioral kill or an invalid mutant. For a population of valid non-exempt mutants, use:

`conservative detection fraction = confirmed behavioral kills / all valid non-exempt mutants in the declared population`

Uncovered, unresolved and pending valid mutants are not kills. If viability of pending mutants is unknown, publish a provisional lower bound over all not-yet-excluded candidates and label it incomplete. Also show an executed-population score for diagnosis, but never present it as complete-package effectiveness. A timeout is not an assertion kill; it may indicate nontermination and merits separate assessment. Excluding a proven equivalent mutant requires recorded reasoning, not an agent's unsupported label.

For a tool configured to generate only covered mutants, describe the result as **covered-code mutation sensitivity** and publish structural coverage alongside it. Missing sites are not recoverable from its mutant denominator. Comparing that score to an unfiltered run is invalid.

**Regression replay:** `detected applicable cases / executable applicable cases`, accompanied by `executable / all curated cases`, unexecutable reasons and results by subsystem/fault family. A clean control must pass. A faulty trial counts only if a designated behavioral assertion fails; collection failures, incompatible dependencies or an unrelated crash do not count. Do not publish a single blended percentage combining historical bugs and synthetic seeds.

**Red/green compliance:** report applicable fix PRs with a valid record divided by applicable fix PRs, not number of tests added. A reviewer may find that an existing test already fails before the fix; then record the existing node ID and why CI missed it instead of manufacturing another test. For code whose old API cannot run the proposed test, use a reviewed local fault patch against the current API or mark the parent-based record inapplicable. Do not count an import error as red.

**Flakes:** retain first-attempt failures per test execution and distinct same-revision pass/fail-varying node IDs per observation window, partitioned by Python, OS, worker count and seed. Failure-then-success on retry is evidence of variability, not proof that the first failure was harmless. Infrastructure outages and genuine schedule-dependent production bugs require classification. With independent trials and zero failures in `n` trials, the approximate 95% upper failure-probability bound is `3/n`; 20 successful reruns cannot establish a very low flake rate. Independence is an assumption, often violated by shared state.

### 2.3 Use per-test contexts without making them a test-value oracle

Coverage.py's built-in `dynamic_context = test_function` identifies functions. Pytest-cov's `--cov-context=test` records pytest node IDs, including parameter cases and setup/run/teardown phases. These are not interchangeable when comparing collected items. Use one context mechanism at a time; two independent switchers can interfere. If pytest-cov is not already approved, either approve it as a test-only integration or use the existing attribution harness through public pytest hooks and coverage's public switching API. [Coverage contexts documentation, accessed 2026-11-06](https://coverage.readthedocs.io/en/latest/contexts.html); [pytest-cov contexts, updated 2026-10-18](https://pytest-cov.readthedocs.io/en/latest/contexts.html).

Use `CoverageData.measured_contexts()`, `set_query_context()` and `arcs()` rather than reading private coverage internals. Normalize filenames to repository-relative identities and keep phase information. Shared fixtures may execute once for a group; their arcs do not mean every subsequent test lacks setup or value. Preserve unattributed/import-time coverage separately. [CoverageData public API, accessed 2026-11-06](https://coverage.readthedocs.io/en/latest/api_coveragedata.html).

For duplicate candidates, compare `(file, from_line, to_line)` sets within a subsystem and the same source revision. Prefer inverted indexes and exact fingerprint groups before expensive similarity comparisons. Keep behavior IDs, input partitions, observable assertions and lane beside each candidate. Assert-AST normalization should preserve expected constants and parameter tables; normalizing all literals away erases the distinctions under investigation. Empty arc sets should form an “unattributed/no measured package code” group, not an automatic duplicate class.

A consolidation is acceptable when the retained table/property/scenario preserves the relevant behavioral obligations and historical regression checks. Re-run the same selected mutation population before and after when practical; at minimum inspect distinct assertions and retain every known distinguishing case. A greedy coverage set is a navigation aid, not a replacement suite. Even identical mutant kill sets cannot establish complete redundancy against faults outside those operators.

### 2.4 Historical regressions as a reusable effectiveness benchmark

Build a small corpus spanning rollup propagation, outline identity/references, migration preservation, claim ownership, stale review rejection, partial writes, crash recovery and real git semantics. Select by user consequence and fault family, not ease of making a clean inverse patch. Include escaped bugs and review-discovered defects, tagged separately to expose selection bias.

Each case needs a bug/fix reference, intended contract, fixed revision or source digest, a minimal fault patch applicable to the current code, relevant tests, expected failure identity and an applicability rationale. Reintroduce only the fault in an isolated temporary checkout; leave today's tests intact. Simply reverting an entire historical commit can remove the regression test, undo unrelated features and invalidate the experiment. Run a clean control, the faulty trial, and preserve both outputs. A second reviewer checks that porting the patch still represents the original defect.

Use current tests on old faulty code to measure **protection today**. To assess whether a change would have caught a bug **before discovery**, use tests that existed before the fix; these are distinct experiments. Retrospective tests written with knowledge of the bug are not evidence of prospective prediction. Publish raw counts and coverage of the corpus before drawing trends from a small sample.

Mutation has independent evidence connecting it to real faults, but not equivalence with them: Just and colleagues' 2014 study found correlation between mutant detection and real-fault detection. Google's 2021 longitudinal study of 15 million mutants also linked live mutants to historical faults and test improvements. Both support mutation as a useful proxy alongside real regressions. [Research paper, 2014](https://homes.cs.washington.edu/~rjust/publ/mutants_real_faults_tr_2014.pdf); [Google/ICSE research, 2021](https://research.google/pubs/long-term-effects-of-mutation-testing/).

### 3.2 A pilot that measures trustworthy signal

1. Freeze one clean source revision, interpreter, dependency lock, pytest configuration and worker allocation. Run the unmodified selected lane successfully. Record installed tools and plugin versions.
2. Choose rollup, outline and migration functions, plus a few essential review/claim rules. Use the same operator families and scope for repeated comparisons. Include comparison boundaries, boolean logic, arithmetic/collection changes and omitted state updates where the tool supports them.
3. Start with about 100–300 candidates across those areas. Keep uncovered areas in the structural backlog. Hand-seed one realistic omitted behavior if ordinary operators cannot express it; report this separately.
4. Verify that the executed tests import the mutated copy, not an installed clean package. A killed control must fail at its intended assertion; a deliberately weakly checked change should survive. Run through pytest's real collection and fixtures.
5. Use outer mutation parallelism with a bounded worker count and in-worker serial pytest first. Benchmark nested xdist only if needed. Multiplying outer workers by inner `-n auto` oversubscribes CPUs, changes timeouts and can manufacture apparent kills.
6. Recheck survivors with the wider relevant suite before declaring a missing assertion. Recheck timeout/error cases at lower concurrency. Record analyzer/selection failures separately; do not add tests to fix a tool's missed attribution.
7. Review survivors in small batches. For each, identify a contract, a distinguishing input and a visible wrong outcome. Strengthen or parametrize the existing behavior test when possible. Stop when the declared behavior list is protected, rather than writing one test per operator occurrence.

The initial outcome should be **actionable gaps found and resolved**, cost per analyzed mutant, reviewer minutes per actionable finding, timeout/error proportion and result stability. A high raw score with mostly logging/string mutants is less useful than finding a missed rollup condition. Sample composition must be visible; a bounded incomplete run must not become a whole-package badge.

### 3.3 Cost model, thresholds and scale evidence

For a declared set of `M` mutants, approximate wall time as baseline/collection cost plus `sum(selected-test duration + per-mutant overhead) / effective parallelism`, with additional timeout and coordination costs. Illustratively, 10,000 mutants each using a full 72-second suite would consume 200 hours of suite wall time if run sequentially. That 72 seconds already uses 32 CPUs; it is not a per-mutant single-core cost that can safely be divided by 32 again. Selection and import reuse can change the result dramatically, which is why a measured scoped pilot is necessary.

Do not prescribe a universal 80%, 90% or 100% Python mutation threshold. This research found no strong multi-team Python evidence establishing one. A tool's `fail_under` flag or tutorial example is not evidence that its number predicts regression risk. Start report-only, then freeze a relevant population and require no loss of protection for essential validated cases. A provisional **70% sensitivity goal** could organize cleanup after triage, but should remain a local planning choice, not an industry standard or first merge gate.

Google's practice favors selective review findings over exhaustive adequacy. Its 2021 scale paper describes changed-code mutation, filtering irrelevant code, limiting mutants and selecting operators using historical feedback, evaluated across over 24,000 developers and 1,000 projects. This is strong industrial evidence for the process, not evidence that Python tooling will reproduce Google's throughput. [Google/TSE paper, 2021](https://research.google/pubs/practical-mutation-testing-at-scale-a-view-from-google/).

The companion ICSE paper describes at most one mutant per covered line and no more than seven reported mutants per file, using developer feedback to reduce unproductive findings. Copy the principle of bounded, actionable feedback; do not treat those exact limits as a validated optimum for specy-road. [Long-term study, 2021, implementation discussion](https://homes.cs.washington.edu/~rjust/publ/mutation_testing_practices_icse_2021.pdf).

Earlier Google industrial work found pursuing full mutation adequacy impractical and undesirable. Mutant redundancy can also skew scores: Just and Schweiggert's study found removal of redundant operators improved both runtime and score interpretation. This is speed work that improves the measurement itself. [Industrial mutation study, 2018](https://research.google/pubs/an-industrial-application-of-mutation-testing-lessons-challenges-and-research-directions/); [non-redundant operators study, 2014](https://homes.cs.washington.edu/~rjust/publ/non_redundant_mutants_jstvr_2014.pdf).

### 3.4 Equivalence, suppressions and reproducible gates

A surviving mutant can mean a missing assertion, missing execution, equivalent behavior under the supported domain, a behavior outside the contract, a test-selection problem or a tool failure. Equivalence is domain-dependent: a case change may be equivalent for a case-insensitive parser, but not for public output. Automatic filters reduce work; they do not solve the general equivalence problem.

Keep a reviewed suppression record keyed to source content/location, operator, reason and scope. Expose suppression counts and changes. “Hard to test,” “the score was too low” and an LLM equivalence judgment are insufficient. Logging mutations may be excluded only where the message is not a contract; never exclude all exception paths or CLI diagnostics indiscriminately. Exemptions should expire on relevant code changes.

A stable mutation gate needs a complete fixed population or a fixed essential-mutant set, clean baseline, reproducible selection, deterministic test profile and clear treatment of incomplete analysis. Missing data is an analysis failure or “not evaluated,” never green. New random samples and time-budget-limited whole-package runs remain reports. Mutmut's documented dependency invalidation can merely warn and retain results by default; force appropriate invalidation for changed tests, dependencies and repository documents/templates on which consistency tests depend. Validate options against the pinned release before adopting them.

## 4. What the evidence says about agent-written tests

### 4.1 Findings, disagreements and confidence

| Evidence | Finding relevant here | Strength and limit |
| --- | --- | --- |
| **TestGen-LLM, Meta, FSE 2024** | Generation was filtered for building, reliable passing and incremental coverage before recommendation to engineers. The published abstract reports 73% acceptance of recommendations. | Peer-reviewed industrial report by the deploying company; useful evidence for an acceptance funnel. Acceptance and added coverage do not establish a particular real-bug detection rate. The work improves existing human-written tests, unlike fully agent-authored code and tests. [Paper, submitted 2024-02-14](https://arxiv.org/abs/2402.09171). |
| **MUTGEN, 2025** | Mutation feedback in generation prompts improved mutation scores over baseline strategies on 204 benchmark subjects; some high-coverage suites had very low mutation scores. | Research evidence for targeted feedback, not proof of spec correctness or effectiveness on a repository of this size. Evaluation against mutants can reward overfitting to the operators. [Paper, 2025-06-03](https://arxiv.org/abs/2506.02954). |
| **ACH, Meta, 2025** | Concern-specific faults and tests were generated together, with tests checked against original and faulty code. Meta reports 73% acceptance and 36% privacy relevance in its deployment trial. | First-party industrial evidence; vendor claims are not independent replication. Killing a constructed fault establishes sensitivity to it, not a guarantee of preventing every bug in the concern class. [Deployment account, 2025-09-30](https://engineering.fb.com/2025/09/30/security/llms-are-the-key-to-mutation-testing-and-better-compliance/). |
| **Software-evolution study, 2026** | Across eight models and 22,374 variants, generated suites became less reliable under both semantic and semantics-preserving edits. | Recent preprint. It examines regeneration under changed programs; do not misreport all results as existing fixed tests failing after refactoring. It suggests sensitivity to source form and the need to preserve explicit behavioral obligations. [Paper, 2026-03-24](https://arxiv.org/abs/2603.23443). |
| **Joint code/test adequacy study, 2026** | On over 6,000 faulty generated programs, oracle weaknesses left triggered faults undetected; mutation only marginally improved over coverage criteria in this setting. | Recent preprint directly relevant to jointly generated code and tests. Benchmark findings challenge universal claims that mutation automatically solves agent-test quality. [Paper, 2026-09-08](https://arxiv.org/abs/2609.09315). |
| **Elixir same-model/different-model study, ESEM 2026** | Five models produced implementations and tests. The authors found no advantage from generating tests with a different model; 99 of 247 implementations flagged as faulty were flagged only by manual tests. | Peer-reviewed, but one language and particular tasks/models. This tests generation, not specy-road's full two-reviewer process. Distinct model families are not demonstrated statistical independence. [Paper, 2026-10-05](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.11). |
| **Python historical-bug comparison, 2026** | A retrieval-assisted generator detected 69% of sampled bugs versus 17.2% for general-purpose human tests in a 29-bug historical benchmark. | Recent preprint with a small sample and unequal task context: bug-targeted generation versus general-purpose existing tests. Supports giving agents concrete bug/spec context, not a universal superiority claim. [Paper, 2026-06-07](https://arxiv.org/abs/2606.08588). |
| **Python corpus non-inferiority study, 2026** | Recent Claude-authored tests were reported non-inferior to Django/Pandas human-test samples across several fault-injection protocols and a design rubric. | Recent single-author preprint, observational corpora and limited model/language scope. Useful counterevidence to “agent-written always means weak”; not a causal estimate of authorship or a finding about this suite. [Paper, 2026-08-15](https://arxiv.org/abs/2608.15188). |
| **VibeCheck, 2026** | A study of 15 student repositories found runnable agent-generated tests often had weak assertions or missing edges. | Recent preprint; rubric and peer-agent evaluation introduce judgment uncertainty. One underlying model across IDE agents is not evidence for diversity across model families. [Paper, 2026-09-05](https://arxiv.org/abs/2609.05978). |
| **Obligation-based analysis, 2026** | A Java benchmark study found concentrated gaps in boundary inputs, catch/default paths and some object/exception oracles despite aggregate measures. | Very recent preprint; useful hypotheses for a checklist, not validated Python thresholds. [Paper, 2026-10-23](https://arxiv.org/abs/2610.32548). |

These findings are compatible with several causes: benchmark familiarity, context quality, model generation, human review, target domain and metric choice. They do **not** establish a universal gap between human and agent tests. The actionable commonality is that runnability, coverage, assertion sensitivity and correct intended behavior must be checked separately.

The near-duplicate-per-fix mechanism in this repository is credible from the supplied local analysis, but this research found no strong causal estimate showing how much two-model review or agent authorship increases duplication. Label that mechanism a **local organizational hypothesis**, not a published universal property of LLM tests. The supplied hand-read categories remain better evidence for this suite than a vendor benchmark.

### 4.2 Prompt-side rules that address those mechanisms

Use a short, mandatory test-design block in the executor prompt:

> Start from the accepted behavior and public contract. List the changed obligations, their allowed input partitions, failure/rollback outcomes, and the smallest public interface that exposes them. Cite the contract or issue for each expected result. Search existing tests and tables before creating a test. For each obligation, name the existing test to extend or explain the new observable regression. Do not calculate an expected result using the production function being tested. Do not change assertions merely because the current implementation disagrees. Use one cohesive behavior per test or parameter table; retain distinct boundary rows and scenario IDs. Exercise production behavior through public names, and assert outputs, errors or state effects. Report the pre-fix failure and post-fix success for applicable regressions. If no additional test is needed, cite the existing test and demonstrate its protection.

Before implementation is available, a spec-derived test list can reduce anchoring on code. Once the list exists, give the agent implementation context needed to construct valid inputs and use existing seams. Absolute “spec-only, never inspect code” rules can produce unrunnable tests and miss operational constraints; that stronger rule is unsupported. Protect a few human-checked acceptance examples and invariants as stable reference points.

For a surviving mutant, supply the **original contract, mutant diff, selected test IDs and actual outcomes**. Ask the user's agent to decide whether it represents a supported behavioral change and propose the smallest distinguishing case. Require the generated assertion to fail against the mutant and pass against clean code. Independently review the expected result. Multiple mutants can be killed by one boundary table or invariant; do not instruct “one new test per mutant.”

The toolkit should generate these prompts and consume local execution records. **INCOMPATIBLE:** embedding model calls in specy-road, even if the provider is local or the feature is opt-in, under the task's fixed constraint 5. An optional hosted agent selected by the user remains outside the toolkit's deterministic measurement path.

### 4.3 Process-side controls

Keep the existing distinct-family reviewers, but assign evidence-bearing questions. One reviewer can examine obligation/oracle alignment and missing partitions; the other can inspect public seams, reproducibility and red/green or mutation evidence. Both still assess the change as required by project policy. This changes review focus, not the number of required reviewers, and does not establish independence merely by using different models.

Require a test rationale in the change description with four fields: **obligation; existing test/table or new node ID; distinguishing faulty behavior; validation evidence**. Add a lane choice only when it is not obvious. Avoid a second permanent registry of every test: file-local IDs/comments and PR evidence are enough unless the project demonstrates a need for more.

Do not allow agents to silently repair failing tests by rewriting their oracles, broadening accepted exceptions, deleting a boundary row, adding skips or suppressing coverage/mutation. A legitimate contract change needs explicit rationale in the diff; existing failing behavioral tests remain protected. Review findings can be resolved by an existing test, a stronger assertion or a table row. “A reviewer requested a fix” is not itself a new behavior.

Use uncertainty as a stop for **specification invention**: if contracts disagree about a result, report the disagreement and continue independent work. Do not turn an implementation's current output into an authoritative golden file. Golden files are appropriate for intentional public artifacts when their content is reviewed and the comparison detects the relevant behavior.

## 5. A short reviewer checklist and scriptable checks

The checklist is an adoptable local policy derived from the evidence above and the repository's constraints. Rules about file organization and table shape are maintainability judgments, not experimentally proven numerical predictors of bugs.

| Reviewer question | Required evidence / disposition | What a script can check | Basis |
| --- | --- | --- | --- |
| **1. What public obligation does this check?** | Cite acceptance text, issue or contract and identify the visible wrong result. Reject an expected value copied uncritically from current code. | Require a rationale field; detect trivial self-comparisons and some production-derived expectations. Cannot prove oracle correctness. | Oracle failures in the joint-generation and obligation studies, section 4. |
| **2. Does it add a distinct check?** | Search and name the existing behavior test/table. Extend it if the setup, action and oracle are the same; preserve distinct scenarios and boundary rows. | Find exact/near AST matches, cross-test imports and similar arc sets. Flag, do not auto-delete. | Local hand-read analysis; coverage limits, section 2. |
| **3. Does the assertion discriminate?** | Show the named failure on faulty code and success on clean code, or identify an existing regression test that does. A new feature may use a reviewed fault variant if the old API is absent. | Execute clean/fault trials, retain node IDs and failure details, flag missing collection. A reviewer confirms causal relevance. | Historical-fault and mutation research, sections 2–3. |
| **4. Is it at the cheapest level that exposes the failure?** | Public in-process function/command for ordinary logic; real git/process where those semantics are the obligation. | Inventory subprocess calls and test markers; detect unmarked process tests. Cannot decide realism. | Measurement visibility and isolation; section 6. |
| **5. Does it avoid private implementation coupling?** | No importing or patching production `_` names. Assert returned values, error categories, files or externally visible state; no mock call-count/order oracle. | AST-resolve explicit imports, attribute accesses and literal patch targets; flag `assert_called*`, `call_count` and source-inspection patterns. Dynamic targets remain manual. | Repository rule; execution-fidelity defects and evolution evidence. |
| **6. Are important boundaries and side effects checked?** | Review empty/minimal/maximum supported cases, invalid input, state before/after failure and preservation of unrelated data as relevant. One coherent behavior may need several assertions. | Compare declared scenario IDs and parameter rows; detect broad `raises(Exception)` and assertion-free bodies as leads. Cannot infer all missing partitions. | Obligation study; property-testing design, section 7. |
| **7. Can it run alone and under the normal worker configuration?** | Fresh temporary state, restored env/cwd, joined workers, no dependency on test order or ambient git identity. Synchronization is explicit. | Flag sleeps, uncontrolled randomness, fixed paths/ports and global mutable fixtures; run isolation/order diagnostics. | [pytest flaky-test guidance, accessed 2026-11-06](https://docs.pytest.org/en/stable/explanation/flaky.html). |
| **8. Is text or fixture abstraction hiding the contract?** | Match structured values when available. Exact prose is justified for a public diagnostic/help/output contract. Shared helpers construct setup, not expected answers or hidden workflows. | Flag long string/regex assertions, imports from test modules, new autouse fixtures and new broad fixture options. Review exceptions by purpose. | Local analysis; official fixture semantics; section 6. |

Apply static gates only to clearly defined new violations: private production imports/patches, cross-test-module imports and unapproved source suppression changes are good candidates. Treat private fixture helpers, stdlib dunder protocol names, test-only `_` variables and production private imports inside the package differently from tests depending on private production API. Resolve aliases where straightforward; describe the scanner as partial rather than pretending it proves no coupling.

Long strings, assertion count, fixture count, test length and percentage overlap are **flags**, not automatic failures. A CLI toolkit legitimately tests diagnostics and generated files. A single assertion can be weak; several assertions can describe one atomic observable state transition. Exception tests should assert the specific error category and relevant state preservation, not demand a new structured error type solely to avoid every message check.

## 6. Suite structure and choosing a lane

There is no evidence-based universal unit/integration/smoke ratio for this toolkit. Allocate tests by the behavior they must expose, and report counts by lane for visibility. Retain the full ordinary suite as a PR gate while its cost is acceptable; the supplied runtime does not justify weakening it.

| Lane | Entry point and real dependencies | What belongs here | Proposed policy |
| --- | --- | --- | --- |
| Unit / small component | Public Python callable or in-process command dispatcher; real small values/files when useful; boundary fakes only where needed. | Rollup decisions, parsing partitions, graph transformations, migration mappings, review-policy decisions and most CLI argument combinations. | Default for new logic. One cohesive behavior/table; properties concentrate here. Full PR execution. |
| Integration / git-backed | Public operation with real temporary repositories, files, locks or coordinated workers. Invocation may still be in-process. | Worktree/branch/index semantics, git config interactions, concurrent claims, atomicity, interruption and rollback. | Retain real git where it creates the failure. Gate deterministic scenarios on PRs; extended schedule exploration can be periodic. |
| CLI smoke / installed artifact | Actual console entry point or `python -m` in a fresh process, preferably exercising an installed wheel. | Entrypoint packaging/imports, representative argument routing, exit status, stdout/stderr separation, cwd/env propagation and required process/signal semantics. | The planned <=50-item lane is a useful provisional budget, not a coverage theorem. Every process-only obligation must have a home; inspect any case displaced by the cap. |
| Repository consistency | Read tracked docs, schemas, templates and generated artifacts; use their documented validators/public contracts. | Scaffold compatibility, schema/document agreement, generated-file drift and dependency-policy recipes. | Separate from production-logic effectiveness totals; run relevant checks on PRs and the complete deterministic lane before release. |

Decision order: identify the observable failure; choose the narrowest public entry point that retains the real cause; then choose isolation and lane. “Calls git” does not mean “must spawn the whole CLI,” and “in-process” does not mean “unit.” Testing a worktree flow with real git through a public callable is integration testing with good coverage visibility.

Keep most test setup close to its owning subsystem. Use local `conftest.py` for fixtures visible to a directory and a small explicitly named test-support module for shared builders. Do not import fixtures or helpers from another `test_*.py` file. Prefer fresh objects and minimal valid repositories. Shared setup may initialize a temporary repo or build a graph; it should not implement another rollup algorithm, decide expected policy results or silently perform the action being tested.

Reuse first, then generalize only when multiple tests have the same concrete need. Avoid a universal fixture with flags for every workflow, session-scoped mutable repositories and autouse fixtures that obscure prerequisite state. A shared helper change has broad impact and should trigger its dependents or a full lane. Pytest's fixture documentation explains per-test freshness, cached fixture execution and scope; it does not guarantee that a complex fixture hierarchy is readable or isolated. [Official fixture guide, accessed 2026-11-06](https://docs.pytest.org/en/stable/how-to/fixtures.html).

Use a few contract tests to validate any reusable fake against the real boundary's public outputs/state. A recording fake may expose structured requests for inspection, but do not make internal call counts or call order the test oracle. Keep real process/git sentinels so changing an adapter cannot make all unit tests green while breaking actual invocation.

## 7. Property-based testing: where Hypothesis earns its place

Hypothesis is already approved as a pinned test-only dependency. Its license is **MPL-2.0**, not permissive; the explicit approval is a scoped exception, not precedent for bundling other copyleft tools. Keep it out of package runtime requirements and consumer default installations. [Official distribution metadata, accessed 2026-11-06](https://pypi.org/project/hypothesis/).

### 7.1 Five high-value property families

These are concrete proposals to refine the five properties already planned, not five additional mandatory tests. Assert only invariants supported by accepted contracts.

| Area | Useful generator | Property / independent oracle | Avoid |
| --- | --- | --- | --- |
| Graph and outline edits | Small valid DAG/tree structures built constructively; stable node keys; distinct external references; separately generated invalid edits. | Moving/renumbering preserves stable identities and references, preserves unrelated nodes, and leaves required graph invariants valid. Inverse edits restore equivalent structure where the contract allows an inverse. | Using the production validator as the only oracle; comparing serialized bytes when presentation order is allowed to change. |
| Milestone rollup | Small nested trees with varied terminal, active and blocked leaf states, especially empty and mixed cases. | Compare public rollup results with a tiny spec-derived truth table over leaves; test invariance under irrelevant ordering only where order is semantically irrelevant. | Copying production traversal code into the expected-value helper; assuming every status is monotone. |
| Parsers / serialization | Valid domain objects plus malformed/ambiguous boundary strings; Unicode and delimiter cases supported by the format. | Parse/serialize preserves semantic values; canonicalization is idempotent; invalid inputs are rejected without partial effects. Add hand-checked expected examples. | A round-trip alone: encoder and decoder can share an error; “does not crash on anything” where invalid input is supposed to raise. |
| Configuration migration | Old-version records with missing optional fields, unknown fields, already migrated values and stable identifiers. | Migration preserves contractual information, generates consistent identifiers, and is idempotent if promised. Test direct-vs-sequential migration equivalence only if both paths are supported. | Assuming arbitrary unknown fields must survive without a contract; recreating production defaults as the oracle. |
| Stateful claims/reviews/workflows | Sequences of claim, release, record review, change head and finish actions, with valid and invalid transitions. | A small abstract model predicts owner/eligibility/status; stale review records never authorize a changed head; failed operations preserve state. Check invariants after each action. | Modeling every implementation field, probabilistic wall-clock expiry and trying to infer real interleavings from a sequential state machine. |

Hypothesis stateful testing generates action sequences and shrinks failures. Start with a list of actions when that suffices; use `RuleBasedStateMachine`, rules, preconditions and bundles only when they improve clarity. The model should be much simpler than the production orchestration system. [Official stateful testing guide, accessed 2026-11-06](https://hypothesis.readthedocs.io/en/latest/stateful.html).

### 7.2 Reproducible PR testing and broader discovery

Use explicit profiles in the pinned test environment rather than relying on evolving library defaults. A reasonable **starting proposal**, to benchmark on these properties, is:

```python
from hypothesis import settings

settings.register_profile(
    "specy_ci",
    max_examples=100,
    stateful_step_count=25,
    derandomize=True,
    database=None,
    deadline=None,
    suppress_health_check=(),
)
settings.register_profile(
    "specy_explore",
    max_examples=1000,
    stateful_step_count=50,
    derandomize=False,
    deadline=None,
    suppress_health_check=(),
)
```

Explicitly load the selected profile in test setup. Bound graph size and sequence length by meaningful domain partitions. Derandomization repeats inputs only for the same relevant code and pinned environment; Python, Hypothesis or test changes may change the examples. It does not make production nondeterminism, thread scheduling or external git state deterministic. Disabling the per-example deadline removes machine-speed-sensitive assertions; bound work structurally and use a generous job timeout as a hang safeguard. [Hypothesis settings reference, accessed 2026-11-06](https://hypothesis.readthedocs.io/en/latest/reference/api.html); [settings tutorial, accessed 2026-11-06](https://hypothesis.readthedocs.io/en/latest/tutorial/settings.html).

Keep generation constructive: generate a DAG by ordering nodes and choosing forward edges, rather than filtering arbitrary graphs until one is acyclic. Treat health-check failures as feedback on strategy quality; do not suppress all checks to force a green run. The current built-in CI profile suppresses the slow-generation check, so an explicit empty suppression list makes this proposed policy deliberate. If that check itself is unstable on constrained machines, fix the strategy or move expensive discovery to the advisory lane and document the specific decision.

Reset mutable state **for each generated example**. A pytest function-scoped fixture is not automatically recreated for each Hypothesis example. For filesystem/stateful tests, create an example-local temporary directory using stdlib facilities or an explicit reset lifecycle; a function-scoped `tmp_path` reused across examples can contaminate results. Bound real git operations or keep them in separate integration properties rather than multiplying every generated action into a new CLI process.

Preserve a discovered regression as a readable `@example(...)`, a parameter row or a separate scenario when it represents a distinct behavior. Failure blobs and cached databases are useful reproduction aids, not permanent portable contracts. Record the seed, versions and shrunk input; the durable case is the input and expected behavior. Keep a reusable database for local/exploratory runs if useful, but make PR acceptance independent of whether a cache was restored. [Official replay guide, accessed 2026-11-06](https://hypothesis.readthedocs.io/en/latest/tutorial/replaying-failures.html).

Run the deterministic profile on PRs and under mutation analysis. Run larger seeded or unseeded discovery periodically, retain evidence, and turn findings into reproducible tests before making them gates. A real newly discovered bug is not “just a flaky test”; the advisory lane is for discovery variability, not permission to ignore defects. Measure whether the five properties catch seeded or historical faults, not just how many examples they generate.

## 8. Weighted buy-versus-build assessment

### 8.1 Scoring method

Scores are **0–3**, higher is better: 0 = unacceptable/absent evidence for the intended use; 1 = substantial limitations; 2 = adequate with controls; 3 = strong fit. They are transparent engineering judgments, not measured probabilities. Scores apply to the use described in the verdict, with incompatibilities called out separately. A high sum cannot override a hard constraint.

`weighted total = 3F + 3G + 2S + 2L + 2C + M + I`, maximum **42**.

| Code | Criterion | Weight |
| --- | --- | --- |
| F | Fit with all six fixed constraints | 3 |
| G | Added signal for regression catching | 3 |
| S | Supply-chain risk: higher means fewer risks/better provenance evidence | 2 |
| L | License fit: permissive 3; explicit limited exception 1; copyleft/unverified bundling permission 0 | 2 |
| C | Run cost and flakiness: higher means more predictable/cheaper | 2 |
| M | Maturity, maintenance and adoption evidence | 1 |
| I | Integration effort with pytest, xdist and coverage.py: higher means easier | 1 |

Do not confuse signing with code safety. PyPI attestations identify the publishing workflow/artifact; they are useful provenance, not an audit. This report did not perform a comprehensive vulnerability or compromise investigation. No candidate receives a “no incidents ever” assurance. Release activity and visible issue handling inform maturity, but no systematic maintainer response-time study was performed. Small-maintainer projects retain concentration risk even with attestations.

### 8.3 Tool-specific buying rationale and supply-chain evidence

**Coverage contexts and pytest-cov:** coverage.py is Apache-2.0, mature and already required; current release metadata shows publishing provenance. Context storage adds no runtime dependency. Pytest-cov is MIT and provides tested pytest/xdist/context integration; its 7.1.0 release is dated 2026-03-21 and the distribution listing shows no provenance. Prefer it to owning distributed coverage glue, but retain a working existing harness if it already solves the problem. [coverage.py metadata, release 2026-11-04](https://pypi.org/project/coverage/); [pytest-cov metadata, 2026-03-21](https://pypi.org/project/pytest-cov/).

**Hypothesis:** frequent maintenance and multiple maintainers justify retaining the approved dependency. Artifact provenance varies across the current distribution files; do not generalize one wheel's status to every platform. The license score stays low because MPL-2.0 remains copyleft despite approval. The buying case is mature generation, shrinking and state machines; building a competing generator/shrinker is unjustified. The highest value is independently reviewed invariants, not replacing every small example with randomized inputs.

**mutmut and Cosmic Ray:** both are permissively licensed and actively released. Mutmut's current PyPI listing has one maintainer and no provenance for the observed release; Cosmic Ray's observed release has two maintainers and provenance. These are risk signals, not evidence of maliciousness. Lock their full dependency closures in isolated development environments. Existing mutation workflow tools installed after the repository audit are specifically described in the repository's supply-chain documentation as outside the frozen lock: close that gap before treating the lane as policy-compliant. This report changes no dependencies or workflows. [Mutmut release metadata](https://pypi.org/project/mutmut/3.8.1/); [Cosmic Ray release metadata](https://pypi.org/project/cosmic-ray/), dates in section 3.

**mutatest and MutPy:** permissive licenses are not enough. The old release/support evidence makes modern interpreter and pytest ownership costly, and bytecode/AST internals evolve. Their low maturity scores mean present maintenance fitness, not that the tools never made useful contributions. Buying neither is cheaper than building compatibility patches or a replacement engine. They add no demonstrated unique signal over a supported candidate.

**Poodle and pytest-gremlins:** PyPI shows provenance on the observed 2026 releases and a single maintainer for each. Poodle offers an alternative runner/reporting model, but selection compatibility is not established here. Gremlins is especially relevant to 2026 agent workflows through its agent guidelines and machine-readable diagnostics, yet its recent fidelity report outweighs headline speed claims. Evaluate in an isolated experiment with known outcomes; do not package an extra backend before a concrete win is established. [Poodle release metadata](https://pypi.org/project/poodle/); [gremlins release metadata](https://pypi.org/project/pytest-gremlins/), dates in section 3.

**pytest-testmon:** MIT, active 2.3.0 release on 2026-11-02, one maintainer and no provenance in the observed files. Its coverage-derived dependency database and xdist support are useful for repeated local feedback; implementing that tracker would be substantial work. But it does not track changes to static files or external services, and tracing can conflict with separate coverage collection. It adds little direct effectiveness signal while the full suite is already short. Keep local selection optional, disable selection for authoritative full-suite coverage, and invalidate for templates/schema/config/helper changes. The optional cloud storage mode is unnecessary. [Release metadata, 2026-11-02](https://pypi.org/project/pytest-testmon/); [official behavior and limitations, accessed 2026-11-06](https://www.testmon.org/).

**pytest-randomly:** MIT, release 5.0.0 on 2026-09-01 with Trusted Publishing, established pytest-dev project and one listed PyPI maintainer. It handles ordering and reproducible random-state reset better than an ad hoc shuffle hook. It supports xdist, but a seed alone cannot replay nondeterministic worker scheduling. Record worker count, distribution and versions; reproduce order pollution serially where appropriate. Installation autoloads the plugin, so explicitly disable it in ordinary deterministic lanes rather than accidentally randomizing every merge gate. [Release metadata, 2026-09-01](https://pypi.org/project/pytest-randomly/); [official plugin documentation, accessed 2026-11-06](https://github.com/pytest-dev/pytest-randomly).

**pytest-rerunfailures:** maintained, supports ordinary xdist use, and can preserve retry details, but retries are a diagnostic convenience rather than proof of reliability. The observed 16.7 release on 2026-09-17 has MPL-2.0 licensing, multiple listed maintainers and no provenance. Under this task's policy, do not bundle it or silently add it under Hypothesis's exception. An independently installed user diagnostic may run failure retries, but the authoritative result must preserve initial failures and traces. Fresh-process repetition with existing pytest is enough for the proposed small flake report. [Release metadata and changelog, 2026-09-17](https://pypi.org/project/pytest-rerunfailures/); [official usage/compatibility, accessed 2026-11-06](https://github.com/pytest-dev/pytest-rerunfailures).

**diff-cover:** Apache-2.0, multiple maintainers, maintained release 11.0.1 dated 2026-11-04. It buys mature diff parsing and reporting, not stronger assertions. Its changed-line percentage should not be called changed-branch adequacy. Integrate optionally with a pinned package or keep a very small report that joins known changed lines to coverage JSON. ## 9. Speed and cost only where they improve effectiveness

**Useful investments:** in-process public entry points make assertions and per-test attribution easier to inspect; minimal fixtures make edge partitions easier to generate; replacing sleeps with explicit events or injected clocks makes concurrency failures repeatable; grouping equivalent inputs in a readable table exposes omissions; bounded mutation selection makes assertion feedback reviewable. Each improves measurement or fault detection as well as speed.

**Selection is an optimization with a validity condition.** Historic coverage can miss newly introduced dependencies, newly reachable code, import/config effects and non-Python assets. Use affected-test selection for the agent's inner loop and for candidate mutation trials; validate against the full ordinary suite before merging. Treat modifications to shared helpers, conftest files, package initialization, dependency locks, templates and schemas as reasons to widen selection. Never update an authoritative coverage floor using only selected tests and stale old coverage.

**Sharding should retain the entire declared population.** Prefer stable ownership or duration-balanced full-suite shards, isolate git directories and resource names, and combine coverage from the same source revision/configuration. Report missing shard data as incomplete. Keep platform/interpreter totals distinguishable rather than hiding an untested platform path behind coverage from another environment. Running fewer tests is different from executing all tests in more shards.

**Subprocess visibility requires an explicit check.** Coverage of the parent pytest process does not automatically cover a Python child. Pytest-cov 7 removed its own older subprocess mechanism; current guidance uses coverage.py's `patch = subprocess` support with separate data files and combination. Existing working `sitecustomize` capture need not be rewritten merely because a newer documented mechanism exists. More importantly, collecting child coverage does not automatically attach the correct parent test context or guarantee that a mutation reaches the child. Preserve and validate that attribution path before reducing process tests. [Pytest-cov subprocess migration, updated 2026-10-18](https://pytest-cov.readthedocs.io/en/latest/subprocess-support.html); [coverage.py process guidance, accessed 2026-11-06](https://coverage.readthedocs.io/en/latest/subprocess.html).

Crash/kill tests may legitimately prevent coverage flush. Record that measurement limitation and validate the behavior through process/file state; do not remove the crash case to improve a percentage. For ordinary child processes, a small known executed branch should verify capture and test attribution. For mutation, a known child-visible fault must actually fail the smoke/integration assertion.

**Changes that weaken evidence:** making retries silently green, counting timeouts as assertion kills, deleting same-arc tests automatically, dropping real git/process scenarios solely to meet a cap, excluding whole modules to raise a score, or using a fixed seed as the only long-term discovery strategy. These are not justified speed improvements. A hosted selection service required by default is **INCOMPATIBLE**; offline local selection can remain optional.

Reports should explain provenance and limits plainly: “these tests executed this branch,” “this mutant survived these selected tests,” or “this historical fault was detected by this assertion.” Avoid a composite “test quality score” that hides those distinctions.

## 11. Where this changes or qualifies the existing plan

1. **The parity harness is necessary but insufficient.** It can preserve an existing bug and old implementation-specific output. Anchor it in accepted contract examples, historical faults and reviewed state invariants; permit intentional contract changes with explicit evidence.
2. **Dedupe worklists should optimize understanding and retain detection.** The supplied arc similarities locate candidates. They do not justify a 69% deletion target, and parameterization can reduce function count without reducing collected items or actual work. Preserve behavior rows, process differences, concurrency cases and existing regression kills.
3. **Public seams are the right direction, but need real-boundary sentinels.** A sea of public fakes can still test a fictional system. Retain real git, installed entry-point and process-lifecycle cases; no private-name patching is required to do that.
4. **Five properties is a starting scope, not an effectiveness measure.** Favor graph identity/reference preservation, rollup rules, parser semantics, migration preservation and state-transition invariants. Demonstrate faults they catch. Round trips and shared validators alone are weak oracles.
5. **The <=50 CLI smoke target is provisional.** Most argument/output combinations can move in-process, but signal handling, packaging, inherited environment and actual child mutation propagation require real processes. The evidence supplies no universal correct subprocess count.
6. **The review-finding test rule is sound with a completeness clause.** Record when an existing test already catches the bug, and accept an additional table row instead of demanding a new function. Parent-revision import errors are not red evidence. Fault variants are useful when a new API makes parent execution impossible.
7. **Distinct reviewer families do not prove independent oracles.** Retain the process; improve the material reviewers inspect. The Elixir evidence limits the stronger assumption, without establishing that two-family review has no value.
8. **Mutation is useful but not a sufficient answer to agent-generated oracles.** Recent joint-generation results are less optimistic than older mutation studies. Pair targeted mutation with historical bug detection and specification review; calibrate against this suite's actual defects.
9. **Do not turn a capped weekly mutation run into a precise gate.** The checkout already has a weekly, time-capped mutmut workflow and a possible per-module baseline comparison. A >2-point drop is meaningful only with comparable population, completion, operators and exclusions. Partial campaigns can shift scores because of execution order. Keep incomplete campaigns advisory and move stable gates to complete, declared populations.
10. **Dependency exceptions must stay explicit.** Hypothesis is MPL-2.0 but already approved. That does not approve pytest-rerunfailures, Qodo Cover or copying share-alike agent skills. Existing exact-pinned mutation tools outside the audited lock still need their transitive closure covered before adoption satisfies the stated policy.

## 12. Adoption sequence and completion criteria

**First: make the current signals legible.** Preserve the full suite and existing floor; publish separate line/branch values by core subsystem; attach a concise test rationale to applicable changes; record first-attempt outcomes. Extend existing context analysis for candidate groups without deleting anything automatically.

**Second: run one bounded mutation pilot.** Use the existing mutmut integration where compatible, with isolated, fully reviewed dependencies and fixed scope. Validate actual mutation execution, selected tests, timeout handling and clean controls. Review 100–300 candidates and report distinct actionable gaps plus reviewer effort. Do not add another engine unless this pilot identifies a concrete blocker.

**Third: establish a small real-regression corpus and the five property families.** Stabilize 20–30 representative bug cases; promote only reliable applicable cases to mandatory replay. Preserve shrunk property regressions as readable inputs. Compare fault detection before and after each subsystem consolidation.

**Then choose gates with the maintainer.** Retain existing configured coverage requirements. Consider the proposed changed-line target only after coverage mapping is reliable. Gate a stable essential mutation/regression population, while broader mutation, random-order exploration, duplicate analysis and flake-rate estimates remain reports. Review the value of each report after two to four weeks; remove reporting machinery that produces no actionable finding.

Success means the declared important behaviors are demonstrably checked, known meaningful faults are caught, failures are reproducible, and reviewers can explain why each retained or added test matters. This report adds no helper, guard, mock, test, dependency, workflow, branch or version change; it proposes their evaluation and writes only this research artifact.
