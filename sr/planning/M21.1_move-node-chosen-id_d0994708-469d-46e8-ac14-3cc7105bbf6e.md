## Intent

rc4 roadmap-tooling fix (maintainer 2026-11-05), filed in M16's fix intake. `move-node` cannot take a chosen id: the moved node always gets one past the highest sibling (`next_free_child_id` in roadmap_outline_renumber.py), so a regroup cannot place nodes at planned ids. And the PM GUI never got M16.67's change: `move_node_outline` (roadmap_outline_ops.py) calls `move_node` with its default `renumber_outline=True`, so the GUI's drag (`/outline/move`), indent and outdent still renumber the whole outline, and `reorder_siblings` (`/outline/reorder`) renumbers every id and persists before it validates.

Evidence: regrouping M16 into sub-milestones using only specy-road commands (scratch run, 2026-11-05) took about 85 commands, a temporary holder node and about 100 s, and left about 950 stale id mentions in prose. Earlier related fix: M16.67 (move-node renumbers only the moved subtree; whole-outline renumber became explicit).

## Approach

- `move_node` gains `new_id` and `fill_gaps`: a chosen id must be a well-formed direct child id of the new parent and free; `fill_gaps` takes the lowest free number. Both renumber only the moved subtree. Combining either with `--renumber-outline` is refused.
- One implementation for CLI and GUI: `move_node_outline`, `apply_indent`, `apply_outdent` default to subtree-only; `reorder_siblings` changes `sibling_order` only (order is `sibling_order`-driven, see `sibling_sort_key`) and stages through `AtomicWritePlan`. Whole-outline renumber only when the request passes the new optional `renumber_outline: true`.
- GUI API additions are optional fields only (`new_id`, `fill_gaps`, `renumber_outline` on `MoveOutlineBody`; `renumber_outline` on reorder/indent/outdent); response shapes unchanged.
- gui/pm-gantt is not edited: `contiguousSubtreeIds` slices visible rows by depth, not by id (plan review).
