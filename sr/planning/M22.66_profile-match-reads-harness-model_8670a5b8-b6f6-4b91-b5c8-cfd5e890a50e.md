## Intent

A roster entry whose `harness_model` is a profile's exact `api_id` (or one of its `aliases`) still matches no profile when its `id` differs, and `validate` warns that the entry's model notes never reach its prompts. Found in field use of 0.3.1rc4, for both a Claude Code and a Cursor entry. The warning is true: without a match, the profile's prompting rules, failure-mode guards and launch facts are not applied to that entry.

## Approach

Matching without a `profile:` path is by the entry's `id` only, in both places it happens:

- the working tree: `profile_for_entry`, `specy_road/model_profiles.py:314`;
- the integration branch: `_integration_profile_for_entry`, `specy_road/orchestration_pinned.py:274-276`, through `_pinned_for_id`.

Both move to one lookup order, in **two passes**, each through the existing `Profile.for_id` (api_id, file name or alias; `model_profiles.py:65`):

1. over all profiles, the first that matches the entry's `id`;
2. only when none does, over all profiles, the first that matches its `harness_model`.

This is not one pass of `for_id(id) or for_id(harness_model)` per profile: that would let a profile earlier in `list_profiles` that matches `harness_model` beat a later profile that matches `id`. An id match always wins, whatever the profile order, so an entry that matches by `id` today keeps its profile. An absent or blank `harness_model` is no key: pass 2 is skipped. `roster_profile_gaps` (`:391`) uses `profile_for_entry`, so the warning follows the match without its own change, and its text says "by api_id, file name or alias of its id or harness_model". An explicit `profile:` path is unchanged.

On the integration branch, pass 2 goes through `_pinned_for_id` like pass 1, so a profile matched by `harness_model` whose working-tree copy differs from the committed one is refused with the existing integration-drift reason, as an id match is today. The committed text decides the match; the refusal is what is returned, so dispatch stops.

A newly matched profile reaches the entry everywhere a profile does: its prompting rules and guards in prompts, `launch_mode` for Claude Code, `effort_by_role`, and the guidance-bypass findings `review delegate` checks (`_guidance_check`). That is the intended effect, and it is why the tier is trust boundary.

Temporary repos with committed profiles, as `tests/test_model_profile_aliases.py` builds them. Assertions go through `validate` output, `prompt` text and the public `pinned_profile_for_entry`. No network, no private patch.

| Row | Setup | Expect |

| alias | Cursor entry whose `harness_model` is one of a profile's `aliases` | Matches that profile; no warning |

## Tier

trust boundary: a newly matched profile changes a worker's launch (`launch_mode`, effort) and the guidance check `review delegate` applies.

## Done but wrong

- Only the working-tree lookup reads `harness_model`, so `validate` is quiet but prompts and launches, which read the integration branch, still get no profile: the pinned row.
- One pass per profile, so an earlier `harness_model` match beats a later `id` match: the id-wins row puts B first.
- `harness_model` is tried before `id`, which changes the profile of entries that match today: the id-wins row.
- Pass 2 on the integration branch bypasses `_pinned_for_id`, so a drifted local profile is used: the pinned-drift rows.
- The warning is silenced without a match: the api_id row also checks the prompt text.

## Zones

Zone changes are the coordinator's. The coordinator adds any needed exact validate-golden path under `tests/parity/` before execution. Otherwise the executor stops and names the path and its before/after fragment; it does not edit the node.

## If this fails

Assumption: no roster in the dogfood fixture or the parity goldens has an entry whose `harness_model` matches a different profile than its `id`. If a golden changes, stop and report its before and after fragment (see Zones); if a launch flag changes for an existing fixture entry, stop and report it.

## Accepted limits

- The no-profile warning still prints on `add-node` and `edit-node`, where it has nothing to do with the command (M23 intake).
