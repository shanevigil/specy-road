## Intent

**Goal: quality, not lines** (maintainer, revision 3). M16 keeps every delivered behaviour — proven by the parity harness (M16.1.1), the review-gate decision table (M16.1.2) and each leaf's own parity table — and moves the code toward best practice: small single-purpose functions, clear module boundaries, no import cycles, explicit dependencies instead of hidden ones (module globals, or functions that reach for the clock or git themselves are given those as parameters where tests need a seam; no dependency-injection framework), each rule stated once rather than duplicated, and docstrings and comments that explain intent kept or improved. Smaller code is a side effect, not the target. Growth since v0.2.3 (package 31k to 65k lines, tests 25k to 65k, 45 to 68 top-level commands) came mostly from orchestration and the review gate, which the maintainer ruled canonical core (2026-11-05, decision D1), and from narrow patches per review round. M16 consolidates structure, commands, config, tests and docs; workers and orchestration stay in core and get one internal subpackage with one state model that the 0.3.2 PM GUI can read. Planned for release candidate rc5; rc4 is fixes only, and rc4 fixes from now on go into M16's feedback-and-fix intake (M16.8.4), not M15. 0.3.1 final is tagged when M16 ends, after an end-to-end pass and a fix round (M16.8.4, M16.8.9). The PM GUI's orchestration view is 0.3.2, phase M17. Version numbers stay with the maintainer.

## Approach

- **Rules for every leaf** (written into constraints/README.md by M16.1.7). Behaviour is preserved: the parity harness (M16.1.1), the review-gate decision table (M16.1.2) and the leaf's own parity table stay green. Two named exceptions add behaviour: zone-scoped `checks:` gates (M16.4.6) and the complexity gate (M16.5.14). **Best practice in what a leaf touches** (revision 3): small single-purpose functions; clear module boundaries and no new import cycle (M16.2.6); explicit dependencies — module globals and functions that call the clock or git themselves are given those as parameters where a test needs a seam, with no dependency-injection framework; one statement of each rule, not copies; names say what the code does; docstrings and comments that explain intent kept or improved, never stripped to save lines; no code squashing (joined statements, removed blank lines, shortened names or deleted explanations to meet a number). Each leaf's last acceptance line is an informational line-change estimate: never a gate and never by itself a review finding. No new config key, policy key or command without retiring one (`checks:` is the named exception; the roster's version-2 form replaces the flat entry). Old commands and config forms stay as hidden aliases, each a row of tests/parity/command_map.yaml, until M16.8.3 (see Alias window). Every deprecation and removal is recorded in CHANGELOG.md's [Unreleased] section by the leaf that makes it. Adopter feedback is parked until M16 ends; rc4 fixes go into M16.8.4's intake.
- **Quality metrics** (revision 3), each non-regressing per leaf and reported per release, from ruff and the existing or planned tests only (no new analysis dependency): ruff C901 plus the rule families PL, B, SIM, RET, N and a D subset for public functions and methods, held by a shrink-only per-file baseline (M16.1.8) so existing findings are recorded and may only fall; line width over 100 characters (M16.1.8); and the import-direction and no-cycles gate (M16.2.6). `scripts/lean_metrics.py --check` (M16.1.7) prints the totals. mypy, radon and duplication tools are out of scope for M16; a project may declare them itself through `checks:` (M19.1, after 0.3.1).
- **Parity tables before moves.** Every leaf that moves or merges behaviour first commits a finite table built from today's behaviour (process corpus M16.2.9, state table M16.3.1, cleanup M16.4.1, config migration M16.4.5, workers M16.5.2, eligibility M16.5.4, guard M16.5.8, grind M16.5.9, records M16.5.10) and then keeps it green. A golden transcript may change only for a command_map.yaml row.
- **Post-fix refactor (maintainer, 2026-11-05).** No leaf's diff raises a function's C901 score above its merge-base score or adds `noqa: C901`; fix rounds end with a consolidation step. M16.5.14 makes this a product gate. Fold leaves rewrap the files they merge, lower their width-baseline entries, and leave no comment naming a roadmap id or review round in those files: each is deleted when it only records split or review history, or rewritten without the id when it explains current behaviour (revision 4).
- **Paths and baselines** (revision 4). Zones and acceptance name paths as at planning; a leaf after M16.2.5 resolves a path through M16.2.5's committed move list, and a leaf after M16.5.3 through M16.5.3's destination list. A leaf that moves or folds modules zones the baselines it touches (scripts/line_width_baseline.json, scripts/ruff_quality_baseline.json, constraints/import-layers-baseline.json, constraints/test-private-imports-baseline.txt, constraints/clone-baseline.json) and changes them only by relocation (M16.1.8's transfer rule, M16.2.6's rename rule; in clone-baseline.json each pair's module names are rewritten through the leaf's committed move or fold mapping) or by lowering an entry (a clone pair that vanished is removed); `scripts/check_clones.py` stays green and no new clone pair enters the baseline (alignment review, S2). Where it updates callers of moved modules (zone `specy_road/`), a diff line outside the moved or folded files and specy_road/orchestration/ changes only an import path or a patch-target string.
- **Review discipline.** Reviewers check the acceptance lines and the leaf's parity tables; a new input class goes to intake. After a second block of the same class the planner rescopes or splits the leaf; a leaf past four rounds is split or rescoped. The review-finding test rule (recommendation 3.4 item 4) applies to every test a fix adds.
- **Order.** Pass 0: M16.1.1, M16.1.2 and the maintainer's triage M16.1.3 feed the baseline M16.1.7, which every code and test leaf follows; M16.1.8's quality baselines follow M16.1.7 and precede the code chain (M16.2.1 depends on M16.1.8, revision 4). The code lane is one serial chain, because each leaf edits the tests of what it moves: M16.2.1, M16.2.2, M16.2.3, M16.2.4 (helpers and index); M16.2.5, M16.2.6, M16.2.7, M16.2.8 (layering); M16.2.9, M16.2.10, M16.2.11 (in-process CLI); M16.3.1 (orchestration interface and state model); M16.3.2, M16.3.3, M16.3.4, M16.3.5, M16.3.6, M16.3.7 (folds; PM UI last, after the snapshot); M16.4.1, M16.4.2, M16.4.3, M16.4.4 (surface); M16.4.5, M16.4.6 (config); M16.5.1, M16.5.2, M16.5.3, M16.5.4, M16.5.5, M16.5.6 (roster split, after the eligibility merge), M16.5.7, M16.5.8, M16.5.9, M16.5.10, M16.5.11 (orchestration moves, each a pure move then a consolidation); M16.5.12, M16.5.13 (review folds, after M16.1.6's evidence); M16.5.14 (complexity gate). The test lane follows the code lane, so the dedupe leaves (M16.7.2-M16.7.5) compare arc sets on production code as M16.5.14 left it, and M16.7.6 then adds only its listed seams (alignment review, G6): M16.6.3, M16.6.4, M16.6.5, M16.6.6, M16.7.1, M16.7.2-M16.7.5, M16.7.6, M16.7.7, M16.7.8. - **Critical path** (leaf count): 56 leaves, M16.1.1 → M16.1.7 → M16.1.8 → the code chain (38) → the test chain (12) → M16.8.1 → M16.8.3 → M16.8.4, plus human waits: the triage, the M16.1.6 decisions, the M16.8.2 alias-window gate and the M16.8.9 tag gate. Wall time is dominated by the move and dedupe leaves and those human waits, not by the count.
- **Removing tests.** Integrity follows renames, so pure moves need nothing. A leaf that removes or folds tests (M16.2.1, M16.5.8, M16.6.6, M16.7.2-M16.7.5, M16.7.7) gets planned_test_changes set by the coordinator before pickup, from its decided list or committed worklist; a removal found mid-leaf is a blocked_on stop.
- **0.3.2 PM GUI is phase M17** (maintainer, 2026-11-05). M16 delivers only the snapshot interface (M16.3.1, fixture tests/fixtures/orchestration_snapshot_v1.json, `schema: 1`) and the PM UI server fold (M16.3.7). M17.1 is the non-dispatchable placeholder that depends on both; GUI-specific acceptance lives there, including ownership of pm-gui.md's existing sections.
- **Targets are soft estimates** (maintainer, revision 2). Line numbers steer planning; none is a gate and none justifies squashing code, stripping docstrings or shortening names. The leaves' estimates sum to about -3,800 package lines through M16.8.1 (65.4k to about 61.6k before rewrap growth; the roster split adds about +270 while both forms are read); 52-56k is a long-run estimate. The hard numbers left are not line counts: canonical command count at most 56 (68, minus 14 retired names, plus the milestone and planning groups), coverage at or above fail_under, and the effectiveness measures the maintainer chooses for M16.7.8 from sr/research/agentic-unit-testing.md. Suite time is informational only and never a gate, threshold or review finding (maintainer, 2026-11-05, decision 5d); test functions about 2,200 is an estimate.
- **Alias window: option A** (maintainer, 2026-11-05). With two users today, old command names and config forms exist during rc5 only and are removed before the 0.3.1 final tag (M16.8.2 gate, then M16.8.3); 'one release' in a leaf's acceptance means rc5. The window must widen as adoption grows (at least a full minor release); revisit at a higher 0.x. CHANGELOG.md's [Unreleased] section is kept current with every deprecation and removal (old name -> new name, and the release it is removed in); version headings stay with the maintainer.
- **Release shape.** 0.3.1 is tagged at the end of M16: after M16.8.3, M16.8.4 runs an end-to-end pass on the toolkit from a built wheel plus a feedback-and-fix round (fixes are new leaves the gate depends on), M16.8.8 brings the release docs in line, and the maintainer clears M16.8.9, ready to tag 0.3.1. M16.8.9 also waits on phase M22 (rc5 fixes), the rc4 fixes in M21 it lists (M21.1-M22.5, among them M21.5 and M22.5, and M21.13-M21.15), and phase M17 (the PM GUI orchestration view, in 0.3.1 and built in parallel with M16; maintainer, 2026-11-05 evening).
