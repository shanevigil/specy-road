## Intent

Make specy-road smaller and more coherent without removing any delivered capability. Growth since v0.2.3 (package 31k to 65k lines, tests 25k to 65k, 45 to 68 top-level commands) came mostly from orchestration and the review gate, which the maintainer ruled canonical core (2026-11-05, decision D1), and from narrow patches per review round. M16 consolidates structure, commands, config, tests and docs; workers and orchestration stay in core and get one internal subpackage with one state model that the 0.3.2 PM GUI can read. Planned for release candidate rc5 (rc4 is fixes only); 0.3.1 final is tagged when M16 ends, after an end-to-end pass and a fix round (M16.65, M16.66). The PM GUI's orchestration view is 0.3.2, phase M17. Version numbers stay with the maintainer.

## Approach

- **Rules for every leaf** (written into constraints/README.md by M16.2). Behaviour-preserving: the parity harness (M16.0), the review-gate decision table (M16.1) and the leaf's own parity table stay green. Two named exceptions add behaviour: zone-scoped `checks:` gates (M16.52) and the complexity gate (M16.22). **Quality, not line counts** (maintainer, revision 2): no touched function rises in complexity (M16.22's rule); docstrings and comments that explain intent are kept or improved, never stripped to save lines; names say what the code does; no code squashing (joined statements, removed blank lines, shortened names or deleted explanations to meet a number). Each leaf's last acceptance line is an informational line-change estimate: never a gate and never by itself a review finding. No new config key, policy key or command without retiring one (`checks:` is the named exception; the roster's version-2 form replaces the flat entry). Old commands and config forms stay as hidden aliases, each a row of tests/parity/command_map.yaml, until M16.62 (see Alias window). Every deprecation and removal is recorded in CHANGELOG.md's [Unreleased] section by the leaf that makes it. Adopter feedback is parked until M16 ends.
- **Parity tables before moves.** Every leaf that moves or merges behaviour first commits a finite table built from today's behaviour (process corpus M16.7, state table M16.15, cleanup M16.11, config migration M16.14, workers M16.46, eligibility M16.47, guard M16.48, grind M16.19, records M16.49) and then keeps it green. A golden transcript may change only for a command_map.yaml row.
- **Post-fix refactor (maintainer, 2026-11-05).** No leaf's diff raises a function's C901 score above its merge-base score or adds `noqa: C901`; fix rounds end with a consolidation step. M16.22 makes this a product gate. Fold leaves rewrap the files they merge, lower their width-baseline entries, and drop comments naming a roadmap id or review round in those files.
- **Review discipline.** Reviewers check the acceptance lines and the leaf's parity tables; a new input class goes to intake. After a second block of the same class the planner rescopes or splits the leaf; a leaf past four rounds is split or rescoped. The review-finding test rule (recommendation 3.4 item 4) applies to every test a fix adds.
- **Order.** Pass 0: M16.0, M16.1 and the maintainer's triage M16.34 feed the baseline M16.2, which every code and test leaf follows. The code lane is one serial chain, because each leaf edits the tests of what it moves: M16.3, M16.4, M16.35, M16.5 (helpers and index); M16.6, M16.36, M16.37, M16.38 (layering); M16.7, M16.39, M16.40 (in-process CLI); M16.15 (orchestration interface and state model); M16.9, M16.41, M16.10, M16.43, M16.44, M16.42 (folds; PM UI last, after the snapshot); M16.11, M16.12, M16.13, M16.45 (surface); M16.14, M16.52 (config); M16.16, M16.46, M16.17, M16.47, M16.63, M16.64 (roster split, after the eligibility merge), M16.18, M16.48, M16.19, M16.49, M16.50 (orchestration moves, each a pure move then a consolidation); M16.21, M16.51 (review folds, after M16.20's evidence); M16.22 (complexity gate). The test lane follows the code lane, so arc sets are compared on unchanged production code: M16.23, M16.54, M16.24, M16.55, M16.25, M16.56-M16.59, M16.26, M16.60, M16.28. Beside the chain: M16.8 (width baseline), M16.27 and M16.53 (public scenarios, new files only, required before M16.41 and M16.42), M16.20 (evidence), and the docs lane M16.29, M16.30, then M16.31 and M16.32 after the code lane. M16.33 closes rc5; M16.62 deletes aliases after the maintainer clears the M16.61 gate; M16.65 runs the end-to-end pass and fix round; the maintainer's M16.66 gate clears the 0.3.1 tag.
- **Critical path** (leaf count): 55 leaves, M16.0 → M16.2 → the code chain (38) → the test chain (12) → M16.33 → M16.62 → M16.65, plus human waits: the triage, the M16.20 decisions, the M16.61 alias-window gate and the M16.66 tag gate. Wall time is dominated by the move and dedupe leaves and those human waits, not by the count.
- **Removing tests.** Integrity follows renames, so pure moves need nothing. A leaf that removes or folds tests (M16.3, M16.48, M16.55, M16.56-M16.59, M16.60) gets planned_test_changes set by the coordinator before pickup, from its decided list or committed worklist; a removal found mid-leaf is a blocked_on stop.
- **0.3.2 PM GUI is phase M17** (maintainer, 2026-11-05). M16 delivers only the snapshot interface (M16.15, fixture tests/fixtures/orchestration_snapshot_v1.json, `schema: 1`) and the PM UI server fold (M16.42). M17.1 is the non-dispatchable placeholder that depends on both; GUI-specific acceptance lives there, including ownership of pm-gui.md's existing sections.
- **Targets are soft estimates** (maintainer, revision 2). Line numbers steer planning; none is a gate and none justifies squashing code, stripping docstrings or shortening names. The leaves' estimates sum to about -3,800 package lines through M16.33 (65.4k to about 61.6k before rewrap growth; the roster split adds about +270 while both forms are read); 52-56k is a long-run estimate. The hard numbers left are not line counts: canonical command count at most 56 (68, minus 14 retired names, plus the milestone and planning groups), coverage at or above fail_under, and half the baseline suite time (M16.28). Test functions about 2,200 and suite time 35 s are estimates.
- **Alias window: option A** (maintainer, 2026-11-05). With two users today, old command names and config forms exist during rc5 only and are removed before the 0.3.1 final tag (M16.61 gate, then M16.62); 'one release' in a leaf's acceptance means rc5. The window must widen as adoption grows (at least a full minor release); revisit at a higher 0.x. CHANGELOG.md's [Unreleased] section is kept current with every deprecation and removal (old name -> new name, and the release it is removed in); version headings stay with the maintainer.
- **Release shape.** 0.3.1 is tagged at the end of M16: after M16.62, M16.65 runs an end-to-end pass on the toolkit from a built wheel plus a feedback-and-fix round (fixes are new M16 leaves the gate depends on), and the maintainer clears M16.66, ready to tag 0.3.1.
