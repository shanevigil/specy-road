## Intent

Make specy-road smaller and more coherent without removing any delivered capability. Growth since v0.2.3 (package 31k to 65k lines, tests 25k to 65k, 45 to 68 top-level commands) came mostly from orchestration and the review gate, which the maintainer ruled canonical core (2026-11-05, decision D1), and from narrow patches per review round. M16 consolidates structure, commands, config, tests and docs; workers and orchestration stay in core and get one internal subpackage with one state model that the 0.3.2 PM GUI can read. Planned for release candidate rc5 (rc4 is fixes only); version numbers stay with the maintainer.

## Approach

- **Rules for every leaf** (written into constraints/README.md by M16.2). Behaviour-preserving: the parity harness (M16.0), the review-gate decision table (M16.1) and the leaf's own parity table stay green. Two named exceptions add behaviour: zone-scoped `checks:` gates (M16.52) and the complexity gate (M16.22). Each leaf declares an expected net line delta, met or explained; additive by design: M16.0, M16.1, M16.2, M16.8, M16.20, M16.22, M16.25, M16.27, M16.36, M16.52, M16.53. No new config key, policy key or command without retiring one (`checks:` is the named exception). Old commands and config forms stay as hidden one-release aliases, each a row of tests/parity/command_map.yaml, until M16.62. Adopter feedback is parked until M16 ends.
- **Parity tables before moves.** Every leaf that moves or merges behaviour first commits a finite table built from today's behaviour (process corpus M16.7, state table M16.15, cleanup M16.11, config migration M16.14, workers M16.46, eligibility M16.47, guard M16.48, grind M16.19, records M16.49) and then keeps it green. A golden transcript may change only for a command_map.yaml row.
- **Post-fix refactor (maintainer, 2026-11-05).** No leaf's diff raises a function's C901 score above its merge-base score or adds `noqa: C901`; fix rounds end with a consolidation step. M16.22 makes this a product gate. Fold leaves rewrap the files they merge, lower their width-baseline entries, and drop comments naming a roadmap id or review round in those files.
- **Review discipline.** Reviewers check the acceptance lines and the leaf's parity tables; a new input class goes to intake. After a second block of the same class the planner rescopes or splits the leaf; a leaf past four rounds is split or rescoped. The review-finding test rule (recommendation 3.4 item 4) applies to every test a fix adds.
- **Order.** Pass 0: M16.0, M16.1 and the maintainer's triage M16.34 feed the baseline M16.2, which every code and test leaf follows. The code lane is one serial chain, because each leaf edits the tests of what it moves: M16.3, M16.4, M16.35, M16.5 (helpers and index); M16.6, M16.36, M16.37, M16.38 (layering); M16.7, M16.39, M16.40 (in-process CLI); M16.15 (orchestration interface and state model); M16.9, M16.41, M16.10, M16.43, M16.44, M16.42 (folds; PM UI last, after the snapshot); M16.11, M16.12, M16.13, M16.45 (surface); M16.14, M16.52 (config); M16.16, M16.46, M16.17, M16.47, M16.18, M16.48, M16.19, M16.49, M16.50 (orchestration moves, each a pure move then a consolidation); M16.21, M16.51 (review folds, after M16.20's evidence); M16.22 (complexity gate). The test lane follows the code lane, so arc sets are compared on unchanged production code: M16.23, M16.54, M16.24, M16.55, M16.25, M16.56-M16.59, M16.26, M16.60, M16.28. Beside the chain: M16.8 (width baseline), M16.27 and M16.53 (public scenarios, new files only, required before M16.41 and M16.42), M16.20 (evidence), and the docs lane M16.29, M16.30, then M16.31 and M16.32 after the code lane. M16.33 closes rc5; M16.62 deletes aliases after the maintainer clears the M16.61 gate.
- **Critical path** (leaf count): 52 leaves, M16.0 → M16.2 → the code chain (36) → the test chain (12) → M16.33 → M16.62, plus the triage, the M16.20 decisions and the alias-window gate as human waits. Wall time is dominated by the move and dedupe leaves and those human waits, not by the count.
- **Removing tests.** Integrity follows renames, so pure moves need nothing. A leaf that removes or folds tests (M16.3, M16.48, M16.55, M16.56-M16.59, M16.60) gets planned_test_changes set by the coordinator before pickup, from its decided list or committed worklist; a removal found mid-leaf is a blocked_on stop.
- **0.3.2 PM GUI.** It reads the snapshot fixture tests/fixtures/orchestration_snapshot_v1.json, starts after M16.15 and M16.42 merge, imports only `specy_road.orchestration`, and owns the existing pm-gui.md sections (M16.31 appends, it does not rewrite).
- **Targets.** rc5 is checked against what the leaves fund: package deltas through M16.33 sum to about -4,100 lines (65.4k to about 61.3k before rewrap growth); 52-56k stays an estimate, not a gate. Canonical command count 56 (68, minus 14 retired names, plus the milestone and planning groups). Test functions about 2,200 and suite time 35 s are reported estimates; the gates are no coverage drop below fail_under and half the baseline suite time (M16.28).
