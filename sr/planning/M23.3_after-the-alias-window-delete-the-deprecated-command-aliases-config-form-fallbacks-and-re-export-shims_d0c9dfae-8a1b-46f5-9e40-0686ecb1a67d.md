## Tier

behavioural: removing fallbacks and dual-read paths can change what an adopter's existing config does, and the goldens only show command-surface changes.

## Done but wrong

- A config that still carries an old form loses its check silently. Check: validate on a repo whose git-workflow.yaml still sets `verify_cmd` fails and names the key.
- A shipped template or skill still names a removed command. Check: after `init project` and `specyrd init` into a temp directory, a search of the generated files for each removed name in REPLACED_COMMANDS finds nothing.

## If this fails

The assumption most likely to break is that the current-form readers already compute every default the fallback paths supplied. If the parity harness differs for a current-form config, the default moves into the current reader. The coordinator decides; if keeping a form past the window is needed, the maintainer decides.
