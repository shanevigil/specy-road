## Intent

A `human:` acceptance criterion is something only a person can satisfy. Today `finish-this-task` accepts it as soon as the leaf's planning sheet has a line `A#: <decision>` committed on the branch (`finish_task_gates.human_acceptance_or_exit`). Any agent can type that line. So the executor, whose work the sheet judges, can write the line that lets its own leaf finish. Maintainer decision, 2026-11-11, in their words: "the planner should never have written the node to write to the planning sheet. All work should be recorded in /work/ sheets, not the planning sheet. Allowing such alteration blurs the line and possibly opens the door for agents to be able to change their plans to create false success conditions." And, on `human:` acceptance criteria: "I want it recorded in the decision ledger, not the plan sheet."

After this leaf, a person's decision on a `human:` criterion is a closed entry in `roadmap/decisions.yaml`. Only a person can create that entry through specy-road's own commands: at an interactive terminal, or through the PM GUI's operator answer. `finish-this-task` reads the ledger, and a sheet line no longer counts. Other leaf decisions also close in the ledger without a sheet line. This is a mitigation, in line with the maintainer's "mitigation over complete solutions" stance: the honour-system limits are stated in the docs (see Accepted limits).

## Approach

**The record.** The record is one `kind: human-action` entry in the tracked ledger, with `node` set to the leaf and a new optional schema field `criterion: A#` (pattern `^A[1-9][0-9]*$`). The entry counts when it is closed with `decided_by: operator` and a `channel` of `terminal` (a new enum value) or `pm-gui` (exists, M17.15). No new entry kind and no new command: `decisions add` gains `--criterion`, and `decisions close` gains the person-only path for an entry that has one.

**Opening is free, closing is a person's.** Any caller (the executor, a coordinator, a person) may open the entry: `specy-road decisions add <NODE> --kind human-action --criterion A2 --summary … --option … --recommendation … --recommendation-reason … --default …`. Asking is not deciding. `add` refuses `--criterion` with any other kind, an `A#` that is not a `human:` criterion of that node (`finish_task_gates.human_acceptance_ids`), and a second open entry for the same node and criterion.

**The person-only close, smallest that fits.** Three precedents exist. I reuse the first two and leave the third out:

- **Interactive terminal, no override.** This is the `review defer` / `review accept-policy` rule: refuse unless `sys.stdin.isatty()`, with no `--yes`. On top of that: `review_override.role_refusal()`, so a launched executor, reviewer or rca worker is refused even inside a pseudo-terminal, and `review_override.recorder()` for the git identity. `decisions close <ID>` on an entry with `criterion` prints the node, the criterion's text and the answer, asks `y/N`, and on `y` closes the entry with `decided_by: operator`, `channel: terminal` and the answer followed by ` (recorded by <name> <email>)`. On anything else it writes nothing.
- **PM GUI operator action.** `gui_app._answer` already closes an open `human-action` entry with `decided_by: operator, channel: pm-gui`, behind the per-start code printed on the GUI's terminal. No GUI change is needed; a test row proves that the GUI path's entry satisfies finish.
- **Signature under `signed_reviews`.** This is out of this leaf. Signing today covers review records (`review record --sign-key`), not ledger entries. Extending it means a new signed-payload format for entries and a verifier in finish. It is the strong control, and it is listed as a maintainer decision in the notes.

**Where finish reads.** `finish-this-task` runs on the leaf branch. The GUI commits to the integration branch, and a person at a terminal may close on either. So finish reads `roadmap/decisions.yaml` as committed at the leaf branch's `HEAD` and as committed at the integration branch tip, using `review_policy_ref.committed_yaml`, the same pair of sources M22.51's `_ledgers` reads (both committed here, never the working tree). `decisions.local.yaml` never counts, because it is gitignored and leaves no trail. Use the integration ref that `finish_task` already resolves (`resolve_integration_defaults`). `finish_task_gates.undecided_human_items(root, node, integration_ref)` returns the undecided ids. The finish refusal and `handoff status` both call it.

**Finish refusal text.** It lists each undecided id and says that a planning-sheet `A#:` line no longer counts. It then names the `decisions add … --criterion A#` form and the two ways a person closes the entry (`decisions close <ID>` in their own terminal, or the PM GUI's Status window). This is the deprecation notice for adopters' existing sheet lines. There is no migration. A tool that copied `A#:` lines into the ledger would turn agent-writable text into a person's record, which is the hole this leaf closes. `recorded_decisions` and `_DECISION` in `finish_task_gates.py` are deleted. The refusal sentence is unconditional, so nothing needs to parse sheets.

**Review gate.** The review gate never read the sheet line. Reviewers mark a `human:` item `n/a` and the gate never counts that as a fail. Its pass/fail stays unchanged: the review attests the code, and the person attests the criterion. The gate's reporting surface, `handoff status`, reads the same function and shows the undecided criteria on one text line and as JSON `human_criteria_undecided` (an empty list when none), so the person sees that they are needed. This adds no exit-code change and no new state.

**Other leaf decisions (outcome 3).** `decisions.close_entry` loses its `sheet_text` requirement and its refusal. `cmd_close` stops reading the sheet. `recorded_on_sheet` stays, because `grind_status.gui_pending` still uses it to decide whether a coordinator has processed an ordinary GUI answer. For a GUI-closed entry that has `criterion`, `gui_pending` lists nothing, because `finish-this-task` is its consumer. Without this, the coordinator skill would tell the coordinator to write the `D#: answer` line onto the leaf's sheet for exactly these entries. Ordinary decisions (no `criterion`) still close from any caller, as today. They gate nothing.

**Order of work.** Schema field and enum value, in the template and in the `sr/` copy (the `sr/` project writes through its copy). Then `add --criterion` and the person-only close. Then the finish read and refusal. Then `handoff status`. Then the `close_entry` and `gui_pending` change. Docs last.

## Tier

trust boundary. This changes what `finish-this-task` accepts for a `human:` criterion, and adds a person-only write that a finish gate reads. `sr/tools/tier.py`'s path floor also raises it (`finish_task_gates.py`, `finish_task.py`, `review_cli.py`).

## Done but wrong

- A sheet `A#:` line still satisfies finish. Check: F2.
- An entry an agent can close non-interactively satisfies finish: a closed entry without a channel, or a `decisions close` from a non-TTY or a worker role. Check: F4, C1, C2.
- Finish reads the working tree or the local ledger, so an uncommitted or gitignored edit counts. Check: F6, F7.
- An entry for another leaf or criterion counts. Check: F5.
- The GUI path, which the brief names as a person's route, does not count. Check: F9.
- The review gate's verdict or exit code changes. Check: F10 and the existing `handoff status` parity rows.
- Ordinary decisions still need a sheet line. Check: L1.

## If this fails

Assumption: reading the ledger at the leaf `HEAD` and at the integration tip with git is enough to see both the person's terminal close and the GUI's commit. If an adopter runs finish where the integration ref does not resolve (no remote and no local branch), only the leaf `HEAD` is read. The refusal then says to commit the entry on the leaf branch. If that is not acceptable, stop and ask the maintainer, rather than reading the working tree.

## Accepted limits

- **Honour system.** These still get through: a process in a pseudo-terminal with the role unset or `coordinator` (as with M22.51 and M22.67); a direct call of `close_entry` from `python -c`; a hand-edited ledger entry committed to either branch; a process that can read the PM GUI's code or drive its browser. The `channel`, the recorder identity in the answer and the commit that adds the entry make a forgery visible in review, not impossible. A5 puts this in the docs.
- No signature on ledger entries, even under `signed_reviews` (maintainer decision in the notes).
- Gate nodes are out of scope. `set-gate-status` reads no `human:` line, and gate sheets are person-edited (`gate-sheet.md.template`'s `## Decisions and notes` stays).
- Milestones and phases are out of scope: finish runs on leaves.
- `gui_pending`'s sheet-line test for ordinary GUI answers, and the orchestrate skill text that tells the coordinator to write that line, are unchanged (maintainer decision in the notes).
- Existing open leaves whose acceptance or sheet says to record a person's decision on the sheet are not edited here. The planner updates them with this leaf; the notes list them.
- No migration of existing sheet lines. The finish refusal is the deprecation notice.
- Overlaps without an edge: M16.3.2 folds `finish_task_gates.py` into `finish_task.py`, and both paths are in the zones; whichever lands second rebases. M16.5.10 moves `decisions.py` and `decisions_cli.py`, and its record parity fixtures should then include a criterion entry. M16.4.3 moves `handoff status`, and the new line moves with it. M19.14, M19.15 and M19.18 edit the ledger CLI and schema after 0.3.1. M16.3.1 (in progress) claims `docs/orchestration.md`, so the overlap warning is expected.
