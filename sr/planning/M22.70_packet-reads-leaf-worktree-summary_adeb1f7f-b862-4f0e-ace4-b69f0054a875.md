## Intent

A reviewer must see the executor's implementation summary. Executors write it in their own worktree under the gitignored `work/`, and a worker's sandbox often cannot write the main checkout. `review-packet` today looks only at the reviewed commit and at the working tree of the checkout it runs in, so a packet built from the integration checkout reports "Not provided: no summary" for a summary that exists. Reviewers trust the packet and block the hand-off criterion (seen on an rc5 leaf: code approved, only the summary's location failed). The maintainer's rule is that all work is recorded in `work/` files, never the planning sheet, so those files have to reach review wherever the worker runs.

## Approach

- In `review_packet.py`'s summary section, add the leaf's own worktree as a lookup between the committed copy and the running checkout's working tree. Find the worktree the way `prompt --role reviewer` does (`role_prompt_cli`'s claimed-worktree lookup: the worktree `git worktree list --porcelain` shows with the leaf's branch checked out). Reuse that code; if it must become public to be shared, make the smallest move.
- Label which copy was used and its path, beside the existing committed and working-tree labels.
- Verify through the public CLI with real git worktrees in a temporary repository; no mocks of the lookup.

## Tier

trust boundary (the change is in the review packet, under the trust paths)
