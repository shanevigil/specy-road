## Intent

M17.1 questions 9 and 11 (maintainer, 2026-11-06: yes, in the 0.3.1 GUI). The PM GUI cannot view or edit a node's acceptance criteria, so a leaf created in the GUI has none and pickup and grind-session skip it until someone adds them on the command line (rc4 sandbox GUI test 2026-11-05 part C row 2b; rc4 final sandbox 2026-11-06 F2).

Out of scope: touch zones, dependencies or any other field's editor; a new API route; changes to edit-node semantics.

## Approach

- Reuse what exists: `PATCH /api/nodes/{id}` with `{"pairs": [{"key": "acceptance", "value": ...}]}` goes to `edit_node_set_pairs`, which applies `edit-node --set acceptance=` semantics: the value is one criterion per line, blank lines dropped, an empty value removes the field. The GUI sends one pair with the criteria joined by `\n`; no server change.
- One text field per criterion, so a criterion can never be split by a newline the user typed: the dialog refuses a newline inside a criterion with a message.
- The edit modal's save queue (`editModalSaveQueue.ts`) already debounces and orders field saves, sends the fingerprint and handles the milestone lock; acceptance becomes one more field in it.
- The logic lives in a pure helper with vitest rows (the GUI's tests run in a node environment with no DOM library).
