## Intent

An adopter's delegated reviewer ran the harness's default model while its record named the rostered one. The roster entry had no `harness_model` and no profile, so `review delegate` passed `harness_model(entry, "")`, got `None`, and launched with no model flag. `worker delegate` and `docs/orchestration-models.md` pass the roster id in that case; review delegate does not. The record then counted toward distinct families under the wrong family. The routing refusal only caught Cursor, and its remedy named `pinned: true` instead of the missing model. M15.3 adds the reported-model check for `prompt --channel cli --run` only; this leaf applies it to `review delegate`.

## Approach

- `review_delegate._Harness`: resolve the model as `worker_ops_launch._cli_for` does (no profile: `harness_model(entry)`, which returns the roster id), not `harness_model(entry, "")`.
- Before `save_run`, refuse when the resolved model is `None` and `entry.get("routing") != "dynamic"`. Raise `DelegateError` so no RUN record is opened.
- After the attempts, read the reported model with `review_model_check.reported_model` (M15.3) over the attempt's text. Compare it with `check(reported, entry, prof)` and pass `model_check=(reported, state)` to `file_review`, as `review_record_write.run_and_file` does. Add `requested_model` and `reported_model` to the run dict.
- `orchestration_config.entry_routing`: compute the resolved model for every harness and return `dynamic` when it is `None`. Keep Cursor's `auto` and `channels.cli` reading as they are. `routing_problem`: when the entry resolves no model, the message names the missing model and `harness_model` first.
- Docs: one paragraph in `docs/orchestration-models.md` next to the existing "With no profile and no `harness_model`" text.
