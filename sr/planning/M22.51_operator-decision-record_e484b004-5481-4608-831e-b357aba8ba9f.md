## Intent

The operator owns the rules and must be able to decide a leaf's review outcome directly, without turning that decision into reviewer paperwork. On 2026-11-08 and 09 the maintainer accepted M16.1.6 as-is, and the tool still refused: a human approval only fills a missing reviewer family, and `review defer` needs an RCA record and refuses correctness findings. Source: maintainer analysis (private), 2026-11-09, section 4.

## Approach

The maintainer decided on 2026-11-09 that an operator decision is given in plain words, for example "approved" or "accept as-is" in the coordinator's chat, and the coordinator records it with a command, without an interactive prompt. That changes a governing rule: `constitution/principles.md` section 6 names interactive approval in `mark-implementation-reviewed` as the one exception to recorded review, and section 7 lets unattended closure use only approval the records already earned. This leaf proposes amending both sections (and the `sr/` copy) to name the operator decision record. The maintainer approved this constitution amendment on 2026-11-09 ("yes to 2", in reply to the coordinator's list item "M22.51: approve or reword the constitution change. It amends principles.md §6 and §7 to name the operator decision record").

Reuse `review defer`'s decision-entry and marker machinery (`review_deferral.py`, read only), without its RCA requirement and refusal rules. The decision entry is the authority, and the marker is a cache.

- **Role check:** the existing orchestration guard never sees this command and knows no coordinator or rca role, so the command reads `SPECY_ROAD_ORCHESTRATION_ROLE` itself before any write. Any set value other than `coordinator` is refused; unset is the manual coordinator.
- **Standing rule:** the coordinator form needs a dedicated `kind: standing-rule` ledger entry that quotes the operator. Routing preferences are not authority to settle findings, so a `preference` entry is refused. A standing rule is not an open question and is not applied as routing.
- **Coordinator evidence (decision 5):** the coordinator form cites two RCAs and two alignment reviews, each by model, path and sha256. The RCA analysts are of two families and not parties to the leaf. The alignment reviewers are of two families, neither an analyst nor the blocking reviewer.
- **Scope of a decision:** it settles only the findings and the shortfall it names, at the commit it names. Every other gate condition still applies.

The standing-rule form never applies to a trust-boundary leaf; the explicit operator form may. Revocation before landing is outside this leaf; after landing, reversal is a follow-up leaf.

## Tier

trust boundary: review records and the gate.

## Done but wrong

- An executor or reviewer can record an operator decision: the role row refuses each launch role, and the marker-only row shows a hand-written marker has no effect.
- An override outlives its commit: after a non-bookkeeping commit (code-commit row), the gate counts reviews again.
- A decision clears more than it names: the later-block and other-gate-failures rows still fail.
- A routing preference authorises the coordinator form: the rule row refuses it.

## If this fails

Assumption: `passed` can be true with no new approval record once the named blocks and shortfall are settled, and the gate can read the decision without widening into other gate modules. If the only way is to file a review record, or another module must change, stop and name it; the maintainer decides.

## Accepted limits

- One leaf and one commit per record; a node with children is refused, so a milestone full review is unchanged. Records are commit-bound, except for today's bookkeeping carry; M22.53's wider carry does not apply to them.
- The standing-rule form never applies to a trust-boundary leaf; the explicit operator form may.
- The role variable is set by the launcher. A process that sets `SPECY_ROAD_ORCHESTRATION_ROLE=coordinator`, or leaves it unset, is not stopped; the audit is the quote and recorder identity in the tracked entry.
- Quotes, session ids, recorder identity and evidence paths are audit assertions, not authentication of a human or proof that a model wrote a file. Deliberate forgery of a committed entry is outside this best-effort leaf.
- With `signed_reviews` off, the entry is unauthenticated, as an unsigned review record is. This leaf adds no signature check.
- There is no revoke command.
- A project with a copied decisions schema runs `refresh-schemas` before using the command.
