## Intent

CR1, part b (§9 replay 2026-11-05, Cursor, 3 of 3). In r1 the delegated reviewer hit a usage limit. composer-2.5 then "[performed] an independent review and [filed] the review record as `claude-opus-5-5`", which produced the merge trailer `Reviewed-by: claude-opus-5-5 (anthropic) approve ab179eb…`. r3 did the same as gpt-6.1-sol. Without `signed_reviews`, `review record --model <id>` takes any rostered reviewer id from any caller.

The rc4 minimum blocks this impersonation without breaking the documented reviewer flows:

- **Delegated runs.** `review delegate` and `prompt --channel cli --run` file through `file_review` inside the run, so this leaf does not change them, whatever harness the coordinator itself runs in.
- **Manual filing from a harness.** A reviewer session that runs `review record` itself inside a harness is identified by that harness and files as today when the harness matches its roster entry. This is the paste or subagent prompt, or a grind pre-finish reviewer-cli.
- **Unidentified callers.** A caller that cannot be identified, such as a plain terminal where a human files pasted notes, must attest with `--human-filed`. The gate counts such a record only when it is signed, or when the project opts in with `policy.count_human_filed_reviews`.

Decision: the caller is identified by a worker id or a harness environment marker, never by anything the caller types. The check compares harnesses, not model ids, because a harness does not reliably expose its model to child processes.

Out of scope:

- Two models on one harness. M21.26 excludes READY authors by model id, and `signed_reviews` is the strong check.
- An agent that unsets its harness marker. That is cooperative, like READY, and M22.5 plus the AGENTS rule from M21.30 cover it.

Overlaps checked (2026-11-05):

- M21.30 also edits review_gate.py, review_cli.py and docs/orchestration-review.md, so this leaf depends on it. That carries M21.26 and M21.27 with it; M21.27 introduces the separate review record argparse handler this check sits in.
- Later milestones listing review_gate.py, orchestration_config.py, orchestration.schema.json or review-record.schema.json (M16.4.5, M16.5.x, M18.17, M18.18 and others) land after rc4.

## Approach

- New `specy_road/review_caller.py`. `caller() -> ("worker", model) | ("harness", name) | None`:
  - When `SPECY_ROAD_WORKER_ID` names a worker record, the result is that record's model.
  - Otherwise the result comes from a table with one environment marker per harness. Claude Code exports `CLAUDECODE=1`. The Codex and Cursor markers are confirmed against the harness versions of the replay before they go in the table. A harness whose marker is not confirmed stays unidentified, which still blocks CR1 through the attestation rule.
- The review record argparse handler (from M21.27; not `cmd_review_record`) checks the caller before any write, lock or REJECTED file:
  - A worker caller whose model is not `--model` is refused.
  - A harness caller is refused when the `--model` entry's `harness` is a different harness, or is missing or `generic`. The message is "<M> is a <harness> roster entry and this command runs under <caller>; file a review only under your own model id (AGENTS.md, Review roles); nothing was written".
  - An unidentified caller needs `--human-filed "<who and why>"`. The text must be one non-empty line. It is stored as `human_filed` on the record before signing, and review-record.schema.json gains the property.
- `review_gate._eligibility`: a record with `human_filed` counts only when its signature verifies against the roster entry's `public_key`, or when `policy.count_human_filed_reviews` (default false, added to orchestration.schema.json and `DEFAULT_POLICY`) is true on the integration branch. Otherwise it goes to ineligible with "filed by hand (human_filed) and unsigned; policy.count_human_filed_reviews is off".
- role_prompt's paste-channel lines: the `review record` command the prompt shows adds `--human-filed "<who filed it>"`. That is the flow in which a human runs it.
