## Intent

An unattended worker turn can call its harness's ask-the-user tool. No person sees the question, the call returns with no answer, and the worker may then write that a person was asked and declined. The post-run check reports the turn as clean, so the record says a person was asked when nobody was. Found in field use of 0.3.1rc4 under the Cursor adapter. Two fixes: the executor prompt says that a headless turn has nobody to ask, and the post-run check names any question-tool call it sees.

## Approach

- **Prompt.** `executor_preamble` (`specy_road/bundled_scripts/role_prompt_rca.py:145`) gains one standing line, the same in every executor prompt, so no caller has to know whether the turn is attended: when the turn runs headless (`worker delegate`, `worker message`, a grind), no person can answer a question tool. Open questions go in the implementation summary under a heading that says they are unanswered, and the summary never says a person was asked.
- **Check.** The post-run check reads parsed stream events (`TurnWatch.observe`, `specy_road/worker_turn_check.py:122`). Its findings (`stream_findings`, `:159`) cover denials, failed turns and retries, and never look at tool names. Add one event type, `interactive_tool`, which the Cursor adapter emits for a `tool_call` event whose tool is Cursor's question tool. `observe` collects it, and `stream_findings` returns one finding of kind `interactive_tool` that names the tool and says no person saw it. So the turn's `post_run_check` event is not clean and the worker is flagged `post_run_findings`.
- **Cursor tool name.** The field report does not name the tool, and Cursor's `tool_call` events nest the tool under a key per tool (`worker_adapter_cursor.py:169-178` reads `shellToolCall`). The first task is to capture one real `agent -p --output-format stream-json` turn that calls the question tool, and to save the redacted lines as a test fixture. The name in code comes from that capture, not from a guess.
- **Claude Code needs no new code.** The executor's tools are an explicit allow-list with prompts off (`worker_adapter_claude.py:21-27`: `Read,Edit,Write,Glob,Grep,Bash`, `--permission-prompts none`). A question-tool call is therefore denied, and the denial already becomes a `permission_denied` finding that names the tool (`_turn_signals`, `:139-160`). One row of the test table pins that behaviour; if the capture shows the tool is not in `permission_denials`, stop (see If this fails).
- Codex `exec` with `approval_policy=never` has no ask-the-user tool to call; nothing changes for it.

Depends on M18.14, which is claimed and edits `worker_turn_check.py` (`git_state` and the stash findings, not `TurnWatch`).

## Tier

trust boundary: the post-run check is what records whether a worker's turn was clean.

## Done but wrong

- The finding fires on every Cursor `tool_call`: the other-tools row stays clean.
- The tool name is guessed rather than captured: the fixture is a real stream, and the test reads the name from it.
- The prompt line appears only for `worker delegate` and not for a prompt pasted into a headless run: the line is in `executor_preamble` itself.
- A Claude question-tool call is reported twice, as both a denial and `interactive_tool`: the Claude row expects exactly one finding.

## If this fails

Assumption: Cursor's stream carries the question tool as a `tool_call` event whose tool key can be read, and a denied Claude call shows in `permission_denials`. If the capture shows otherwise (no event, or the call is invisible in the stream), stop and report what the stream shows; the coordinator decides before any file outside the zones changes.

## Accepted limits

- A harness with no stream event for the tool cannot be checked; the prompt line is the only guard there.
- Chore executors (`chore_cli.chore_prompt`) do not get the line in this leaf: that module is in a claimed zone (M16.2.3). M23 intake.
