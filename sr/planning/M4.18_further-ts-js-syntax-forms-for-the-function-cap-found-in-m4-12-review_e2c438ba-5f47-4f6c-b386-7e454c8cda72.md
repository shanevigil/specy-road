## Intent

M4.12's later review rounds recorded TypeScript and JavaScript forms that the function-length cap still misses: a class arrow field with a definite-assignment `!` (`onChange! = () => {…}`, with or without a type annotation), and an `as` or `satisfies` cast after a grouped arrow, where the declarator that follows the cast was not measured. This slice makes `file-limits` measure each form and name it correctly, so an over-cap function written that way fails instead of passing silently.

## Approach

Extend the scanner in `specy_road/file_limits_js.py` only: accept `!` wherever the optional-member `?` is accepted, and skip a cast keyword and its type after a grouped arrow's closing parenthesis before splitting declarators. Keep the function under ruff's complexity limit by moving the grouped-arrow comma logic into a helper. One fixture per form under `tests/fixtures/file_limits_js/`, with a span check and a public-validator check that the form no longer prints OK when over the cap. Verify with the file-limits test files, ruff and `specy-road file-limits`.
