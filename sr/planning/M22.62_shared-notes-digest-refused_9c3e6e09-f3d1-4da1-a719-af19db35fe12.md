## Intent

Two reviewers from different families filed one commit, yet both REVIEW records carry the same `notes_sha256`. Someone checking independence reads that as one reviewer's notes filed twice. Found in field use of 0.3.1rc4.

`notes_sha256` is the SHA-256 of the Markdown body below the front matter, normalised (`review_signing.notes_digest`, `specy_road/review_signing.py:53`: line endings joined with `\n`, trailing whitespace at the end dropped). It is written by `review record` (`review_rejected.py:194`) and re-checked by the gate (`review_gate.py:233`, via `notes_problem`). It does not cover the front matter, so `findings`, `commands_rerun` and `required_changes` are outside it.

The cause is a shared body, not an empty one. The toolkit's own M22.29 review pair shows it: two models' records share `notes_sha256` `4be2d337…325d`, with byte-identical, non-empty bodies and different `findings` and `commands_rerun`. That is not the empty-string digest `e3b0c442…b855`. A front-matter `notes` key is not a route either: `review-record.schema.json:59` is `$defs/notes`, the array type used by `findings` and the other lists, and the schema has `additionalProperties: false`, so `load_review` refuses a `notes` key before any digest is taken. An empty body is still possible on its own (a schema-valid record with nothing below the front matter) and still says nothing, so the leaf refuses it too.

## Approach

All checks go in `review record`'s validation in `specy_road/review_rejected.py` (`_review_record_validate`, next to where the digest is computed). The gate and `notes_digest` are unchanged, so records already filed keep counting exactly as today, and signed records keep verifying.

- **B1, empty notes.** `review record` refuses a schema-valid record whose body below the front matter is empty or whitespace only after `notes_digest`'s normalisation. The message says that the notes go in that body and that `notes_sha256` covers only it. The refusal goes through `trace.refuse`, so `REJECTED-<model>.md` is written as for any other refusal. `review delegate` already passes the answer's `notes` into the body (`review_record_write.py:288`); a whitespace-only `notes` now gets this refusal, which is a rerun.
- **B2, a body another model already filed at this commit.** `review record` refuses a record whose non-empty `notes_sha256` equals `notes_digest` of the stored body of another model's REVIEW record for the same leaf at the same commit.
  - **Detection set.** The current `REVIEW-*.md` files that `list_reviews` returns for this leaf with `ok` true, another model id, and the same resolved commit. A record counts as a candidate whether or not the gate would count it: signature, roster and policy are not checked, so no gate-eligibility logic is copied here. `history/` copies, `REJECTED-` files and files `list_reviews` reports with errors are not candidates. The digest compared is `notes_digest` of each stored body, not the stored `notes_sha256` field.
  - **Message.** It names both models and says the two notes bodies are the same after normalisation; that `notes_sha256` covers only the body, not `findings` or `commands_rerun`; and that a body left as the notes template matches too. It asks for this review's own notes in the body. It does not say or imply that the record was copied: an honest second reviewer who kept the template and wrote everything into `findings` gets this refusal, and it must read as an instruction, not an accusation.
  - A model re-filing its own record at that commit, and an equal body at another commit, are filed as today.
- **Docs.** `docs/orchestration-reviewer-output.md` says what `notes_sha256` covers (the body below the front matter, normalised) and what it does not (the front matter, `findings`, `commands_rerun`, the file as a whole), and that two models' identical bodies at one commit are refused.

## Tier

trust boundary: changes what the record checks accept.

## Done but wrong

- The check is added to the gate, so records already filed stop counting: the gate-unchanged row.
- A model cannot re-file its own record after a rerun: the own-re-file row.
- The empty-body refusal is phrased as a digest problem and says nothing about where the notes go: the empty-body row asserts the message names the body.
- The duplicate check compares the stored `notes_sha256` field rather than re-digesting the stored body, or skips normalisation: the CRLF and trailing-whitespace rows.
- The refusal reads as an accusation of copying: the shared-body row asserts the message wording.
- The digest definition changes to cover `findings` or `commands_rerun`: every existing signed record would then fail `notes_problem`. The digest function is unchanged.

## If this fails

Assumption: the shared field digest is the normalised body, and `notes_digest` stays byte-identical. The M22.29 pair already shows a shared non-empty body. If the red rows do not fail before the fix as described, or if the only way to tell the two records apart is to change `notes_digest`, stop and report the evidence; the coordinator decides whether to change the node and sheet before implementation continues. Do not change `notes_digest`.

## Accepted limits

- Same body with different `findings` or `commands_rerun` is refused. The digest is not widened to those fields: that would change `notes_digest` and fail `notes_problem` on records already signed. The M22.29 pair is this case.
- Two reviewers who really write identical notes are refused; one of them reruns. Identical notes from two families are not independent review evidence.
- These are filing checks, not proof of independent review. The unchanged gate does not itself enforce body uniqueness or non-emptiness, including for files placed directly in the review directory.
- Records filed before this change are not re-checked.
