## Intent

The maintainer wants the grind status from M22.68 in the PM GUI too, in their words (2026-11-09): a live, near-real-time status window with a "last updated" time, a refresh interval and a manual refresh icon. It is a modal in the app's existing modal style, not a separate window or panel. It goes under M17 and lands before M17.9, the human-led GUI acceptance run, so that run covers it. This leaf is read-only. Decisions made from the modal are M17.15.

## Approach

**Route.** One read-only route: `GET /api/grind-status?until=<NODE>&under=<NODE>`. Both parameters are optional, as the CLI flags are. The route calls M22.68's builder in-process, the function behind `grind-session --status --json`, with the server's repo root (`get_repo_root`), and returns its JSON object unchanged. It adds no envelope and no field, so the modal and the CLI read one shape. The cases where the CLI exits 2 (no scope, unknown node) answer `400`, with the CLI's message as `detail`. The route writes nothing except the history cache under `.specyrd/cache/`, the same as the CLI. It has no POST twin. Under `specy-road gui --read-only` it is served like every GET.

**The clock.** `create_app` takes an optional `clock` (a function returning the current time) and passes its value to the builder as `now`. Production leaves it unset and gets the current time. The route-body test sets it, so the body can be compared with the builder's output byte for byte, `generated_at` and the estimate included.

**Where the route lives.** In `specy_road/gui_app.py` as it is today. This leaf does not wait for M16.3.7 (coordinator, 2026-11-09, below); whichever of the two lands second merges.

**Modal.** `StatusModal.tsx` uses `ModalFrame` (`storageKey="grind-status"`), the component behind every dialog and drawer in the app, with its title bar, close, Escape and stored size. It follows the Orchestration drawer's pattern:

- `App.tsx` loads it lazily and opens it from a **Status** toolbar button, with an `open` flag and `onClose`.
- `grindStatus.ts` holds the response types, one `loadGrindStatus(fetch, scope)` that never throws (it returns ok, unavailable on `404`, refused on `400` with the detail, or error), and the poll helper. This copies the shape of `loadOrchestration` and `pollOrchestration` in `orchestrationSnapshot.ts`. On `404` (a server from before this leaf) the text helper returns "the server does not provide the status"; on `400` it returns the server's `detail` unchanged.

The modal body shows, in the CLI's order:

1. **Scope.** Two fields, *Until* and *Under*, that take node ids. Both empty means the server's default, the milestone session. They are browser preferences per repo, using `readBrowserPref` and `writeBrowserPref` with new `BROWSER_PREF_KEYS` entries, so the goal survives a reload. A `400` shows the server's detail and asks for a goal.
2. **Header.** The totals line, and **Last updated** with the time of `generated_at` and its age ("12 s ago"). When a later load fails, the last good report stays on screen. Its age keeps growing, and the error shows beside it.
3. **Sections.** Held, active, ready, waiting, not pickable, the estimate (method, inputs, range or reason), decisions, sessions, and missing. Every text field is shown as the server sent it. The modal does not reword options or recommendations, and it shows "not recorded" and "no options recorded (not a ledger entry)" as given. Each `missing` entry is shown verbatim with the record it belongs to, so an unreadable brainstorm file or an absent recorded field is visible and not hidden behind a `200`.
4. **Scope label.** The report shows the `goal` and `scope` it returned, not the values typed in the fields.

**Refresh.**

- A **refresh icon** button (a new `IconRefresh` in `toolbarIcons.tsx`, labelled "Refresh now") loads at once and restarts the interval.
- An **interval** select: Off, 30 s, 60 s, 2 min, 5 min. The default is 60 s. The command takes seconds on `sr/` (`grind-session --plan` alone took 3.7 s), so the existing 15 s orchestration cadence would keep the server busy. The interval is a browser preference per repo, like **Auto-refresh**, not a project config key.
- Polling runs only while the modal is open (M17.1 question 5 set this rule for the orchestration drawer). A tick that comes while a load is still running is skipped, so requests never pile up.
- Changing *Until* or *Under* starts a load for the new scope at once. Only the result for the scope currently requested replaces the report: a slower response for the old scope is dropped when it arrives. A report kept on screen after a failure keeps the scope label it was returned with.

## Tier

behavioural. A read-only route over M22.68's builder and a read-only modal. It writes nothing a gate reads, and it decides nothing. The risks are drift between server and GUI, and a poll that overloads the server or shows a stale report as current. The contract row, the poll rows and the last-updated row cover them.

## Done but wrong

- The route reshapes the JSON, so the CLI and the modal disagree. Check: the route-body row compares the body with the builder's output.
- The mock drifts from the route, and the modal is built against fields the server never sends. Check: the contract row checks key paths both ways.
- The modal polls while closed, or stacks requests when the command is slow. Check: the poll row's skip case. Also check that the modal unmount clears the timer, in the poll helper's stop function.
- After a failed load, an old report looks current. Check: the last-updated row.
- After a scope change, a late answer for the old scope shows under the new scope's fields. Check: the scope-change row.
- A `200` hides an incomplete report. Check: the verbatim row's `missing` entry.
- A server from before this leaf shows a blank modal. Check: the load-results row's `404`.
- The modal builds its own dialog instead of `ModalFrame`. Check: review reads `StatusModal.tsx`.
- The modal rewrites a recommendation or invents pros and cons. Check: the verbatim row.

## If this fails

Assumption: M22.68's builder is a public function that takes the root, the scope and `now` and returns the JSON object, so the route needs no subprocess. If M22.68 landed it only behind the CLI's argument parsing, stop and name the function. The coordinator decides whether to extract it (an M22.68 zone) before this leaf calls the CLI.

## Accepted limits

- **Not real time.** The report is as fresh as the last load. The command takes seconds on a large roadmap, so the shortest interval is 30 s. **Last updated** shows the time and the age.
- **Each open modal polls.** Two browser tabs with the modal open each poll. No server cache is added.
- **The scope is per browser.** The goal fields are browser preferences, not project state. The CLI and the coordinator pass their own flags.
- **No decisions here.** The modal is read-only; decisions are M17.15.
- **The acceptance run.** M17.9's checklist needs status-modal items; the coordinator adds them when it amends M17.9's sheet.
- **The M17 parent sheet.** It still says the GUI reads only the orchestration snapshot and is read-only in 0.3.1. This leaf adds a second read path (the grind-status builder). Correcting the parent sheet is coordinator plan upkeep, not this leaf's work.
