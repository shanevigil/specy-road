## Intent

<!-- historical -->`group-nodes --into-new M16.1 M16.0 M16.1 ...` is refused with `id 'M16.1' is already taken by another node` (REHEARSAL.md step 1), although M16.1 is one of the nodes being grouped and leaves that id in the same transaction.<!-- /historical --> Every regroup into ids the flat leaves occupy then needs a temporary id and one `move-node --id` per group (8 commands became 16 in the rehearsal), and the temporary id lands in the group sheet (M22.4). After this leaf the regroup is one command per group.

Out of scope: move-node, indent and outdent (move-node --id already ignores the moved subtree), apply (M21.5 calls group-nodes and benefits), a GUI control, and B4's sheet text (M22.4).

## Approach

1. `group_nodes`: pass the listed nodes' subtree ids (`subtree_ids` from roadmap_outline_renumber) as `ignore_ids` to `check_chosen_child_id` instead of the empty set.
2. `move_nodes` / `NewParent.insert`: a second node with id NEW_ID must never exist in memory while `_apply_move` builds `by_id`. Give the new parent a transient in-memory id while the moves run (keyed by node_key, so a move naming the parent still resolves), then set NEW_ID and its subtree through `assign_subtree_ids_inplace` before staging. The transient id never reaches disk, the planning sheet path or the printed map. The new parent's sheet is planned for NEW_ID (it already is: `plan_planning_sheet_for_new_node` runs on the final node).
3. Chain safety comes from the existing staging: `_stage_planning_moves` reads every source before staging deletes, and registry/zone rewrites look each id up once in the old -> new map.
4. Verify with the M1.1 / M1.2 / M1.3 test and the GUI contract test; then by hand in a scratch worktree, <!-- historical -->`group-nodes M16.0 M16.1 ... --into-new M16.1` from REHEARSAL.md step 1<!-- /historical -->.
