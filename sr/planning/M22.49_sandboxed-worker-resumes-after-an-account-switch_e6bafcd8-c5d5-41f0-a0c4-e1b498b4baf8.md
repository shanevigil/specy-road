## Intent

A sandboxed Claude Code worker can be resumed after the dispatcher moves executors to another account. Today the resume fails at startup with "Configuration error in ~/.claude/.claude.json: JSON Parse error: Unexpected EOF", so every fix round for a worker launched on the old account fails until a coordinator starts a fresh worker.

## Approach

Observed 2026-11-08: a worker launched with one `CLAUDE_CONFIG_DIR` was resumed with another. Its state directory held a 0-byte, read-only `.claude/.claude.json` left from the first launch, and the harness read that instead of a copy of the new directory's file. The likely cause is that the per-worker copy of a seeded file in a replaced directory is kept when it already exists, even when it is the empty mount placeholder or was copied from another account's directory. Confirm the cause with a test first.

- Find where `_harness_binds` decides to reuse a per-worker copy, and make a resume under a different config directory refresh the copy from the new directory's file.
- Keep the worker's transcripts and sessions; do not clear its state directory.
- Verify with the table-driven rows in the acceptance, through the public launch path the existing sandbox tests use.

## Tasks / checklist

- [ ] A1: record the source directory beside the state; refresh the copy on a change or a missing record, placeholder included; same directory keeps the copy; user's file and transcripts untouched
- [ ] A2: three rows through worker_runner.run (row 2 parametrized over a non-empty and a zero-byte 0444 old copy); docs sentence; CHANGELOG [Unreleased] entry

## Tier

trust boundary: launch and resume of a sandboxed worker.

## Done but wrong

- The resume starts but reads the old account's configuration: row 2 checks the copy's content equals the new directory's file.
- The resume starts because the state directory was cleared, and the session is lost: A1 requires the transcripts to stay, and the test checks a transcript file written before the switch is still there.
- Only one of the two old-copy shapes is handled: row 2 runs with a non-empty old copy and with the zero-byte mode-0444 placeholder the failure left.
- The fix binds the user's file instead of copying it: row 2 checks the user's source bytes are unchanged after the harness renames its copy.

## If this fails

If the harness keeps account-specific state that cannot move between accounts, the resume cannot be made to work. Then document that a worker must be resumed on the account that launched it, and that the coordinator starts a fresh worker in the same worktree after a switch. The maintainer decides whether to take that docs-only version.

## Accepted limits

- Cursor and Codex account switches are not covered: no case has been seen.
- A human `--resume` from the user's own home still does not find a sandboxed worker's session (documented today).
- A switch onto a config directory with no `.claude.json` is unchanged: setup does not fail and does not invent a file. The home-root `~/.claude.json` seed is not selected by `CLAUDE_CONFIG_DIR` and is not refreshed.
- The tests use a fake harness, so a real Claude login and cross-account session compatibility are not established by them.
