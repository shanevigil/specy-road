## Intent

The operator's gate for the irreversible steps of the sweep. History rewrites, force-pushes, repository visibility, GitHub Support and TestPyPI deletions are operator-only; no agent runs them. 0.3.1 is not tagged until this gate is cleared. Final pass, before the 0.3.1 tag. Source: the maintainer's scrub plan (private), section 4, approved 2026-11-09.

**Agents must never run set-gate-status on this gate; only the maintainer clears it.** `set-gate-status` does not read this sheet or the `human:` line, so an agent could mark the gate Complete and unblock M16.8.9 without any of the steps below. A reviewer refuses a gate commit whose sheet lacks the records listed under Approach.

## Approach

The maintainer clears this gate (sets it Complete) after doing these steps, using M22.58's evidence and printed commands. The concrete sets:

- **Machines and worktrees:** the operator's list of machines, and on each the output of `git worktree list`. Both are recorded here before the push (as machine labels, not hostnames or paths), and only those are re-cloned. A clone that is unknown or unavailable keeps this gate open until the maintainer resolves it explicitly.
- **TestPyPI candidates:** rc1 to rc4, the four published before the rewrite.

Steps:

- **Freeze:** stop every worker and grind session on the listed machines before the push, so no session pushes old history back.
- **Guard publish:** `.github/workflows/release-publish.yml` starts on any `v*.*.*` tag push, and the `testpypi` environment has no reviewer; a push to `main` also runs `main-release-tag-gate.yml`, which can create a tag. Before updating any tag, disable that workflow or finish the TestPyPI step first. The new-repository route does not fire the old repository's workflows; the force-push route does.
- **Publish the rewrite:** run M22.58's printed branch commands (expected-old-tip leases), or move to a new repository built from the rewritten history (which drops pull-request refs and caches but loses stars, issues and the PyPI trusted-publisher binding). Update tags only after the guard above.
- **Support:** file the GitHub Support request for the pull-request refs and cached commit views; record the date.
- **TestPyPI:** decide yank or delete for each of rc1 to rc4 and carry it out; one line per candidate with the date.
- **Re-clone:** re-clone each listed machine and worktree. Keep the pre-rewrite bundles of local-only branches, refs and the stash offline. For local-only work worth keeping, transplant the changes onto the rewritten history and run the hygiene checks before restoring push access; never fetch old refs or apply the old stash wholesale. Record each machine's disposition here.

## Tasks / checklist

- [ ] Machine and worktree list recorded; workers and grind sessions frozen
- [ ] release-publish guarded (workflow disabled or TestPyPI step done) before any tag update
- [ ] Rewritten branches pushed, or the move to a new repository
- [ ] GitHub Support request filed (date)
- [ ] TestPyPI rc1 to rc4: one yank-or-delete line each, with date
- [ ] Each listed machine and worktree re-cloned; dispositions recorded
- [ ] Fresh-mirror check recorded
- [ ] Maintainer: gate cleared (date)

## Tier

none: a human gate. No agent work is dispatched or reviewed under it.

## Done but wrong

- Old history comes back: a fresh clone's heads and tags match M22.58's approved rewritten inventory, its reachable history passes the same history-wide scan, and no old commit the rewrite changed (old SHA differs from new, or removed) is reachable through those refs. Unchanged clean commits are allowed. Record the inventory and scan result before clearing the gate.
- A clone was missed: every machine and worktree on the recorded list has a disposition line, and none still has a ref at a changed old SHA.
- The gate was cleared by an agent: the status change was made by the maintainer, with the records above present.

## If this fails

Assumption: a tag push matching `v*.*.*` starts `release-publish.yml`, and `testpypi` has no required reviewer. If that workflow starts unintentionally, or the trusted-publisher binding or the release-version CI fails on the new SHAs, the gate stays Not Complete and M16.8.9 stays blocked. The maintainer disables the workflow or fixes the binding; clearing this gate is not the fix.

## Accepted limits

- Forks and copies made while the repository was public are out of reach.
- Pull-request refs and cached views stay until GitHub Support acts.
- `set-gate-status` does not check this sheet; the rule above and the reviewer's check of the gate commit are the only brakes. The 0.3.1 tag stays on M16.8.10, which this gate does not set.
