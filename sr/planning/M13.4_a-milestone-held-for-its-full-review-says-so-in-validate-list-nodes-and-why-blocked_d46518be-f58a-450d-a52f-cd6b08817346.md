## Intent

When `policy.milestone_full_review` (on by default since rc3) holds a milestone whose leaves are all Complete at In Progress, say so wherever a PM or agent looks. In the report, the only symptom was `export --check` / `digest --check` drift; validate was silent, `list-nodes` showed no reason, and the reason ("full review is not approved at …, 0/2 distinct-family approvals") was reachable only by calling `milestone_review_hold()` from Python.

## Approach

- **Source of truth.** Reuse `milestone_review_hold()` and `milestone_review_next_steps()` in `specy_road/finish_ancestor_rollup.py`; add one formatter there that returns the reason plus the three ways out: (1) run the full review (the commands `milestone_review_next_steps()` prints), (2) record the milestone Complete deliberately (`specy-road edit-node <ID> --set status=Complete` or the documented route), (3) set `policy.milestone_full_review: false` in `roadmap/orchestration.yaml`. Skip holds that start with `UNRESOLVABLE_HOLD` the same way `demote_pending_milestone_rollups()` does, but still print them as a one-line notice so they are not invisible.
- **validate.** In `specy_road/bundled_scripts/validate_roadmap.py`, after the graph loads, print one `milestone review: notice — …` line block per held milestone (non-fatal). Upgrade shows these because it runs `validate_at()`.
- **why-blocked.** In `specy_road/bundled_scripts/roadmap_query_cli.py`, `cmd_why_blocked` on a held milestone prints the same block (next to the existing `plan_hold` rendering).
- **list-nodes.** In `specy_road/bundled_scripts/roadmap_crud_ops.py`, the ROLLUP column shows `In Progress (review hold)` for a held milestone; `--json` rows gain `review_hold: <reason>` (added at the call site rather than in `registry_claim_status.list_nodes_json_row`).
- **Docs.** `docs/orchestration-review.md` "Milestone full review" shows the notice and the three ways out.
- **Verify.** Tests under `tests/` with a fixture milestone whose leaves are all Complete and no approvals: validate notice text; why-blocked text; list-nodes text and JSON field; no notice when the policy is off.

## Tasks / checklist

- [ ] A1 — validate prints one notice per held milestone with reason and three ways out; upgrade surfaces it via validate. Test pins the text.
- [ ] A2 — why-blocked prints the same; list-nodes marks the rollup and `--json` carries the reason. Tests.
- [ ] A3 — Docs updated. Out of scope: when the hold applies (including exempting milestones completed before an upgrade, which the adopter suggested; record as a follow-up if wanted) and the policy default.
