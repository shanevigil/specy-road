## Intent

The maintainer asks the coordinator the same question many times in each grind: how many leaves are left until the goal, how many are done, how many are active, when it will finish, and what the maintainer has to decide. The coordinator rebuilds the answer each time from `grind-session --plan`, `handoff status`, `decisions list`, the registry and git history. This takes many tool calls, and the result changes with how it was assembled. Maintainer request, 2026-11-09, in their words: "I'd like this to become a simple specy-road command the coordinator can call to get that information quickly and easily without recreating it on the fly every time." The maintainer put it in RC5.

## Approach

**The command.** `specy-road grind-session --status`. It is a read-only mode of the command group that runs the grind, next to `--plan`. It takes the grind's own scope flags:

- `--until <NODE>`: the goal and everything it needs.
- `--under <NODE>`: a subtree.
- With both flags, the scope is the intersection of the until-closure (below) and the `--under` subtree. This is narrower than the loop: the loop plans with `--under` only and stops after it picks `--until` (`_run_loop`), so it can also run ready leaves under `--under` that `--until` does not need. Status does not count those (accepted limits).
- With neither flag, the default is the parent named in `work/.milestone-session.yaml` (`start-milestone-session`), used as `--under`. This is the only "current goal" the product records.
- With no flag and no session file, the command exits 2 and names `--until`, `--under` and `start-milestone-session`. An unknown node exits 2 naming the id (`no node M99`).

It adds no top-level command and no persistent state. It adds one optional config key, the watch interval below. `--status --json` prints one JSON object. `--status` cannot be combined with `--plan` or `--step`, the same way `--step` already refuses `--plan` (`_reject_step_conflicts`).

**What "until" counts.** `--until G` scopes the leaves G needs before it can close:

- Seed the scope with G's own leaves (G itself when G is a leaf).
- For every node added that is not Complete, add its effective dependencies (`RoadmapIndex.effective_dependencies`, which includes the dependencies inherited from ancestors). A dependency that is a group adds its leaves, and each of those leaves is expanded the same way. So a leaf L inside goal group P that depends on an outside X brings X in, even though P itself does not name X.
- A dependency that is already Complete (`RoadmapIndex.status`, the rollup, not a group's own status field) adds its leaves as done, and its own dependencies are not followed. Without that stop, every leaf ever finished would count toward every goal.
- Leaves are deduplicated by `node_key`.

For a leaf goal such as the RC5 end-to-end pass M16.8.4, the scope is everything that has to land before that pass.

**Gates are not leaves here.** Gate nodes (`is_gate`) are never counted in a bucket or a total, as `_classify` already skips them. An open gate appears only as the reason and the next step of the leaves it holds.

**Buckets.** The command does not classify leaves again. It loads the same git-enriched plan as `grind-session --plan` (`gather_session_plan(root, None)`) and keeps the non-gate leaves in scope. The plan alone does not give one bucket per leaf, so the command applies these rules, first match wins, and every non-gate leaf in scope is in exactly one bucket:

| Bucket | Rule |
|---|---|
| done | own status Complete |
| cancelled | own status Cancelled; never counted as remaining |
| held | waits on a person: an open gate among its unmet dependencies, whether or not the leaf is claimed (`plan.gated` holds only the unclaimed ones, because `_classify` puts a claimed or In Progress leaf in `active` before its gate test; a claimed one is still held, next step `set-gate-status <GATE>`); or claimed with review state `escalated`, `fix_round_budget_spent` or `executor_blocked`, a policy change since the claim (`GateResult.policy_pin`), or a live worker whose lease holder is `human` or which carries the `needs_person` flag. Live means `worker_state.active_for_node`: not `failed` or `terminated`; `completed` still counts |
| active | claimed or In Progress and not held; shows the review state from `review_state` (`waiting`, `in-review`, `stale`, `blocked`, `approved`) and the live worker (id, harness, state) when there is one. A leaf in `plan.finished_claimed` stays here, and its line says the feature tip is Complete and the integration branch has not merged it |
| ready | `plan.ready`: what pickup would claim now |
| waiting | `plan.blocked` with reason `dependency`, listing `waiting_on` |
| finished, awaiting merge | each leaf in `plan.finished_unmerged` (unclaimed, Complete on `feature/rm-<codename>`, which `enrich_session_plan_with_git` removes from `ready` and puts in no other bucket), with the reason "Complete on its feature branch; the integration branch has not merged it". It is not done and it counts in remaining (its own bucket: maintainer, 2026-11-10) |
| not pickable | `plan.unauthored` and `plan.needs_codename`, each with its reason |

remaining = total − done − cancelled.

The review state of each claimed leaf in scope comes from one function. The leaf extracts it from `handoff status`'s `_node_status` (`review_cli.py`) as a public `review_state(root, node_id)`. It covers the gate, READY, loop escalation, the fix-round budget and the policy pin, and it leaves out the trial merge, reviewer eligibility, runs and rounds: `review_state` does not call `trial_merge`, which `_node_status` adds only on the `handoff status` path. `handoff status` calls it too, so the state names keep one definition and `handoff status`'s output and exit codes do not change. The command evaluates only claimed leaves in scope, and never the all-nodes sweep: on `sr/` (358 review directories) that sweep ran for more than 8 minutes before it was stopped.

**Estimate.** The estimate is computed from history the project already has, `history_index` (the git-derived cache under `.specyrd/cache/` that `specy-road history` uses):

- **Input.** For each done leaf in scope, the earliest event with kind `status` and `to` Complete. Events are matched by the leaf's current `node_key`, not its display id: an event's `id` is the id at that commit, and ids are reused (`history_index.resolve_node_key` exists for that reason). A completion recorded before a renumber of that `node_key` still counts; a different node that now holds the old id does not. The event's time is its `at` field, the commit's author date (`%aI`).
- **Not enough data.** With fewer than 5 such completions, or less than 24 hours between the first and the last, the estimate is "not enough data", and the output gives the count and the minimum.
- **Overall rate.** (n − 1) / (last − first).
- **Recent rate.** The completions in the 7 days before now, divided by 7 days.
- **Range.** `earliest` and `latest` are ISO 8601 datetimes with offset: now plus remaining divided by the faster rate, and now plus remaining divided by the slower rate. When the recent rate is zero, `latest` is the string "none at the recent pace (no completions in 7 days)" and `earliest` is now plus remaining divided by the overall rate.

The output states the method, n, the first and last completion, the recent count, the window and the minimum. It also says the assumption: held and waiting leaves clear at the past pace. `now` is a parameter, so tests pin the clock.

**Decisions.** The command lists what waits on a person, from the records only, and does not write its own pros, cons or recommendations:

1. Open `decision` and `human-action` entries in the merged ledger (`decisions_local.load_merged`), in scope first. For each entry it prints the node, summary, `why_now`, the options with their effects, the recommendation and its reason, the default if unanswered, needed-by, and the ledger (shared or local). Open entries on nodes outside the scope follow as one line each (id, node, summary). Pros and cons are printed as "not recorded: the decisions schema has no field for them" (the schema addition goes to M23).
2. Each held leaf, with its reason and the next step the existing record names: the escalation trigger and its RCA command; the budget step (`fix_round_budget`'s `next`, a ready-made `decisions add` when no agent command would succeed); the executor's `blocked_on` lines; the policy change and `specy-road review accept-policy <ID>`; the open gate and `specy-road set-gate-status <GATE> --status Complete`; the worker lease or flag and `specy-road worker reclaim` or `worker status`. These are not ledger entries, so they have no options or recommendation. The output says "no options recorded (not a ledger entry)" and does not make any up.

**Sessions.** The status lists the planning and brainstorming work in progress, from the records that exist. It ignores the goal scope, because these sessions belong to the project, not to one goal:

- **Open brainstorm sessions:** `brainstorm_session.list_slugs` and `read_session`, the `work/brainstorm-*.yaml` files that `brainstorm close` has not moved to `work/brainstorm-closed/`. Each shows slug, mode and idea count, as `brainstorm sessions` prints them. An unreadable file is named under `missing` and does not hide the others.
- **Live presence sessions:** `session_presence.list_sessions(root, live_only=True)`, as `session list` reads them. Each shows agent, branch, note, expiry and `stale_reason()`.
- **No planner marker.** A presence record has no role field (`Session` holds agent, branch, worktree, paths, times, user and an optional `note`), and nothing else marks a session as a planner. The status therefore does not pick out planners. It lists every live presence session with its note. The docs tell a planner to start with `specy-road session start --note 'planner: <topic>'`, so the note shows what it is. A `role` field on the presence record goes to M23.

**Output.** The text output gives, in order: a header (goal, scope rule, totals line, `last updated <local time>`, and the source line `as of <branch> @ <short HEAD>, this checkout, not fetched`), held, active, ready, waiting (`waiting_on` per leaf), not pickable, the estimate, the decisions, and the sessions. The JSON object has these keys: `generated_at` (ISO 8601 with offset), `source` (`branch`, the checked-out branch or null when HEAD is detached; `head`, the full HEAD sha; `fetched`, always false), `goal`, `scope`, `totals`, `held`, `active`, `ready`, `waiting`, `not_pickable`, `estimate` (`method`, `inputs`, `earliest`, `latest`, `reason`), `decisions` (`ledger`, `ledger_outside_scope`, `held`), `sessions` (`brainstorm`, `presence`), and `missing` (every field a record lacks, named per record). M17.14's route serves this object unchanged.

**Interval report.** A CLI cannot post to an agent's chat on its own. The interval report is therefore two parts:

1. **Watch mode.** `grind-session --status --watch [MINUTES]` prints the report, sleeps, and prints it again until Ctrl+C, which exits 0. Each report starts with its `last updated` line, after a separator line. The interval is MINUTES when given. Otherwise it is the new optional key `grind_session_status_interval_minutes` in `roadmap/git-workflow.yaml`, read with `load_git_workflow_config` like the other `grind_session_*` keys (`grind_session_limits.py`). Otherwise it is 30. The interval must be a positive integer; anything else exits 2. With `--json`, each report is one JSON object on one line. The sleep and the clock are parameters, so tests run the loop without waiting.
2. **Coordinator instructions.** The bundled coordinator skill (`specyrd-orchestrate.md`) and the grind skill (`specyrd-grind-session.md`) say: during a grind, run `specy-road grind-session --status` with the grind's scope at the start and then every `grind_session_status_interval_minutes` (default 30), and post its text output to the chat unchanged. Where the harness has a scheduler or wake-up, use it for the interval. Where it has none, run the status at the first turn after the interval has passed. The text names no harness's scheduler. The coordinator does not use `--watch` for this: a chat agent cannot read a process that never ends. `--watch` is for a person's terminal. Wiring a scheduler is left to the adopter.

No existing key fits the interval. The `grind_session_*` keys are limit-wait bounds, the roster `policy` section holds review and worker policy, and nothing in the product runs on a clock today (searched for interval, poll, check-in, heartbeat and schedule; the only intervals are the GUI's polling and the registry overlay's fetch throttle, which is an environment variable). The key joins the `grind_session_*` group in `git-workflow.yaml`, its schema and the template's commented list. The maintainer asked for the interval in project config.

**Dependencies and overlaps.** M16.2.5 comes first, so the new package module imports library code from its new home. Three Not Started leaves share files with this one and have no edge to it:

- M16.4.3 (the `handoff status` rename) lists `review_cli.py`, `cli_usage.py`, `docs/`, `specy_road/templates/specyrd/` and `CHANGELOG.md`.
- M17.6 (snapshot schema 2) lists `review_cli.py`.
- M16.2.9 (commands in the CLI's process) lists `cli_usage.py` and all of `specy_road/bundled_scripts/`.

This leaf does not depend on them: waiting for M16.4.3 would make this leaf rewrite every `handoff status` reference. The proposed order is that M16.4.3 and M17.6 come after this leaf and call `review_state`, which needs `05b23f6c-3e4d-4ac9-b0a0-022b4fe7f7f1` added to their dependencies. Those edges are on other nodes, so this revision does not add them; the maintainer or coordinator decides (revision notes). Until an order is set, pickup's zone check stops a second leaf that overlaps one already claimed (accepted limits).

## Tier

behavioural. This is a new read-only reporting mode, a watch loop around it, one optional config key read only by it, and skill text. It records nothing, closes no gate and changes no state a gate reads. The change to `review_cli.py` is an extraction. The handoff status tests and parity rows pin `handoff status`'s output and exit codes, and `review_gate.py` is not touched.

## Done but wrong

- The closure walks through Complete dependencies, so a late goal counts every leaf ever finished. Check: the until-closure row keeps D out of scope.
- A leaf lands in two buckets or in none, held leaves are also counted as active, a gate is counted as a leaf, or a leaf that is Complete only on its feature branch is counted as done or dropped. Check: the buckets row asserts each non-gate leaf appears once, the gates are not counted, and the totals add up.
- A done leaf is found by its display id, so a renumber drops or misattributes a completion. Check: the renumbered row.
- The until walk expands only the goal's own dependencies and misses a dependency of a leaf inside a goal group. Check: the group-goal row.
- The command makes up a recommendation or pros and cons. Check: the ledger row asserts the printed options and recommendation are the ledger's text, word for word, and that held items print "no options recorded".
- The estimate gives dates on two completions. Check: the not-enough-data row.
- Status is slow because it runs the `handoff status` sweep or the trial merge. Check: `review_state` takes only the claimed leaves in scope (the buckets row's review directory outside scope is never read), and it runs no trial merge (the held-review row's conflicting leaf). Report the wall time on `sr/` for `--until M16.8.4` in READY (informational).
- Status fetches or writes. Check: the read-only row's upload-pack sentinel, which a fetch whose error is ignored would still trip.
- The `handoff status` text changes. Check: the handoff-unchanged row.
- The status guesses which session is a planner, or hides sessions it cannot classify. Check: the sessions row prints the note word for word and lists every live session.
- The watch loop really sleeps in tests, or its interval ignores the key. Check: the watch row asserts the seconds handed to the fake sleep for the flag, the key and the default.
- The skill tells the coordinator to run `--watch` in the chat, or names one harness's scheduler as the only way. Check: the skill-text row, and review reads the paragraph.

## If this fails

Assumption 1: the classification in `gather_session_plan(root, None)`, filtered to the scope, is the same as the scoped plan's for every bucket. `compute_session_plan` classifies each leaf without looking at the scope; only `gates_open` reads it, and this leaf does not use `gates_open`. With the bucket rules above (gates excluded, claimed gated leaves held, `finished_unmerged` waiting), every non-gate leaf in scope has a bucket. If a scoped non-gate leaf still matches no rule (for example `_classify`'s "deps met but not pickable" skip), that is this assumption failing.

Assumption 2: `review_state` can be extracted from `_node_status` without changing `handoff status`'s output.

If either fails, stop. Name the bucket, or the field that would change. The coordinator decides before `session_plan.py` or the gate is touched.

## Accepted limits

- **Stale history.** The estimate counts completions on this checkout's first-parent history. A leaf finished on another clone and not yet pulled is not counted. `history_index` may write its cache under `.specyrd/cache/`, as `specy-road history` already does. That is the only write.
- **No idle time.** The estimate does not model idle time or parallel width. It is a range from two observed rates, with the method printed.
- **Default goal.** The only default goal is a milestone session. The toolkit's own grind passes `--until` (for RC5, `--until M16.8.4`).
- **The loop is wider than status.** The grind loop plans `--under` only and stops after it picks `--until`, so it can still run ready leaves under `--under` that `--until` does not depend on. Status does not count those.
- **Overlapping Not Started leaves.** M16.4.3, M17.6 and M16.2.9 share files with this leaf and have no edge to it. Until the maintainer or coordinator sets an order, pickup's zone check stops whichever of them is picked second.
- **Planner sessions are not marked.** Nothing records a session's role. The status lists every live presence session with its note, and a planner is recognisable only if it followed the `--note 'planner: …'` convention. A `role` field is an M23 item.
- **The chat report depends on the coordinator.** The product prints the report; posting it on the interval is the coordinator following its skill. A harness with no scheduler posts at the first turn after the interval, not on the minute.
- **One more config key.** `grind_session_status_interval_minutes` is new; no key is retired for it.
- **The GUI status modal and PM decisions** are M17.14 and M17.15. This leaf fixes the JSON they read.
- **Pros and cons.** These stay unrecorded until the M23 schema item. This deferral is the maintainer-accepted choice of this plan: the status says "not recorded" for each entry rather than inventing them.
