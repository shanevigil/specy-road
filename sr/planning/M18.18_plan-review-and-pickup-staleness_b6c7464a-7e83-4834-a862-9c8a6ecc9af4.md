## Intent

Today specy-road reviews code after implementation. Nothing reviews a leaf's plan before an executor starts: the only spec review is the optional single-pass `review-node` (and the PM GUI's LLM Review), which is advisory and runs in the planner's own context. This leaf adds a **plan review in two stages**, built on `review delegate`, with the review itself **layered into configurable lenses** (maintainer decision, 2026-11-05):

- **(a) Full plan review right after planning.** After adding leaves or editing acceptance, zones, dependencies or a sheet, the planner explicitly runs `review delegate` in plan mode with the leaf ids (or a milestone id for the alignment lens). Fresh reviewers from distinct families critique them through the routed lenses. Findings are recorded and the planner answers them. Policy can require a current, answered plan review before the leaf is pickable.
- **(b) A light check just before pickup.** Deterministic, no model: has the leaf's plan changed since its plan review; did a dependency land changes to files in its zones; do its zones still match tracked files; are findings unanswered. In advisory mode every condition warns. In required mode only a missing or stale review or an unanswered finding makes the leaf not pickable; the dependency and zone conditions always just warn.

**Out of scope:** automatic plan review from `add-node`, `edit-node`, batch commits or git hooks; any LLM call by the toolkit outside the rostered reviewer launch; marking lenses required (a later M20 posture may do that); operability and performance lenses (the format must allow adding them later, but none ship now); changes to `review-node`.

## Layered lenses

| Layer | Lens | Scope | Rows (summary) |
|---|---|---|---|
| 1 | `item` | every leaf | each acceptance line paraphrased and checkable yes/no; contradictions between lines or with the sheet; zones cover every file the acceptance and approach change; no open-ended detection rule; scope bounded and stated; dependencies right (missing, unnecessary, cycles including through group-node dependencies) |
| 2 | `alignment` | once per milestone or batch plan, over the **set** | fit with the project's constitution, principles and constraints; each leaf belongs to the milestone theme; scope creep and duplicates anywhere in the roadmap; does the set deliver the milestone purpose (gaps, ordering, droppable leaves); coherence across leaves |
| 3 | `security` | routed by trigger | trust boundaries: launch/resume, guards, review records and gate, roster/policy, finish/land, steering files, secrets; attacker-controllable code run before a decision; fail-closed refusals; safe defaults; regression test |
| 3 | `testability` | every leaf (default on, cheap) | each line testable at the cheapest level; tests specified concretely and table-driven; deterministic; change observable through a public interface |
| 3 | `gui-api` | routed by trigger | PM GUI server, outline/CRUD, node ids: response shapes kept, one shared implementation, GUI paths not left behind, npm gate when `gui/pm-gantt` changes |

- Lens checklists ship as **data** (one file per lens under `specy_road/orchestration/plan_lenses/`, added to `[tool.setuptools.package-data]` in `pyproject.toml` so wheels carry them), not code; `policy.plan_review.lenses` lets a project replace a lens's rows or add a lens of its own.
- `policy.plan_review.routing` maps each layer-3 lens to zone globs and title/acceptance keywords. Built-in routing: `item` and `testability` always; `security` on zones such as launch, guards, `review_*`, roster, policy, `finish_*`, steering files; `gui-api` on `gui_app_*`, `roadmap_outline_*`, roadmap CRUD. `alignment` is never routed per leaf; it runs once when plan mode is given a milestone id or a batch of leaf ids.
- Every finding carries a `lens` tag (and a row id), so answers, records and later posture rules can be read per lens.
- Seed the built-in checklists from the coordinator's hand-run lenses: `sr/work/orchestrator-2026-11-04/lenses/{item,alignment,security,testability,gui-api}.md`.

## Approach

- Evidence (coordinator, `sr/work/coordinator-rough-edges.md`):
  - Under-specified acceptance produced review loops in which each round found a new input class (M9.7 encodings, M8.1 YAML layouts).
  - A design term that contradicted an acceptance line (M11.4: `--offline` against "a global limit") looped reviewers for many rounds. The same pattern recurred on rc4 leaves.
  - Touch zones missed files that acceptance named, so executors stopped for zones on most M10/M11 leaves (M10.4, M10.5, M10.9, M10.13, M11.4, M11.8, M11.13), a coordinator round trip each.
- Evidence that the lensed hand-run review pays off (2026-11-05, `sr/work/plan-reviews/`):
  - `m16-full/`: the full M16 plan review returned 125 findings before any executor started.
  - It caught defects in M21.14 and M21.15, and `rc4-steering/` caught M21.7's: the planned check ran `git status`, which would have executed a changed `core.fsmonitor` before reporting it. That was a security-shaped finding, the reason security is its own routed lens rather than a row of `item`.
- **Stage (a) is already run by hand.** From 2026-11-05 the coordinator runs a fresh distinct-family lensed plan review on its own newly planned leaves; this leaf makes that a supported mode with a record and a policy.
- Source of the pattern: `sr/docs/research/elephant-goldfish-2026-11-05.md` (section 4, item 1). Borrow the "paraphrase first" comprehension test and resolving each finding explicitly. Do not depend on EGM or vendor its prompts.
- Reuse, no new entrypoint: plan mode of `review delegate` reuses the roster pick, distinct families, fresh bare sessions, run lock and transcript. It does **not** call the code-review filing (`file_review`, `write_schema`, `final_answer`); `review_record_write.py` and `review_answer.py` stay unchanged.
- **Plan records are separate from code-review records** (resolves Sol high / Grok high in `sr/work/plan-reviews/m18-m20-batch-1/`): plan packets, run logs, reviewer records and answers use plan-prefixed names (`PLAN-REVIEW-<model>.md` etc.) under `work/reviews/<ID>/` (alignment records under the milestone id), validate against a new plan-review schema in `specy_road/schemas/`, never count toward code-review approval and never overwrite code-review artifacts. Plan review works before any claim or READY exists.
- Packet: the requested leaves, their ancestor context and effective dependencies; reviewers may read code and docs those inputs cite. Unrelated leaves are out of scope (alignment additionally reads the milestone sheet and the governing docs).
- Fingerprint, written by the filing command (never by the reviewer): SHA-256 of canonical JSON of ordered acceptance, touch_zones and dependencies plus the planning sheet's UTF-8 content, together with the integration commit it was read at.
- Planner answers: one disposition per finding id on the plan record, `amended` or `not a defect because <reason>` (nonempty). An amendment changes the fingerprint, so required mode needs a new review at the amended plan.
- **Required vs stage (b)** (resolves the contradiction both reviewers flagged): stage (b) evaluates four conditions. Advisory: all four warn and pickup proceeds. Required: no plan record at the current fingerprint, or an unanswered finding, excludes the leaf from selection; the dependency-landed and unmatched-zone conditions warn in every mode and never refuse. Dependency-landed rule: a dependency that was not Complete at review time is Complete now and `git diff --name-only <stored commit>..<current integration commit>` intersects the leaf's zones (existing zone matcher); if either commit is unavailable, warn that the check is undetermined.
- Integration point: pickup filtering and warnings go in `specy_road/bundled_scripts/do_next_task.py` (M16.3.2 folds `do_next_task_leaf_guards.py` into it).
- Related items, not duplicated here: `review-node` (stays as is); M18.12 and M18.13 (deterministic plan-time checks; this leaf is the reader test beside them); batch H item H1.4 "stale brief after pickup" (M16.1.3 sheet): stage (b) covers edits up to pickup, H1.4 after it; M20 may later mark lenses required.
- Depends on M16.5.12 (review fold) and M16.5.3 (roster and role prompts move into `specy_road/orchestration/`). Re-check zones before pickup. The phase starts after the 0.3.1 tag gate.
