## Intent

A field run with sibling repositories not set in `nested_repos` could not get an approval to count. `review delegate --worktree` ran the reviewer in the leaf, but the record stored the main checkout's sibling heads. `heads_problem` then needs an exact match with every sibling clean, so unrelated dirt in other repositories staled the record and the answer depended on where it was asked. Mechanism read here: `_review_record_signed_data` stamps from `root`, and the gate evaluates `sibling_repos(repo_root)`.

## Approach

Stamp sibling heads from the checkout the reviewer ran in. Limit `heads_problem` to siblings the leaf's touch zones name; a leaf that names none has nothing to go stale. Evaluate the same set from either checkout. This narrows a staleness check, so keep it strict for named siblings and say so in docs. Fix the `review list` wording and the block count at the same time.

- [ ] Record heads from the reviewed checkout

## Tier

trust boundary: it narrows which sibling changes make a filed review stale, which decides whether an approval counts.

## Done but wrong

- A named sibling slips through because of how a zone names it: a zone naming a file inside the sibling (not only its root) makes that sibling named, and its moved head makes the record stale.
- The answer still depends on where it is asked: the same record gives the same gate result from the main checkout and from the leaf worktree when the siblings seen from each place differ in head or dirt.

## If this fails

Most likely to break: sibling repositories resolve to the same places from the main checkout and from a linked worktree (they are found relative to the checkout). If they do not, one record cannot give one answer from both. The maintainer decides which root sibling paths resolve from.

## Accepted limits

- A leaf whose zones name no sibling repository is not made stale by any sibling change.
