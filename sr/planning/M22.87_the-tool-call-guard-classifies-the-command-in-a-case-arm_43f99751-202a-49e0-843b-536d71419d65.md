## Intent

A second guard gap found on 2026-11-20 while tracing M22.86's cause, and a different one. `$X` and `sudo $X` are refused because the command name comes from a shell expansion, but inside a case arm, `case a in a) $X;; esac`, the same command is allowed: the pattern word `a)` is not treated as opening a command, so unwrapping stops at `case` and the arm's command is never classified. A literal `case a in a) git stash;; esac` is still refused. Maintainer 2026-11-20: "pairs ok, case gap gates final": this leaf gates the 0.3.1 tag, not RC5.

## Approach

- Not ready for pickup. A planner first names the function and the arm forms (see the second acceptance criterion) and replaces this section; the plan and the trust-tier zone then go to the maintainer.
- Expected shape: the guard classifies each arm's command list as it does a command after `;`, reusing the existing segment handling rather than adding a case parser.
- Out of scope: other compound commands (for, while, select, function bodies) unless the planner shows the same cause reaches them; the rule-table rewrite is M23.8.

## Tier

trust: it changes the guard that refuses destructive commands.

## Done but wrong

- The arm's command is classified but the pattern list is read as a command and ordinary case statements are refused: each refused row has an allowed row beside it.
- Only the single-arm `;;` form is handled: the rows draw every form the planner lists.

## If this fails

If classifying arms needs a real shell parser, stop and report; do not add one in this leaf.

## Accepted limits

- The check draws the forms the planner lists. It is not a claim about every compound command.
