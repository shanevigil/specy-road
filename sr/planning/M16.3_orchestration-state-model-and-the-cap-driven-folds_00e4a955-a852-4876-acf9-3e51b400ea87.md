## Intent

Give orchestration its single public interface and state model (the 0.3.2 GUI's read path). Then fold the cap-driven splits that sit on the way to the surface work: pickup and finish, nested-repo landing, the LLM client, brainstorm and the managed-block engine, the misc single-importer siblings, and the PM UI server and CRUD splits (last, after the snapshot is fixed).

## Approach

Leaves run in id order, which is chain order: every leaf's prerequisites have a smaller id, and no edge points to a later group. There are no group-level dependencies; the leaf edges give the order.

Why together: These are the chain's folds, headed by the interface they read (M16.3.2's chain predecessor is M16.3.1, kept per the Grok G9 rejection). M17.1, the GUI placeholder, depends on exactly M16.3.1 and M16.3.7, so the GUI prerequisite is one group.
