## Intent

rc4 fix (maintainer decision 2026-11-05: steering-file protection is an rc4 fix), filed in M16's fix intake as a dependency of gate M16.66. specy-road runs unattended executors in linked git worktrees, and some files they can write are later read or run by trusted code outside the executor: the coordinator's harness, git, the coordinator's shell, the toolkit's own gate. Today nothing notices a change to them. The post-run check (worker_turn_check.py) compares HEAD, branch, stash and porcelain only, and finish checks that work landed inside the zones, not what it touched outside them.

Evidence:

- sr/docs/research/agent-safety-posture-2026-11-05-claude-research.md, Executive summary item 3 "Protect the steering files" and Disagreements item 2 ("the toolkit is itself in the attack path"). It describes the CVE class where an agent writes a file that trusted code later runs: harness settings and hooks, git hooks and `core.fsmonitor` / `core.hooksPath`, shell startup files, virtualenv interpreters, and symlinks the unsandboxed parent follows.
- The 2026-11-04 context-regression replay (docs/design-notes/context-regressions-2026-11-04-triage.md, CR1 / cursor; docs/orchestration-review.md "What the gate cannot stop"). An executor added itself to `roadmap/orchestration.yaml` on the integration branch and approved its own work. Another called the toolkit's record writer from `python -c`. A third drove the human menu with `expect`.

Found in the code (2026-11-05):

- In a linked worktree, `.git/hooks` and `.git/config` are the common git dir's. An executor that writes them changes the coordinator checkout's git.
- `env_setup.link` (worktree_env.py) symlinks `.venv`, `.conda` and `node_modules` from the main checkout into the worktree. A write through `.venv/bin/python` changes the coordinator's interpreter.
- Claude Code executors in `launch_mode: full` load the worktree's project `.claude/settings.json`, hooks included, on the next turn.
- Codex runs `workspace-write` with `approval_policy=never`. Cursor runs `--force`.
- The only existing protection: Cursor's built-in write block on `.cursor/*.json`, `.vscode/**` and `.git/hooks/**` (maintainer, harness behavior). It is not written down anywhere in the repo yet.

## Approach

- **One list** in a new `specy_road/steering_paths.py`, documented in docs/orchestration-workers.md. For each worker it snapshots, in the worktree and in the main checkout:
  - harness config and hooks: `.claude/settings*.json`, `.claude/hooks/**`, `.codex/**`, `.cursor/*.json`, `.cursor/hooks/**`;
  - git steering, read from the filesystem only (no git command): the hooks directory (`core.hooksPath` when set, else `<common-git-dir>/hooks` and `<worktree-gitdir>/hooks`) as sorted direct regular-file names with sha256, non-recursive, or the marker `capped` past 200 direct children; and the bytes of the common `config` and `config.worktree`. A `git_config` finding reports the file digests plus the changed values of `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `include.path` and `includeIf.*.path`;
  - the toolkit's policy and record inputs: `roadmap/orchestration.yaml`, `roadmap/orchestration.local.yaml` and `roadmap/git-workflow.yaml` in the tree and as the blob at the local integration branch tip (no fetch), so a roster commit made from another checkout shows; `roadmap/registry.yaml` `entries` items whose `node_id` is another leaf; every file under `work/reviews/` except the leaf's own READY;
  - shell and env: root shell startup files (`.bashrc`, `.bash_profile`, `.profile`, `.zshrc`, `.zshenv`, `.envrc`); for each `env_setup.link` target, its `bin/` entry names, types, link text and resolved regular-file sha256 (a write through an unchanged `.venv/bin/python` link changes the digest, not the link);
  - symlinks: a porcelain entry in either checkout, new or retargeted during the turn, whose target resolves outside the worker's git root. No directory walk; gitignored paths and links created then removed within one turn are outside detection scope, and the docs say so.
  Paths compare project-relative the way `zone_matches` does, and one real path is stored once.
- **After each turn, ordering matters:** `close_turn` compares the git-steering snapshot first. On a change it records the finding and marks the post-turn git probes skipped, so `git status` never runs under a changed `core.fsmonitor` or hooks. Otherwise it runs the existing git probes, then compares the rest. Each change is one `steering_file` finding (`path`, `class`, `before`, `after`) that replaces any porcelain or `committed_outside_zones` finding for the same path. The sticky `steering_changed` worker flag shows in `worker status --json` `flags` and `handoff status --json` `workers[].flags` (text handoff status is unchanged; review_cli.py stays out of zones). A clean turn leaves it set; `worker reconcile <id>` without `--dismiss` prints one `path class before after` line per `steering_file` finding recorded while it was set, then clears it.
- **At finish:** `finish-this-task` refuses before its bookkeeping commit when the branch diff changes an in-tree steering path, unless a touch zone names that exact path. `roadmap/registry.yaml` is ignored there. The message names the path and the next step.
- **At launch, where cheap:** Claude Code launch and resume deny `Edit(./<rel>)` and `Write(./<rel>)` per exact file (each in-tree steering file present at launch, plus `.claude/settings.json`, `.claude/settings.local.json` and the three roadmap policy files), skipping exact touch-zone paths. No parent glob, so no rule can match an exempt file. New files, shell writes, the common git dir and the main checkout stay detection-only (relative rules resolve inside the worktree only). Cursor's existing block and what Codex `workspace-write` already refuses are written down, not duplicated. Custom `channels.cli` commands keep their argv and get detection only.
- **Out of scope:** OS-level isolation, signing, the M20 posture model and doctor probes, and restoring a changed file. This leaf detects and refuses.
