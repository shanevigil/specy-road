## Intent

Final harness re-test, 2026-11-06. A Cursor composer-2.5 reviewer filed 2 of 5 reviews. Two failures were parse failures: "the final message does not end with a JSON object", caused by a fenced object or prose after it. These get no repair turn, because M21.35 repairs only a `review record` refusal; a parse rerun is explicitly excluded (tests/test_review_delegate_repair.py:72, case `no-json`).

This leaf extends M21.35's repair path to every rerun request `final_answer` or `file_review` makes about the answer itself: an empty final message, no object, a fenced object or trailing text, an unfinished object, nesting too deep, a stray or cut-off event line, a final turn with no final message or no end event, a null result, or an object that fails the output schema. It feeds back the reason, with the same one-repair limit and the RUN record fields plus one discriminator.

Decisions:

- **Which runs get the repair turn.** Only a run whose last attempt exited 0 with no capacity reason, and whose answer turned into a `Rerun`. These keep today's behavior and get no repair turn: a capacity failure, a harness non-zero exit, an unreadable run log (`UNREADABLE_ANSWER`, an I/O error rather than the reviewer's answer), a review failure (a write) and a chore reviewer. `file_review`'s write check still runs before the repair decision, so an unparseable answer that also wrote a file is a `review_failure` with no second launch.
- **RUN fields.** `run["refusal"]` holds the reason, `run["refusal_kind"]` is `parse` or `record`, and the repair attempts are marked `repair: true`. RUN files have no schema, so no schema file changes. `--resume` on an incomplete run with a stored reason sends the repair pair (M21.35's rule) built for the stored kind; a record with no `refusal_kind` (written before this leaf) is a `record` refusal.
- **One repair per run.** A repair turn that fails again, whether by parse or by refusal, leaves the run incomplete, exit 1, with both reasons. There is never a third turn. This holds after a resume too: a resumed parse repair that fails again names both the stored and the new reason.
- **Repair section wording.** `repair_prompt` takes the reason's source. A parse reason is introduced as specy-road's reading of the final message, not `review record`'s output, then says: send the whole JSON object as the final message, no fence, nothing after it. The notes rules stay only for refusals.
- **Planned test change.** `test_no_repair_turn_unless_review_record_refused` loses its `no-json` case. That case moves to the repair table, and the test is renamed for the remaining cases.

Overlaps: M21.38 edits `_prompt_file` in the same file and depends on this leaf. M22.16 (rc5) changes the summary line and capacity reason later.

## Approach

- `review_delegate._delegate_locked`:
  - The repair condition becomes "a refusal, or a parse rerun from a clean last attempt".
  - `_repair` takes the reason text and its kind; the run records both.
  - `_start` returns the stored kind with the stored reason on `--resume`; the resume branch joins both reasons for a parse failure as it already does for `filed.refusal`.
- `Outcome`: the `Rerun` from `file_review` carries its reason in a field `_repair` can read, or `_file` returns the `Rerun` reason. Either is fine; keep `Outcome.refusal` for refusals.
- `review_record_write.repair_prompt(reason, kind)`: the fence logic is unchanged.
