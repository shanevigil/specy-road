## Intent

Two PM GUI Publish defects from the rc4 sandbox rehearsal (part C).

- High. GUI edits change the graph but not `roadmap.md` or `roadmap-context.md`. Publish (`POST /api/publish` → pm_publish.publish_roadmap) commits and pushes the stale files. The pushed commit fails `export --check` and `digest --check` (sandbox: ed18196, exit 1 for both), so a PM publishing from the GUI breaks CI.
- Medium. With no remote configured, Publish commits locally first (8abd659). The push then fails, and the API returns 502 with git's raw `fatal: No configured push destination…`. The result is a half-done local commit.

Decision: regenerate at Publish, not on every GUI edit. Publish is the GUI's only commit path, and the drift checks are a contract on what is committed. Regenerating on each `PATCH`/outline call would render the digest (which reads git history for "Quality by area") on every autosave, and would touch both generated files for edits a PM may still undo. The GUI archive routes already regenerate because archive is a commit-shaped operation; they are unchanged.

Out of scope: regenerating on GUI edits (above); a branch with a remote but no upstream (today's "No upstream branch configured" message after commit); push rejection handling; the frontend (the modal already shows `blocked` + `detail`); acceptance-criteria editing and grouping in the outline UI (sandbox finding, recorded as an open question on M17.1).

Overlaps checked (2026-11-05): M21.17 adds the symlink guard inside `regenerate_generated_files`, which this leaf calls without editing it. M17 leaves edit the GUI frontend and orchestration API, not pm_publish.py.

## Approach

- `publish_roadmap`: after the existing message and branch checks, and before staging:
  1. Refuse when no remote is configured: `git remote` lists nothing, or the push remote named by the branch config / `remote.pushDefault` does not exist. Raise `ValueError` (HTTP 400) with "No git remote is configured, so Publish cannot push. Add one (git remote add origin <url>), push the branch once with -u, then publish again." Nothing is staged or committed.
  2. Regenerate both generated files from the project root with `generated_files.regenerate_generated_files(root)`. A graph that does not load or validate raises `ValueError` (400) naming the error, before anything is staged.
  3. Recompute `scope_changed_files`, which now includes the regenerated files (both are in `PUBLISH_PATHSPECS`), then stage, commit and push as today.
- `classify_publish_status`: a new `blocked_reason` value `no_remote`, with `detail` carrying the same message, so `GET /api/publish/status` shows the refusal before the button is pressed. Response keys and types are unchanged; `blocked_reason` is already a free string in gui/pm-gantt/src/types.ts.
- Contract tests in tests/test_pm_publish.py, on a real git repo with a bare remote. After a graph edit that changes a title, publish returns 200 with the same keys as today, and the pushed commit's `export --check` and `digest --check` exit 0 (run against a clone or worktree at the pushed commit). With no remote: `/api/publish/status` reports `blocked: true`, `blocked_reason: "no_remote"`; `POST /api/publish` returns 400 with the message; `git rev-parse HEAD` and the index are unchanged. Existing publish tests pass unchanged.
- docs/pm-gui.md: one sentence that Publish regenerates both files before committing, and refuses without a remote.
