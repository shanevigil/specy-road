## Intent

Approvals are lost to commits that change no code under review. Today `only_planning_or_review_bookkeeping_since` keeps an approval only across the leaf's own sheet, its implementation summary and its review files, and never across a merge. A coordinator edit to another node in a phase chunk, a registry row, or a merge from the integration branch that leaves the leaf's code diff unchanged sends both families back to review, which spends the leaf's fix rounds. The maintainer approved a wider carry on 2026-11-09. Source: the governance compatibility plan, section D.

## Approach

Extend the bookkeeping carry in `review_bookkeeping.py`, in two steps.

All paths are project-relative, after the existing project-prefix rebase: in this repo the roadmap is `sr/roadmap/` and the sheets are `sr/planning/`, so a git-root glob would never fire here.

- **Paths:** a commit that touches only `roadmap/**` (except `roadmap/orchestration.yaml` and `roadmap/git-workflow.yaml`, which `review_packet.py` already treats as policy a reviewer must see), `planning/**`, `roadmap.md`, `roadmap-context.md`, this leaf's implementation summary and its review directory keeps the approval.
- **Merges:** for a two-parent merge M with first parent P and second parent I on the policy-resolved integration history, compare the non-bookkeeping full-index diffs `merge-base(P,I)..P` and `I..M` with the same diff options and exclusions. Carry only if they are byte-identical. Other merge shapes, unrelated merges and failed git queries do not qualify. No trial merge.

In both cases, the carry is refused when the leaf's own `acceptance` or `touch_zones` changed (resolved by `node_key` across chunk moves), or when the parsed tier value under its sheet's `## Tier` heading changed. The value sits on the line after the heading, so comparing the heading line alone would miss plain to trust boundary. A sheet with no tier value is not eligible. Every other range keeps today's rule.

**Scope against other leaves:** depends on M22.51 (both edit `docs/orchestration-review.md`). Only `only_planning_or_review_bookkeeping_since` widens, and only for review records: M22.51's operator decisions keep today's predicate, so a decision never survives a policy commit. M23.1 edits `count_at_later_commit`'s sibling-head logic in the same file; this leaf leaves that function alone, and whichever lands second merges with the first.

## Tier

trust boundary: review bookkeeping decides which approvals count.

## Done but wrong

- The leaf's own acceptance changes and the approval still carries: a commit that edits only this leaf's acceptance in its phase chunk refuses the carry, while the same commit editing another node's acceptance keeps it.
- A merge brings in code under review: an integration merge that changes a file in the leaf's diff refuses the carry, even when the leaf's branch did not edit that file after the merge.
- The tier changes silently: a commit that changes only the value under the sheet's `## Tier` heading refuses the carry.
- A policy edit rides along: a commit of only `roadmap/orchestration.yaml` is under `roadmap/**` and looks like bookkeeping, but refuses the carry.

## If this fails

Assumption: "the leaf's non-bookkeeping diff against its merge base" can be computed from git alone, before and after the merge, without a trial merge. If it cannot, stop and record the case; the coordinator decides before the merge carry is dropped or widened.

## Accepted limits

- A merge that changes the merge base but leaves the leaf's diff byte-identical carries, even if the integration code it now sits on changed. The integration branch's own reviews and the land check cover that code.
- Other nodes' acceptance and zones are bookkeeping for this leaf.
- Trust-boundary leaves get the same carry; the refusals above are what protect them.
- A `roadmap/decisions.yaml` commit carries: it is under `roadmap/**` and is not a policy file, and an M22.51 decision is bound to its full commit and read on its own terms.
- The merge test proves diff equivalence, not semantic compatibility with every upstream change.
- `TRIAL_MERGE_BOOKKEEPING` and the packet's bookkeeping marks are unchanged.
