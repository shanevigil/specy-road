## Intent

M16 keeps every old name and config form for one release so adopters can move; this leaf ends that window.

- Split from M16.8.1 in revision 1 and held by the M16.8.2 gate (Sol 22); exit code 2 with a one-line pointer (Grok 17); policy removal stays out (Sol 13). Revision 2: also removes the version-1 roster form (M16.5.5, M16.5.6); runs before the 0.3.1 final tag (option A), then M16.8.4 runs the end-to-end pass; the list to delete is M16.8.1's.

- Behaviour-preserving: the parity harness (M16.1.1) and the review-gate decision table (M16.1.2) stay green; no function rises above its merge-base complexity; docstrings and comments that explain intent are kept or improved, never cut to save lines.

## Tier

behavioural: removing fallbacks and dual-read paths can change what an adopter's existing config does, and the goldens only show command-surface changes.

## Done but wrong

- A config that still carries an old form loses its check silently. Check: validate on a repo whose git-workflow.yaml still sets `verify_cmd`, and on one with a version-1 roster, fails and names the key or form.
- A shipped template or skill still names a removed command. Check: after `init project` and `specyrd init` into a temp directory, a search of the generated files for each removed name in REPLACED_COMMANDS finds nothing.

## If this fails

The assumption most likely to break is that the current-form readers already compute every default the fallback paths supplied. If the parity harness differs for a current-form config, the default moves into the current reader. The coordinator decides; if keeping a form past the window is needed, the maintainer decides.
