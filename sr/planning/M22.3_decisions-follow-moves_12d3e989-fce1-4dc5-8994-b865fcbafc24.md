## Intent

decisions.yaml entries name their node by display id <!-- historical -->(`node: M16.69`)<!-- /historical -->. A move leaves them naming the old id, which then names nothing or another node, and validate never checks them <!-- historical -->(REHEARSAL.md B3: D8 still said M16.69 after the move to M16.8.7)<!-- /historical -->. After this leaf a move rewrites the ledger's node fields in the same transaction as the registry claims, and validate notices an open entry whose node is gone.

Out of scope: the untracked decisions.local.yaml, switching the ledger to node_key (a schema change; rewriting keeps the file readable and the shape stable), free text in summary, why_now or answer, closed entries and expired preferences in the validate check, and M19.14, M19.15 and M19.18 (ledger features, not this defect).

## Approach

1. In `stage_id_rewrite`, beside `_stage_registry_ids`, add `_stage_decision_ids(plan, root, renamed)`: only when `renamed` is non-empty and the tracked ledger exists, read it with `read_decisions` (yaml.safe_load) and check it against the existing decisions schema (`schema_errors`) before looking at any entry; a parse error, a non-mapping root or schema errors raise `ValueError` naming the ledger, so the CLI exits 1 and the GUI handlers (which catch ValueError) answer 400, before anything is staged. Then replace `node` where it is a key of `renamed` (one lookup per entry) and stage the text only when something changed. Keep the YAML dump style `write_decisions` uses.
2. validate: one stdout notice built from `open_questions` (open decision and human-action) and `active_preferences` (decisions.py), listing an entry only when its `node` is a non-empty string that is not a live id; keep the check a helper in decisions.py so `run_validation` (validate_roadmap_checks.py) only calls it. An unreadable or schema-invalid ledger adds nothing here (validate has no ledger check today; this leaf does not add one).
3. Verify with the tests, then on a scratch worktree: move M21.15 and check D8.
