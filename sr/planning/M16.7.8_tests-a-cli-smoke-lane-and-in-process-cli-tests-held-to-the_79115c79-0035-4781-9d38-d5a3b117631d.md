## Intent

464 tests spawn the CLI as a subprocess (32% of CPU in the slimming report), and in-process dispatch (M16.2.9) removes the reason. The purpose of this leaf is a suite that is better at catching regressions, measured by the measures the maintainer chooses; it is not a speed target (maintainer, 2026-11-05, decision 5d).

## Approach

- Decision 5d (maintainer, 2026-11-05): suite speed is the wrong goal; tests target coverage and effectiveness at catching regressions (or other standard measures of what unit tests are for). Revision 1's "median of three runs at most half the M16.1.7 baseline" line is removed. Suite time is recorded for information only and is never an acceptance threshold, a review finding or a CI failure.
- A1 gates the leaf. The maintainer chooses the effectiveness measures (for example a coverage floor, a mutation score on named core modules, regression-catch evidence) from the research item `sr/research/agentic-unit-testing.md` and records them below as `A1: <measures, thresholds, modules, who and when>`. The coordinator does not dispatch this leaf until that line is committed; finish refuses the leaf without it.
- Why the smoke-lane and in-process lines (A2, A3) stay: they serve effectiveness, not speed. In-process tests run under coverage.py and mutation tools directly, while subprocess CLI tests need a sitecustomize hook and lose attribution when a test builds its own environment (02-tests.md section 0); per-test coverage contexts (M16.1.7's `--contexts`) and any mutation run then see the code each test exercises. A bounded smoke lane keeps every console entry point and the exit-code contract tested end to end. If the A1 decision names measures that this structure does not serve, the planner revises A2-A5 before dispatch.
- A5 compares each chosen measure at the leaf's merge base and head with the same settings, so the leaf needs no new baseline from M16.1.7.
- Revision 1: counts items that start the CLI, not git or worker children (Grok 11, Sol 17, Sol 18); its half-the-baseline time gate is withdrawn by decision 5d.
- Depends on: M16.7.7. The last acceptance line is an informational line-change estimate, not a gate; report `scripts/lean_metrics.py --check` deltas in READY once M16.1.7 has landed.
- Behaviour-preserving: the parity harness (M16.1.1) and the review-gate decision table (M16.1.2) stay green; no function rises above its merge-base complexity; docstrings and comments that explain intent are kept or improved, never cut to save lines.

## If this fails

The assumption most likely to break is that the A1 measures can be compared at merge base and head on the same settings within reasonable time (a mutation run can be slow or noisy). If they cannot, record the timings and the spread. The maintainer decides the settings or the measure.
