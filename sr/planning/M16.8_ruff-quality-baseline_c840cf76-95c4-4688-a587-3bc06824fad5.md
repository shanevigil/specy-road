## Intent

The toolkit's cap went from 400 to 1,000 lines on 2026-11-05. Lines over 100 characters went from 78 to 3,068 because width was the way around the old cap; the width rule closes that before the folds start. The consumer template still says 400. Revision 3 (maintainer, 2026-11-05): M16's goal is code quality, so the same shrink-only mechanism also records ruff's quality rule families per file, so existing findings are known and may only fall.

## Approach

- Do not touch project.version.
- Revision 1: the baseline counts long lines per file instead of listing files, so a listed file cannot gain more (Sol 19); the decision is an acceptance line (Grok 16). Revision 2: the maintainer decided 1,000 lines with a 750 warning, the toolkit's own values; upgrade only reports the new default and never rewrites a project's file.
- Revision 3: the rule families C901, PL (pylint-style), B (bugbear), SIM, RET, N (naming) and D102/D103 (docstrings on public methods and functions) are selected only by the baseline script, so today's `ruff check` gate does not start failing; the baseline holds per-file, per-family counts. Ruff is the only tool: mypy, radon and duplication detectors are out of scope (M19.1 lets a project declare its own). Lowering an entry is written with `--shrink`; the fold leaves lower the width entries of files they merge as before.
- Depends on: M16.2. The last acceptance line is an informational line-change estimate, not a gate; report `scripts/lean_metrics.py --check` deltas in READY once M16.2 has landed.
- Behaviour-preserving: the parity harness (M16.0) and the review-gate decision table (M16.1) stay green; no function rises above its merge-base complexity; docstrings and comments that explain intent are kept or improved, never cut to save lines.
