## Intent

The maintainer, 2026-11-09: "the PM should be able to make decisions in the status window. Any active coordinator should detect those decisions and process them as a 'PM GUI' operator decision." M17.14's status modal is read-only. This leaf adds the decision path behind it as its own trust-boundary leaf, so the read-only modal does not wait on it. It lands before M17.9, so the acceptance run covers it.

## Approach

**What the PM can decide.** Two kinds, both already in the product:

1. **Answer an open ledger question.** An open `decision` or `human-action` entry that the status lists. The PM picks one of its recorded options, or *Other*, and types the reason.
2. **Approve a leaf over a reviewer's block.** This is M22.67's option, and it is offered under M22.67's rule. The leaf is claimed, its gate has counted blocks, and settling them would pass the gate (`as_if_decided(gate).passed`). M22.68's status gains `commit` and `can_approve_over_block` on each claimed leaf it evaluates, so the modal knows when to offer it.

Other held items (a policy pin, an open gate, a worker lease) keep their own commands and get no GUI action.

**The record: the existing ledger path, no new kind.**

- **An answer** closes the entry through `decisions.close_entry(..., ledger_only=True)`, the existing close for a caller that keeps its own trail. The entry gets `decided_by: operator`, the new `channel: pm-gui`, and the answer `<option label>: <the PM's words>` (or only the words for *Other*). The planning-sheet line that `decisions close` asks for is the coordinator's processing step (below).
- **An approval over a block** is the same record M22.67 writes: one closed `kind: decision` entry from `append_decision`, with `decided_by: operator`, the answer naming the full commit, each block with its findings, any shortfall, and the PM's words as the quote. The `OPERATOR-<commit>.yaml` marker has session `pm-gui <UTC time>`. The only addition is `channel: pm-gui` on the entry.
- **Shared ledger entries go through M22.67's commit.** For both kinds, the entry is committed on the integration branch from a detached temporary worktree (`in_temp_worktree`). With a remote, it is pushed fast-forward only. With none, the ref is moved by compare-and-swap (`move_ref`). This is M22.67's integration commit and push, so every coordinator sees the decision after a pull. An entry in the gitignored `decisions.local.yaml` is closed in place, as `decisions close` does for it.
- **Sharing M22.67's steps.** The preflight and the record step (`_over_block_preflight` and `_record_over_block` in `mark_implementation_reviewed.py`) move to public functions in `review_override.py`. They take the root, the session text and the channel as parameters instead of the module's `ROOT`. Two steps stay with the CLI: the leaf-checkout clean-tree check and the registry commit, because the GUI runs in the coordinator's checkout, not the leaf's. Everything else is the same code: the role check, git identity, the fetch and re-evaluation, the holder check and `as_if_decided`. `mark-implementation-reviewed` calls the shared functions, and its output, exit codes and tests do not change.
- **The schema gains one field.** `channel` is optional, with `enum: ["pm-gui"]`. It is allowed only on closed `decision` and `human-action` entries. No existing field fits:
  - `decided_by` says who decided, not where;
  - the marker's `session` is gitignored;
  - `answer` is free text.
  Adopters run `specy-road refresh-schemas`. A copied schema from before the field refuses the write with that instruction, as M22.67's path already does for `decided_by`.

**The route.** `POST /api/pm-decisions`, with the JSON body:

- `{"kind": "answer", "id", "option", "words"}`, or
- `{"kind": "approve-over-block", "node_id", "commit", "words"}`.

The route refuses before writing anything:

- `403` under `--read-only` (the existing guard).
- `403` when the decision code (below) is missing or wrong.
- `400` when `words` is empty after stripping, the option is not one of the entry's labels, or the entry is not an open `decision` or `human-action`.
- `409` when the leaf's commit under review is not the `commit` the modal showed, so a PM never approves a commit they did not see. Also `409` when the entry has closed since the report was loaded.
- `400` with the reason when the shared preflight withholds the approval: role, identity, a failed fetch, a dirty holder, or "settling the block(s) would not pass the gate".

On success the route returns the entry id, the integration commit and where it went (`origin/<branch>` or local).

**Forgery mitigation.** The GUI is a local server, so any local process can call it.

- **What exists today** (checked): the GUI has no local auth at all. It has the loopback-only CORS regex in `create_app` (it stops other web pages from reading responses), the `--read-only` guard, and `require_pm_gui_write_header`. That last one is an outline-fingerprint concurrency check, not auth: anyone can `GET` the fingerprint. This leaf reuses the read-only guard and the CORS rule, and does not use the fingerprint check (it would refuse a decision whenever the outline changed).
- **A per-session decision code.** When the server starts (FastAPI startup, not module import), `gui_app` draws `secrets.token_urlsafe(16)` and keeps it in memory on `app.state`. It prints it once to the server's stderr, which `specy-road gui` leaves on the terminal of the person who started it: "PM decisions: enter this code in the Status window to confirm a decision: <code> (kept in memory only; it changes each time the GUI starts)". The code is never written to a file, an environment variable, a log line or an API response. Under `--read-only`, no code is made and nothing is printed. `create_app` takes an optional `decision_code` argument for tests.
- **The browser side.** The modal asks for the code once per page load and keeps it in React state only, not in `localStorage` or `sessionStorage`. It sends the code as the `X-PM-Decision-Code` header, and the server compares it with `secrets.compare_digest`. A custom header also forces a CORS preflight, and the loopback rule refuses that preflight for any other origin.
- **An explicit confirm.** The form needs a typed reason. The PM clicks **Review decision**, which shows the exact text that will be recorded (entry or leaf, commit, option, words), then **Record decision**. Nothing is sent before the second click. The server's own checks are the non-empty `words`, the code and the commit match.
- **The channel is recorded.** `channel: pm-gui` on the entry and the `pm-gui` session on the marker let GUI decisions be audited apart from the others: `decisions list --json` shows the field.

**Status and the coordinator.**

- M22.68's builder gains `decisions.gui_pending`, shown as **Decided in the GUI, not yet processed** in the CLI text and in M17.14's modal. Each item is a closed entry with `channel: pm-gui` that the coordinator has not acted on yet, judged from records that already exist:
  - **An approval over a block** (the entry is named by an `OPERATOR-*` marker) is pending while the leaf's registry `implementation_review` is not `approved`. Next step: `specy-road mark-implementation-reviewed --yes` on `<branch>` (the recorded decision lets it pass, per M22.67), then finish.
  - **An answer** is pending while the node's planning sheet has no `<ID>: <answer>` line in its decision block (`recorded_on_sheet`). Next step: add that line under `## Decisions and notes`, commit it, then act on the answer.
  - No acknowledgement field and no new state.
- The bundled coordinator skill (`specyrd-orchestrate.md`) says:
  - before each status check, pull the integration branch fast-forward only, because the GUI pushes there;
  - on each status check, process every "decided in the GUI" item as an operator decision, with the PM's words as the operator's;
  - say each one in the chat as it is processed: "Processing PM GUI decision <id> on <node>: <words>". The person then sees every GUI decision in the chat, including one they did not make.

Plan review applies the gui-api and trust lenses before pickup.

## Tier

trust boundary. A local HTTP route writes operator decisions that settle counted reviewer blocks, and it commits and pushes to the integration branch. A forged call has the same effect as the PM's. `sr/tools/tier.py`'s path floor also raises it (`review_override.py`).

## Done but wrong

- The GUI writes a new kind of record, or a decision the gate reads differently from M22.67's. Check: the over-block row asserts the same entry and marker as M22.67's rows, plus the channel.
- A call without the code, from another origin, or from a read-only server records something. Check: the code, cross-origin and read-only rows.
- The code leaks to a file, a log, an environment variable or a GET response, where an agent reading the repo or logs would find it. Check: the code-secrecy row.
- The PM approves a commit they were not shown. Check: the stale-commit refusal.
- A refusal comes after a write. Check: every refusal row asserts nothing recorded, and the push-refused row asserts no marker.
- The GUI stamps the registry in the coordinator's checkout, or skips the coordinator. Check: the over-block row asserts the registry is unchanged, and the pending row shows the coordinator's step.
- A processed decision stays listed, or an unprocessed one drops out. Check: the pending row.
- Moving M22.67's steps changes `mark-implementation-reviewed`. Check: the CLI-unchanged row.

## If this fails

Assumption 1: M22.67's preflight and record steps can run with a root and a feature branch passed in, from the coordinator's checkout and not the leaf's, and give the same gate result. The gate is evaluated on the leaf's branch by name, as `handoff status` does from any checkout.

Assumption 2: `decided_by: operator` on an answered question is ignored by the gate, because the gate honours a decision only through a marker.

If either fails, stop and name the function or the gate rule. The coordinator decides before `review_gate.py` is touched.

## Accepted limits

- **Best effort against a local agent.** The code keeps out other web pages, scripts that do not have it, and calls by mistake. It does not stop an agent that runs as the same user and can:
  - read the terminal where the GUI started (scrollback, a terminal multiplexer's capture);
  - read the server's memory;
  - drive the browser;
  - start its own GUI and read that GUI's code.
  Such an agent can already run `review operator-decision` or `decisions close` itself (M22.51's accepted limit), so the GUI adds no power it lacked. Two things make a forgery visible, not impossible: the recorded channel and recorder identity, and the coordinator's chat line for every GUI decision.
- **An agent that starts the GUI sees the code.** The code is shown to whoever started the server. The docs say: start the GUI yourself, in your own terminal.
- **Retyped after a reload.** The code lives in page memory only, so a reload asks for it again.
- **Seen after a pull.** With a remote, the decision lands on the remote integration branch. The status command does not fetch, so a coordinator sees it after its next pull, which the skill makes part of each status check.
- **Two kinds only.** Policy pins, gates and worker leases keep their CLI commands.
- **One more schema field.** Adopters refresh their copied schemas, and the refusal names the command.
- **Protected integration branch.** If direct pushes to it are refused, the approval path is unavailable, as in M22.67. The refusal names `review operator-decision`.
