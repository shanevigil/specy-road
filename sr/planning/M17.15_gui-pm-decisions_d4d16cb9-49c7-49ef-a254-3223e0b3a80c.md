## Intent

The maintainer, 2026-11-09: "the PM should be able to make decisions in the status window. Any active coordinator should detect those decisions and process them as a 'PM GUI' operator decision." M17.14's status modal is read-only. This leaf adds the decision path behind it as its own trust-boundary leaf, so the read-only modal does not wait on it. It lands before M17.9, so the acceptance run covers it.

## Approach

**What the PM can decide.** Two kinds, both already in the product:

1. **Answer an open ledger question.** An open `decision` or `human-action` entry that the status lists. The PM picks one of its recorded option labels, or the explicit *Other* choice, and types the reason. *Other* is not a label: it records the words alone.
2. **Approve a leaf over a reviewer's block.** This is M22.67's option, and it is offered under M22.67's rule. The leaf is claimed, its gate has counted blocks, and settling them would pass the gate (`as_if_decided(gate).passed`). M22.68's status gains three fields on each claimed leaf it evaluates, so the modal knows when to offer it and what it would settle:
   - `commit`: the gate's commit;
   - `can_approve_over_block`: true or false;
   - `settles`: the strings the decision would name, in `append_decision`'s order: one `block_item` per counted block (reviewer, commit, findings, from `blocks_to_settle`) and the `shortfall_text` when approvals are short.

**Older servers.** The three claimed-leaf fields and `decisions.gui_pending` are optional for GUI readers. With no `can_approve_over_block`, the modal offers no approval. With no `gui_pending`, it shows no pending section. The GET body stays the builder's output; there is no second response shape for the GUI.

Other held items (a policy pin, an open gate, a worker lease) keep their own commands and get no GUI action.

**The record: the existing ledger path, no new kind.**

- **An answer** closes the entry through `decisions.close_entry(..., ledger_only=True)`, the existing close for a caller that keeps its own trail. The entry gets `decided_by: operator`, the new `channel: pm-gui`, and the answer `<option label>: <the PM's words>` (or only the words for *Other*). The planning-sheet line that `decisions close` asks for is the coordinator's processing step (below).
- **An approval over a block** is the same record M22.67 writes: one closed `kind: decision` entry from `append_decision`, with `decided_by: operator`, the answer naming the full commit, each block with its findings, any shortfall, and the PM's words as the quote. The `OPERATOR-<commit>.yaml` marker has session `pm-gui <UTC time>`. The only addition is `channel: pm-gui` on the entry.
- **Shared ledger entries go through M22.67's commit.** For both kinds, the entry is committed on the integration branch from a detached temporary worktree (`in_temp_worktree`). `close_entry` and `append_decision` run against that worktree's root only, never the server's checkout, so the server checkout stays clean and its `decisions.yaml` unchanged. With a remote, the commit is pushed fast-forward only. With none, the ref is moved by compare-and-swap (`move_ref`). This is M22.67's integration commit and push, so every coordinator sees the entry after a pull. An entry in the gitignored `decisions.local.yaml` is closed in place, as `decisions close` does for it; that is the one write to the server's checkout.
- **An approval works in the server's clone only.** The gate honours an operator decision only through the `OPERATOR-<commit>.yaml` marker (`apply_operator_decisions` reads no ledger without one). The marker lives in `work/reviews/`, which is gitignored and shared by the main worktree and its linked worktrees (`reviews_root`), not by other clones. A pull carries the ledger entry to another clone but not the marker, so the approval does not settle the block there. This leaf states that limit and does not move the marker (accepted limits; the maintainer decision is in the revision notes). Answers have no marker and work in every clone.
- **Sharing M22.67's steps.** The preflight and the record step (`_over_block_preflight` and `_record_over_block` in `mark_implementation_reviewed.py`) move to public functions in `review_override.py`. They take the root, the session text and the channel as parameters instead of the module's `ROOT`. M16.2.9 removes that same module-global `ROOT` and also edits `mark_implementation_reviewed.py`, so this leaf depends on M16.2.9 and lands after it; the shared functions take `root` from the caller, the shape M16.2.9 already requires. Two steps stay with the CLI: the leaf-checkout clean-tree check and the registry commit, because the GUI runs in the coordinator's checkout, not the leaf's. Everything else is the same code: the role check, git identity, the fetch and re-evaluation, the holder check and `as_if_decided`. `mark-implementation-reviewed` calls the shared functions, and its output, exit codes and tests do not change.
- **The schema gains one field.** `channel` is optional, with `enum: ["pm-gui"]`. It is allowed only on closed `decision` and `human-action` entries. No existing field fits:
  - `decided_by` says who decided, not where;
  - the marker's `session` is gitignored;
  - `answer` is free text.
  Adopters run `specy-road refresh-schemas`. A copied schema from before the field makes `write_decisions` raise `ValueError`. `append_decision`'s caller in M22.67 already adds "run `specy-road refresh-schemas`" to that error; `close_entry`'s path does not, so the route adds it for both kinds (below).

**The route.** `POST /api/pm-decisions`, with the JSON body:

- `{"kind": "answer", "id", "option", "words"}`, where `option` is one of the entry's labels or `null` for *Other*; or
- `{"kind": "approve-over-block", "node_id", "commit", "settles", "words"}`, where `commit` and `settles` are the values the modal showed.

The route refuses before writing anything:

- `403` under `--read-only` (the existing guard).
- `403` when the decision code (below) is missing or wrong.
- `400` when `words` is empty after stripping, `option` is neither a label of the entry nor `null`, the id is unknown, or the entry is not a `decision` or `human-action`.
- `409` when the entry has closed since the report was loaded.
- `409` when the leaf's commit under review is not the `commit` the modal showed, so a PM never approves a commit they did not see.
- `409` when the re-evaluated settlement set is not the `settles` the modal showed (for example, a second reviewer blocked the same commit after the preview), so a PM never settles a block they did not see.
- `400` with the reason when the shared preflight withholds the approval: role, identity, a failed fetch, a dirty holder, or "settling the block(s) would not pass the gate".

**Errors from the shared code.** `close_entry` raises `SystemExit` for a missing id, a closed entry or a missing sheet line; `_record_over_block` raises `SystemExit` after a refused push and after a gate that still fails; `write_decisions` raises `ValueError` for a schema refusal. The route catches `SystemExit` and `ValueError` from these calls, and the server process stays up:

- A schema `ValueError` becomes `400` naming `specy-road refresh-schemas`; nothing is recorded.
- A refused push or a failed commit becomes `400` with the git error; nothing is recorded and no marker is written.
- **Recorded, but the gate is still not met.** When the integration commit has landed and the marker is written, but the re-evaluated gate is not passed, the route returns `200` with the entry id, the commit, where it went, `gate_met: false`, and the CLI's sentence that the registry was not stamped. It leaves the marker and does not roll the commit back. `as_if_decided` in the preflight usually prevents this case.

**Success.** A shared entry returns `{"id", "integration_commit", "destination": "origin/<branch>" or "local <branch>", "gate_met"}` (`gate_met` only for an approval). A `decisions.local.yaml` answer returns `{"id", "integration_commit": null, "destination": "local ledger"}`.

**Forgery mitigation.** The GUI is a local server, so any local process can call it.

- **What exists today** (checked): the GUI has no local auth at all. It has the loopback-only CORS regex in `create_app` (it stops other web pages from reading responses), the `--read-only` guard, and `require_pm_gui_write_header`. That last one is an outline-fingerprint concurrency check, not auth: anyone can `GET` the fingerprint. This leaf reuses the read-only guard and the CORS rule, and does not use the fingerprint check (it would refuse a decision whenever the outline changed).
- **A per-session decision code.** When the server starts (FastAPI startup, not module import), `gui_app` draws `secrets.token_urlsafe(16)` and keeps it in memory on `app.state`. It prints it once to the server's stderr, which `specy-road gui` leaves on the terminal of the person who started it: "PM decisions: enter this code in the Status window to confirm a decision: <code> (kept in memory only; it changes each time the GUI starts)". The code is never written to a file, an environment variable, a log line or an API response. Under `--read-only`, no code is made and nothing is printed. `create_app` takes an optional `decision_code` argument for tests.
- **The browser side.** The modal asks for the code once per page load and keeps it in React state only, not in `localStorage` or `sessionStorage`. It sends the code as the `X-PM-Decision-Code` header, and the server compares it with `secrets.compare_digest`. A custom header also forces a CORS preflight, and the loopback rule refuses that preflight for any other origin.
- **An explicit confirm.** The form needs a typed reason. The PM clicks **Review decision**, which shows what will be recorded: for an answer, the entry, the option (or *Other*) and the words; for an approval, the leaf, the commit, every `settles` line (each counted block with its findings, and the shortfall) and the words. Then **Record decision**. Nothing is sent before the second click. The preview is not the full answer text, because the server adds its recorder identity; it is every part the PM chooses or settles. The server's own checks are the non-empty `words`, the code, and the commit and settlement-set matches.
- **The channel is recorded.** `channel: pm-gui` on the entry and the `pm-gui` session on the marker let GUI decisions be audited apart from the others: `decisions list --json` shows the field.

**Status and the coordinator.**

- M22.68's builder gains `decisions.gui_pending`, shown as **Decided in the GUI, not yet processed** in the CLI text and in M17.14's modal. Each item is a closed entry with `channel: pm-gui` that the coordinator has not acted on yet, judged from records that already exist. Every read is a local git ref or file; nothing is fetched.
  - **An approval over a block** is an entry whose answer has the operator-decision form (`Accepted by operator decision (approve) for commit <sha>,`), whether or not this clone has its marker. It is pending while the registry on the leaf's own branch (`read_registry_at_ref` at `feature/rm-<codename>`) does not have `implementation_review: approved`. The leaf branch is the tree `mark-implementation-reviewed --yes` commits to, so the item drops out as soon as that runs in the leaf's worktree, before the leaf lands. Next step, when this clone has the `OPERATOR-<sha>.yaml` marker: `specy-road mark-implementation-reviewed --yes` on `<branch>` (the recorded decision lets it pass, per M22.67), then finish. When it does not: "this clone has no marker for this decision; process it from the clone that ran the GUI" (accepted limits).
  - **An answer** is pending while the planning sheet at the local integration branch ref has no `<ID>: <answer>` line in its decision block (`recorded_on_sheet` on that text). A line that exists only on a leaf branch, or only in the working tree, does not clear it. Next step: commit that line under `## Decisions and notes` on the integration branch, then act on the answer.
  - No acknowledgement field and no new state.
- The bundled coordinator skill (`specyrd-orchestrate.md`) says:
  - before each status check, pull the integration branch fast-forward only, because the GUI pushes there;
  - on each status check, process every "decided in the GUI" item as an operator decision, with the PM's words as the operator's;
  - say each one in the chat as it is processed: "Processing PM GUI decision <id> on <node>: <words>". The person then sees every GUI decision in the chat, including one they did not make.

Plan review applies the gui-api and trust lenses before pickup.

## Tier

trust boundary. A local HTTP route writes operator decisions that settle counted reviewer blocks, and it commits and pushes to the integration branch. A forged call has the same effect as the PM's. `sr/tools/tier.py`'s path floor also raises it (`review_override.py`).

## Done but wrong

- The GUI writes a new kind of record, or a decision the gate reads differently from M22.67's. Check: the over-block row asserts the same entry and marker as M22.67's rows, plus the channel.
- A call without the code, from another origin, or from a read-only server records something. Check: the code, cross-origin and read-only rows.
- The code leaks to a file, a log, an environment variable or a GET response, where an agent reading the repo or logs would find it. Check: the code-secrecy row.
- The PM approves a commit they were not shown, or settles a block they were not shown. Check: the stale-commit and stale-settles refusals.
- A refusal comes after a write. Check: every refusal row asserts nothing recorded, and the push-refused row asserts no marker.
- The GUI writes into the server's checkout and leaves it dirty. Check: the answer and over-block rows' clean `git status`.
- A shared-code `SystemExit` kills the request, or a landed decision is reported as "nothing recorded". Check: the push-refused, old-schema and gate-still-unmet rows.
- A pending item clears or stays depending on which tree the status reads. Check: the pending row's leaf-branch-only line and leaf-worktree approval.
- The GUI stamps the registry in the coordinator's checkout, or skips the coordinator. Check: the over-block row asserts the registry is unchanged, and the pending row shows the coordinator's step.
- A processed decision stays listed, or an unprocessed one drops out. Check: the pending row.
- Moving M22.67's steps changes `mark-implementation-reviewed`. Check: the CLI-unchanged row.

## If this fails

Assumption 1: M22.67's preflight and record steps can run with a root and a feature branch passed in, from the coordinator's checkout and not the leaf's, and give the same gate result. The gate is evaluated on the leaf's branch by name, as `handoff status` does from any checkout.

Assumption 2: `decided_by: operator` on an answered question is ignored by the gate, because the gate honours a decision only through a marker.

If either fails, stop and name the function or the gate rule. The coordinator decides before `review_gate.py` is touched.

## Accepted limits

- **Best effort against a local agent.** The code keeps out other web pages, scripts that do not have it, and calls by mistake. It does not stop an agent that runs as the same user and can:
  - read the terminal where the GUI started (scrollback, a terminal multiplexer's capture);
  - read the server's memory;
  - drive the browser;
  - start its own GUI and read that GUI's code.
  Such an agent can already run `review operator-decision` or `decisions close` itself (M22.51's accepted limit), so the GUI adds no power it lacked. Two things make a forgery visible, not impossible: the recorded channel and recorder identity, and the coordinator's chat line for every GUI decision.
- **An agent that starts the GUI sees the code.** The code is shown to whoever started the server. The docs say: start the GUI yourself, in your own terminal.
- **Retyped after a reload.** The code lives in page memory only, so a reload asks for it again.
- **Seen after a pull.** With a remote, the decision lands on the remote integration branch. The status command does not fetch, so a coordinator sees it after its next pull, which the skill makes part of each status check.
- **An approval is usable only in the GUI's clone.** The approval's ledger entry reaches every clone with a pull, but the `OPERATOR-<commit>.yaml` marker the gate needs is gitignored and stays in the clone that ran the GUI (and its linked worktrees). A coordinator in another clone sees the approval listed with the step "process it from the clone that ran the GUI"; its gate there still counts the block. Answers carry no marker and are usable in every clone. Moving the approval across clones is a maintainer decision (revision notes).
- **Two kinds only.** Policy pins, gates and worker leases keep their CLI commands.
- **One more schema field.** Adopters refresh their copied schemas, and the refusal names the command.
- **Protected integration branch.** If direct pushes to it are refused, the approval path is unavailable, as in M22.67. The refusal names `review operator-decision`.
