## Intent

A grind leaf gets one or two fix rounds. Today a fix after a block needs a full review from both families again: `evaluate_gate` drops the other family's approval in `count_at_later_commit` unless the range holds only this leaf's sheet, summary and review files. A code fix therefore resets the approval the other family already gave, and each round costs two full reviews. The maintainer approved a fix-check on 2026-11-09: the blocking reviewer checks only its own findings against the fix, and the other family's approval carries. Source: the governance compatibility plan, section D.

## Approach

The executor names the block it answers with `specy-road ready --fix-of <reviewer>@<commit>`, which writes a schema-valid `fix_of` field to READY (`handoff.schema.json` rejects unknown keys, and `ready` rewrites READY from a fixed dict, so a hand-written key would not survive). The gate counts the other family's approval at that commit at the one fix commit only when the named record is the round's only block, the fix commit's sole parent is that commit, every changed path is in the leaf's zones as they were at that commit, and the integration-branch sheet explicitly parses as plain or behavioural. The carry sits beside `count_at_later_commit` in `review_gate.py`; `review_bookkeeping.py` (also edited by M22.53 and M23.1), `delta_problem`, `DELTA_MAX_FILES` and `delta_from` are unchanged. Only the bookkeeping-only restriction is relaxed: `policy.delta_review: false`, a full-packet stamp and a delta integrity finding still prevent the carry. The carried approval alone never opens the gate; the blocking reviewer must approve the fix commit, and a new block keeps it unmet.

The blocking reviewer's prompt lists its findings and the fix diff, and asks for a verdict on each finding and for new findings only where the fix broke something. The reviewer still gives results for every acceptance line, as today, reusing the prior record's unchanged results as evidence.

Depends on M22.51: both edit `review_gate.py` and `docs/orchestration-review.md`.

## Tier

trust boundary: the review gate decides which approvals count.

## Done but wrong

- The carry ignores the tier: a leaf whose sheet on the integration branch names trust boundary, but whose branch copy says plain, still carries. Check: the trust-refusal test edits only the branch copy of the sheet.
- A path outside the zones carries: the out-of-zone test changes one file outside the leaf's zones and the approval does not count.
- A READY without `fix_of` carries: with `fix_of` absent the gate gives the same result as today on the same delta.
- The fix widens its own zones: the widened-zones row leaves the approval stale.
- An unreadable tier carries: the tier-unknown row leaves the approval stale.

## If this fails

Assumption: the gate can read the integration branch's copy of the sheet with the existing git helper, and can count an older approval without filing a new record for that family. If it cannot, stop and name the helper or the record; the coordinator decides before any file outside the zones is added.

## Accepted limits

- One block, answered by one fix commit, at a time. A fix that answers two blocks needs today's full reviews.
- A fix that breaks something the blocking reviewer does not look at is caught only by later review or tests. The gate does not check that the blocker looked only at its findings.
- Trust-boundary leaves keep today's rule. `delta_from` is unchanged.
- The product does not apply `sr/tools/tier.py`'s path floor: a sheet whose tier is plain carries even if the diff touches review modules. The grind must not write `fix_of` when `tier.py` prints trust.
- `fix_of` is executor-written; the block and parent checks, not the field, are what bind it.
