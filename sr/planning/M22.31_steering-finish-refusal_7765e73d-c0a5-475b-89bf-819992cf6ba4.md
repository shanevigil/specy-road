## Intent

Restores the refusal at finish that the 2026-11-06 split took off feature/rm-steering-file-guard. Detection after a turn only reports a changed steering file; this leaf stops `finish-this-task` from landing a branch that changes one unless a touch zone names that exact path, so a reviewed zone is the only way a steering change reaches the integration branch.

## Approach

- **First commit:** the leaf starts from the integration branch with `git revert` of R31 (the commit under `## Source`). Conflicts are resolved in that commit by keeping everything predecessors already landed (narrowed M22.5, M22.30, M22.14, M22.10 and M22.20) and adding only this leaf's class; no file is taken from narrowed M22.5's version where a predecessor has changed it since. Review covers this leaf's own diff from its merge base.
- **At finish:** `finish-this-task` refuses before its bookkeeping commit when the branch diff against the merge base changes an in-tree steering path (harness config and hooks, the three roadmap policy files, root shell startup files), unless a touch zone names that exact path; a directory or glob zone does not count. `roadmap/registry.yaml` is ignored there. The message names each path and the next step: add that exact path to `touch_zones` with `specy-road edit-node` and get it reviewed, or revert it.
- **Where it lives:** `specy_road/steering_gate.py`, called from `bundled_scripts/finish_task.py`. Its module docstring names its topic (the steering list's uses at finish and, after M22.32, at launch), not the file limit: the cap is 1,000 lines and cap-driven splits are being folded (constraints/file-limits.yaml).
- **Out of scope:** the launch denies (M22.32), OS-level isolation, signing, the M20 posture model, and restoring a changed file.
- **Verify:** the tests below, then one full Sol sweep of the merged result.
