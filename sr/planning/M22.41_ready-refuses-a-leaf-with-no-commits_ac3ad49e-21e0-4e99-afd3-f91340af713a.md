## Intent

A field run showed a worker that could not commit still reach review. `ready` wrote READY with `commit` equal to `base` and no changed paths, its `--run` checks passed against uncommitted files, and `handoff status` showed `ok` and offered review. Confirmed in `cmd_ready`: nothing refuses an empty leaf.

## Approach

Add one check in `cmd_ready`, run before the `--run` commands and again after them: no committed in-zone change against the integration merge base (outer repository and covered nested repositories, through the existing zone and nested-repository helpers), or uncommitted in-zone changes. Name the paths. In `handoff status`, report an old empty READY as invalid for leaves with no covered nested repository, without invalidating a blocked READY.

## Tasks / checklist

- [ ] Refuse an empty or dirty leaf in `ready`
- [ ] Stop showing ok for an empty READY
- [ ] Tests, docs, CHANGELOG

## Tier

behavioural: a new refusal in `ready`; a test of the simple case can pass while the zone match is wrong for others.

## Done but wrong

- Zone matching is too broad or too narrow: the table's boundary rows (a directory zone, a path that only starts with a zone's name, an outside path) give the stated result.
- Nested-only work is wrongly refused: the nested-only row writes READY.
- A verifier changes state after the first check: a --run that dirties a zone file or moves HEAD is refused and the old READY is unchanged.

## If this fails

Assumption: configured nested repositories expose an integration base and a committed in-zone diff through the existing nested-repository helpers. If a covered repository cannot be assessed, stop and report the repository and the missing git evidence; the maintainer decides how to amend the requirement.

## Accepted limits

- `ready` gets no `--blocked-on` flag in this leaf: a worker blocked before any commit says so in its summary. A flag is an M23 intake item.
- Old READYs of nested-only leaves keep today's status; no new recorded evidence is added for them.
