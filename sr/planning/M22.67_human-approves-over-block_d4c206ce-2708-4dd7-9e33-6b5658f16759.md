## Intent

A person at a terminal must be able to approve a leaf over a reviewer's block in one command. Today they cannot. `handoff status` offers the human `mark-implementation-reviewed <LEAF_ID>`. That command refuses a leaf id, and run without the id it refuses again because a block stands. The only way past the block is M22.51's `review operator-decision`, which the person has to find, run from the integration-branch checkout, and then commit by hand before the leaf's gate can see it. In the field this stopped an adopter's work. Sources: an adopter's sanitized coordinator notes on rc4, item 24 (`sr/work/sandbox-feedback/2026-11-09-field-coordinator-notes-rc4.md`), and part 2 finding 37 (`sr/work/sandbox-feedback/2026-11-09-solo-user-part2-triage.md`). On 2026-11-09 the maintainer chose option A for 0.3.1 and called it critical: "This is the type of hardening that is too much and affects specy-road's usability." This leaf replaces finding 37's M23 item.

## Approach

The person runs `mark-implementation-reviewed` on the leaf's feature branch, in an interactive terminal and without `--yes`. When the gate is not met because of reviewer blocks, the command shows each blocking record's findings and offers `[a] Approve over the block`. It asks for the reason in the person's own words. Then it records an M22.51 operator decision (the same closed `kind: decision` entry with `decided_by: operator`, the same answer text naming the full commit, each block and any shortfall, the words as the quote, the git identity as recorder, and the same `OPERATOR-<commit>.yaml` marker), and commits the registry approval. All of this is one command.

**Where the entry goes.** The entry is committed on the integration branch, from a detached temporary worktree, so no checkout's branch changes. The gate reads a decision from the working-tree ledger or from the ledger committed on the integration ref that policy is read from (`review_override._ledgers`). It honours the decision only while the marker's commit is the one under review, or only the leaf's sheet or review bookkeeping changed since. Two other designs were weighed and rejected:

- **Commit the entry on the leaf branch.** The ledger commit becomes the new commit under review: the commit-under-review rule skips only registry-only commits, and the bookkeeping carry does not cover `roadmap/decisions.yaml`. So the decision would end at once (`docs/orchestration-review.md`, operator section). Carrying it anyway would widen the gate. It would also conflict at landing and in PRs with the coordinator's own appends to the ledger, and could reuse an id the integration branch already holds (`next_free_id` reads only the local ledger).
- **Leave the entry uncommitted in the leaf checkout.** The gate would honour it, but the clean-tree check before the registry commit refuses it. `finish-this-task` refuses it too, and nothing tracked records the decision.

The integration-branch commit needs no gate change, and it is what M22.51 already tells the coordinator to do by hand. The steps:

- **With a remote,** the gate reads only `<remote>/<integration>`. Fetch, add a detached temporary worktree at that tip, append the entry there (the id comes from the integration ledger), commit only `roadmap/decisions.yaml`, then `git push <remote> HEAD:refs/heads/<integration>`. Git refuses a push that is not a fast-forward, so if the branch moved meanwhile, nothing lands. No local branch or checkout is touched. The coordinator's checkout is one commit behind and fast-forwards on its next pull.
- **With no remote,** the gate reads the local integration branch. Commit the same way in a temporary worktree, then move `refs/heads/<integration>` by compare-and-swap. A worktree holding that branch must have no uncommitted tracked changes, checked before anything is written; its index and files then follow the ref. This is the nested-repo `land: local` logic.
- Both steps reuse `nested_repos_land.py`. Its temporary-worktree step (`_merge_in_temp_tree`) and its compare-and-swap-and-follow step (`move_ref` with `_follow_in_checkout`) become two public functions, called by both the nested landing and this path. The nested landing's behaviour is unchanged, and its existing tests are the regression.

**Order.** Every refusal comes before anything is written:

1. The trial merge, which is already there.
2. The clean-tree check, moved forward on this path so a recorded decision never sits beside an unstamped registry (the problem behind part 2 finding 29).
3. `role_refusal()`.
4. Git identity.
5. Whether settling every counted block, plus the shortfall when `signed_reviews` is off, would pass the gate. Check this by evaluating a copy of the `GateResult` with the blocks cleared and the shortfall settled.

Only then is the option offered. After the menu and a non-empty reason come the integration commit (or push), then the marker (only once the entry has landed), then `evaluate_gate` again, then `_commit_registry_approved`. If anything fails after the menu, the command exits 1 with nothing past that point written.

**Code reuse.** `review operator-decision` and this path call one shared function that records the decision. It is split out of `cmd_operator_decision` and takes the gate, the root the ledger is written in, the quote and the session. The session is `mark-implementation-reviewed <UTC time>`. The command's behaviour and tests stay as they are.

**Status and refusal text.**

- In `handoff status`, the human row gives the command form that works. For a leaf: "run `specy-road mark-implementation-reviewed` on <branch>", with no id. For a milestone: with the id, as now. While a block stands on a leaf, the row says "can approve over <model>'s block" (each blocker named) with that command.
- When the gate is not met, the refusal on a leaf with a block (non-interactive, or `--yes`) names the interactive path and `specy-road review operator-decision <id> --decision approve --quote '<the operator's words>' --session <id>`. When the option was withheld, the refusal also names why: the role, git identity, or the gate's remaining problems.
- `--yes` and a non-TTY never approve over a block. The milestone path is unchanged, because an operator decision is for one leaf.

No constitution change is needed. Principles §6 and §7 already name the interactive human approval in `mark-implementation-reviewed` and the operator decision record.

## Tier

trust boundary: this adds a human path past a reviewer block, writes a decision that settles counted correctness findings, and commits or pushes to the integration branch from a review command. `sr/tools/tier.py`'s path floor also raises it (`review_override.py`, `review_eligible.py`).

## Done but wrong

- The entry is committed on the leaf branch, so the decision ends at once or the leaf conflicts at landing. Check: the local and linked-worktree rows assert the leaf branch has no ledger commit and status is `approved`.
- A decision lands but the registry is not stamped (half done). Check: the unclean-tree and holder-dirty rows refuse before anything is recorded, and the push-refused row leaves no marker.
- `--yes`, a non-TTY or an agent role approves over a block. Check: the not-interactive and role rows.
- The coordinator's checkout is changed. Check: the linked-worktree row asserts its HEAD and status are unchanged.
- The option is offered and a decision recorded, but the gate still fails. Check: the would-not-close rows show no option and nothing recorded.
- The status hint still prints the id for a leaf. Check: the status-rows row.

## If this fails

Assumption: a commit made in a detached temporary worktree, then pushed (with a remote) or moved onto the local branch by compare-and-swap (without one), is what `policy_source`'s ref reads. Second assumption: the decision write and the nested-repo helpers can be shared without changing either existing behaviour or test. If the gate cannot see the entry this way, or the nested landing's tests change, stop and name the module. The maintainer decides before the gate or `review_bookkeeping.py` is touched.

## Accepted limits

- Leaf only. An operator decision is for one leaf and one commit; a milestone full review with a block is unchanged.
- A process in a pseudo-terminal with the role unset or `coordinator` is not stopped, as in M22.51. The audit is the quote and the recorder identity in the tracked entry.
- If the integration branch is protected against direct pushes, the push is refused and the path is unavailable. The refusal names `review operator-decision` from the coordinator's checkout. Pickup's claim push has the same need.
- With no remote, a worktree holding the integration branch has its files updated to the new tip, as the nested `land: local` path already does.
- The registry commit adds no trailer for the decision. The decision is in the ledger and in `handoff status`.
- When the human row is excluded for a roster reason (for example, not a reviewer role), it keeps that reason, even though an operator decision does not need the human on the roster.
