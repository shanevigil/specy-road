## Intent

A person at a terminal must be able to approve a leaf over a reviewer's block in one command. Today they cannot. `handoff status` offers the human `mark-implementation-reviewed <LEAF_ID>`. That command refuses a leaf id, and run without the id it refuses again because a block stands. The only way past the block is M22.51's `review operator-decision`, which the person has to find, run from the integration-branch checkout, and then commit by hand before the leaf's gate can see it. In the field this stopped an adopter's work. Sources: an adopter's sanitized coordinator notes on rc4, item 24 (`sr/work/sandbox-feedback/2026-11-09-field-coordinator-notes-rc4.md`), and part 2 finding 37 (`sr/work/sandbox-feedback/2026-11-09-solo-user-part2-triage.md`). On 2026-11-09 the maintainer chose option A for 0.3.1 and called it critical: "This is the type of hardening that is too much and affects specy-road's usability." This leaf replaces finding 37's M23 item.

## Approach

The person runs `mark-implementation-reviewed` on the leaf's feature branch, in an interactive terminal and without `--yes`. When the gate is not met because of reviewer blocks, and settling them would pass the gate, the command prints each blocking record's findings and offers `[a] Approve over the block`. It asks for the reason in the person's own words. Then it records an M22.51 operator decision (the same closed `kind: decision` entry with `decided_by: operator`, the same answer text naming the full commit, each block and any shortfall, the words as the quote, the git identity as recorder, and the same `OPERATOR-<commit>.yaml` marker), and commits the registry approval. All of this is one command.

**Where the entry goes.** The entry is committed on the integration branch, from a detached temporary worktree, so no checkout's branch changes. The gate reads a decision from the working-tree ledger or from the ledger committed on the integration ref that policy is read from (`review_override._ledgers`). It honours the decision only while the marker's commit is the one under review, or only the leaf's sheet or review bookkeeping changed since. Two other designs were weighed and rejected:

- **Commit the entry on the leaf branch.** The ledger commit becomes the new commit under review: the commit-under-review rule skips only registry-only commits, and the bookkeeping carry does not cover `roadmap/decisions.yaml`. So the decision would end at once (`docs/orchestration-review.md`, operator section). Carrying it anyway would widen the gate. It would also conflict at landing and in PRs with the coordinator's own appends to the ledger, and could reuse an id the integration branch already holds (`next_free_id` reads only the local ledger).
- **Leave the entry uncommitted in the leaf checkout.** The gate would honour it, but the clean-tree check before the registry commit refuses it. `finish-this-task` refuses it too, and nothing tracked records the decision.

The integration-branch commit needs no gate change, and it is what M22.51 already tells the coordinator to do by hand.

**The integration commit.** It is made in a detached temporary worktree of the integration tip the gate just read. The commit changes only the project-relative `roadmap/decisions.yaml`: `<prefix>roadmap/decisions.yaml` from the git root, where the prefix is the project's place under the git root (`sr/` in this repository, empty for a project at the git root). The id comes from that tree's ledger.

- **With a remote,** the gate reads only `<remote>/<integration>`. The commit is pushed as `git push <remote> HEAD:refs/heads/<integration>`. Git refuses a push that is not a fast-forward, so if the branch moved meanwhile, nothing lands. No local branch or checkout is touched. The coordinator's checkout is one commit behind and fast-forwards on its next pull.
- **With no remote,** the gate reads the local integration branch. `refs/heads/<integration>` moves by compare-and-swap from the tip the worktree was built on. A worktree holding that branch must have no uncommitted tracked changes (checked before the menu); its index and files then follow the ref. This is the nested-repo `land: local` logic.
- **Reuse of `nested_repos_land.py`.** `_merge_in_temp_tree` is not the helper: it merges the feature branch before its callback. Two steps are made shared and public instead. The first only adds a detached temporary worktree at a tip, runs a callback in it and removes it. The second is the compare-and-swap: `update-ref` of `refs/heads/<integration>` from the tip the worktree was built on, then `_follow_in_checkout` for a holder. The feature-branch merge stays inside `_land_one` and `_land_one_locally`, which call those steps. Nested landing's behaviour, messages and tests stay as they are.

**Order.** Every refusal comes before anything is written:

1. The trial merge, which is already there.
2. The clean-tree check (`work/` excepted), moved forward on this path so a recorded decision never sits beside an unstamped registry (the problem behind part 2 finding 29).
3. `role_refusal()`.
4. Git identity.
5. With a remote: fetch the integration branch, then evaluate the gate again, so the policy is read from the fetched tip (`policy_source` reads only the remote-tracking ref and does not fetch). A failed fetch refuses. With no remote: the holder check above.
6. Whether settling every counted block, plus the shortfall when `signed_reviews` is off, would pass the gate. Check this on the gate from step 5: evaluate a copy of the `GateResult` with the blocks cleared and the shortfall settled, so a policy pin, an unmet `strong_review` item, a verifier problem or a signed-review shortfall withholds the option. One function in `review_override.py` answers this, and `review_eligible.py` uses the same one.

Only then does the command print each blocking record's findings, offer the option and read the reason.

After a non-empty reason:

1. The decision commit is made in the temporary worktree, at the tip step 5 read, and pushed (or the ref moved).
2. Only after the push or ref move succeeds, the marker is written in the checkout running the command. A refused push leaves no marker and no ledger change on any branch.
3. Stdout names the new integration commit (full id) and where it went (`origin/dev`, or local `dev`).
4. `evaluate_gate` runs again. If it does not pass, the command exits 1, does not stamp the registry, leaves the integration commit in place and names the gate's remaining problems.
5. `_commit_registry_approved` runs.

**Code reuse.** `review operator-decision` and this path call one shared function that appends the closed decision entry to the ledger in the root it is given; for this path, that is the project directory inside the temporary worktree. The function does not write the marker. `cmd_operator_decision` writes its marker right after the call, as now; this path writes it in the checkout running the command, after the entry has landed. The function is split out of `cmd_operator_decision` and takes the gate, the root, the quote and the session. The session is `mark-implementation-reviewed <UTC time>`. `review operator-decision`'s behaviour and tests stay as they are.

**Status and refusal text.**

- In `handoff status`, the human row gives the command form that works. A leaf names no id; a milestone keeps today's id form.
- For a leaf, the human row's text depends on the gate:
  - **No counted block:** `can approve, interactively: run \`specy-road mark-implementation-reviewed\` on <feature branch>`.
  - **Counted blocks, and settling them would pass the gate (step 6):** `can approve over <names>'s block(s), interactively: run \`specy-road mark-implementation-reviewed\` on <feature branch>`. The names are joined with ` and `.
  - **Counted blocks, and settling them would not pass the gate:** `to request interactive approval over <names>'s block(s), run \`specy-road mark-implementation-reviewed\` on <feature branch>; other gate requirements still apply`. It does not promise an approval.
  - When `signed_reviews` is on, ` --sign-key <your private key>` stays inside the command, as now.
- When the gate is not met, the refusal on a leaf with a block (non-interactive, or `--yes`) names the interactive path and `specy-road review operator-decision <id> --decision approve --quote '<the operator's words>' --session <id>`. When the option was withheld, the refusal also names why: the role, git identity, a failed fetch, a dirty holder, or the gate's remaining problems. The existing "the review gate is not met" sentence stays.
- `--yes` and a non-TTY never approve over a block. The milestone path is unchanged, because an operator decision is for one leaf.

No constitution change is needed. Principles §6 and §7 already name the interactive human approval in `mark-implementation-reviewed` and the operator decision record.

## Test table

These are in-process CLI tests on temporary repos. A TTY means `sys.stdin.isatty` is patched true and `input` is fed. There are no sleeps and no network. "Nothing recorded" means that four things are unchanged: the integration ledger (on every branch and on the remote) is byte-identical, the marker directory is byte-identical, the leaf registry is byte-identical, and the integration tip has not moved.

**Fixtures.** The review gate stays on in every fixture: `require_implementation_review_before_finish: true` on `dev`, the roster `ROSTER` from `tests/test_review_override.py`. Do not use `delegate_layout` or `prepare_layout_merge_mode_remote`: both commit a workflow without the flag, which turns the gate off. The two project layouts are:

- **root:** `make_review_repo(orchestration=ROSTER)`, the project at the git root.
- **sr/:** `make_layout_finish_repo(tmp, "nested")`, the project under `sr/`. `ROSTER` is committed as `sr/roadmap/orchestration.yaml` on `dev` and `dev` is merged into the leaf. The shared helpers in `tests/review_repo_helpers.py` stay unchanged.

## Tier

trust boundary: this adds a human path past a reviewer block, writes a decision that settles counted correctness findings, and commits or pushes to the integration branch from a review command. `sr/tools/tier.py`'s path floor also raises it (`review_override.py`, `review_eligible.py`).

## Done but wrong

- The entry is committed on the leaf branch, so the decision ends at once or the leaf conflicts at landing. Check: the local and remote rows assert the leaf branch has no ledger commit and status is `approved`.
- The entry is written at the git root instead of the project's `roadmap/` (an `sr/` project). Check: the sr/ local and remote rows assert the commit changes only `sr/roadmap/decisions.yaml` and no root ledger exists.
- The temporary worktree merges the leaf into the integration branch. Check: the local and remote rows assert the integration commit changes only the ledger.
- A refusal comes after something is written: a decision is recorded and the gate is still unmet, or a marker exists without a landed entry. Check: the unclean-tree, holder-dirty, stale-policy and would-not-close rows refuse with nothing recorded, and the push-refused row leaves no marker.
- A failure after the decision lands is silent or claims success. Check: the registry-commit-refused row asserts what is recorded, what is not, and the recovery text.
- `--yes`, a non-TTY or an agent role approves over a block. Check: the not-interactive row and the parametrized role row (which also covers empty, padded and differently cased values).
- The coordinator's checkout is changed. Check: the remote row asserts its HEAD and status are unchanged.
- The status hint still prints the id for a leaf, or promises an approval the command would withhold. Check: the status-rows row.

## If this fails

Assumption: a commit made in a detached temporary worktree, then pushed (with a remote) or moved onto the local branch by compare-and-swap (without one), is what `policy_source`'s ref reads. Second assumption: the decision write and the nested-repo steps can be shared without changing either existing behaviour or test. If the gate cannot see the entry this way, or extracting the worktree step changes a nested landing test, stop and name the module. The maintainer decides before the gate or `review_bookkeeping.py` is touched.

## Accepted limits

- Leaf only. An operator decision is for one leaf and one commit; a milestone full review with a block is unchanged.
- A process in a pseudo-terminal with the role unset or `coordinator` is not stopped, as in M22.51. The audit is the quote and the recorder identity in the tracked entry.
- If the integration branch is protected against direct pushes, the push is refused and the path is unavailable. The refusal names `review operator-decision` from the coordinator's checkout. Pickup's claim push has the same need.
- With no remote, a worktree holding the integration branch has its files updated to the new tip, as the nested `land: local` path already does.
- The registry commit adds no trailer for the decision. The decision is in the ledger and in `handoff status`.
- When the human row is excluded for a roster reason (for example, not a reviewer role), it keeps that reason, even though an operator decision does not need the human on the roster.
- M22.53 already claims `docs/orchestration-review.md` and `CHANGELOG.md`. The overlap warning is expected. This leaf does not wait on M22.53; whichever lands second rebases the operator paragraph and the changelog entry.
- The decision commit, the marker and the registry approval are separate operations. A later failure does not roll back a decision that has landed:
  - If the push or ref move succeeds and the following `evaluate_gate` does not pass, the command exits 1, does not stamp the registry, leaves the integration commit in place and names the gate's remaining problems.
  - If the registry commit fails after the decision lands, the decision stays recorded. The command exits 1 and says how to finish: restore `roadmap/registry.yaml`, then re-run `specy-road mark-implementation-reviewed --yes`, which the recorded decision now lets pass.
