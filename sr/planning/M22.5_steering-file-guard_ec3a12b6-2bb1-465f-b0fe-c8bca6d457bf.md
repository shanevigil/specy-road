## Intent

rc4 fix (maintainer decision 2026-11-05: steering-file protection is an rc4 fix), filed in M16's fix intake as a dependency of gate M16.8.9. specy-road runs unattended executors in linked git worktrees, and some files they can write are later read or run by trusted code outside the executor: the coordinator's harness, git, the coordinator's shell, the toolkit's own gate. Today nothing notices a change to them. The post-run check (worker_turn_check.py) compares HEAD, branch, stash and porcelain only, and finish checks that work landed inside the zones, not what it touched outside them.

Evidence:

- sr/docs/research/agent-safety-posture-2026-11-05-claude-research.md, Executive summary item 3 "Protect the steering files" and Disagreements item 2 ("the toolkit is itself in the attack path"). It describes the CVE class where an agent writes a file that trusted code later runs: harness settings and hooks, git hooks and `core.fsmonitor` / `core.hooksPath`, shell startup files, virtualenv interpreters, and symlinks the unsandboxed parent follows.
- The 2026-11-04 context-regression replay (docs/design-notes/context-regressions-2026-11-04-triage.md, CR1 / cursor; docs/orchestration-review.md "What the gate cannot stop"). An executor added itself to `roadmap/orchestration.yaml` on the integration branch and approved its own work. Another called the toolkit's record writer from `python -c`. A third drove the human menu with `expect`.

Found in the code (2026-11-05):

- In a linked worktree, `.git/hooks` and `.git/config` are the common git dir's. An executor that writes them changes the coordinator checkout's git.
- `env_setup.link` (worktree_env.py) symlinks `.venv`, `.conda` and `node_modules` from the main checkout into the worktree. A write through `.venv/bin/python` changes the coordinator's interpreter.
- Claude Code executors in `launch_mode: full` load the worktree's project `.claude/settings.json`, hooks included, on the next turn.
- Codex runs `workspace-write` with `approval_policy=never`. Cursor runs `--force`.
- The only existing protection: Cursor's built-in write block on `.cursor/*.json`, `.vscode/**` and `.git/hooks/**` (maintainer, harness behavior). It is not written down anywhere in the repo yet.

## Approach

- **One list** in a new `specy_road/steering_paths.py`, documented in docs/orchestration-steering-files.md and docs/orchestration-workers.md. For each worker turn it snapshots:
  - git steering, read from the filesystem only (no git command): the hooks directory (`core.hooksPath` when set, else `<common-git-dir>/hooks` and `<worktree-gitdir>/hooks`) as sorted direct regular-file names with sha256, non-recursive; and the bytes of the common `config` and `config.worktree`, with the files they name by `include.path` or `includeIf.*.path` as `specy_road/git_config_text.py` reads them. A `git_config` finding reports the file digests plus the changed values of `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `include.path` and `includeIf.*.path`;
  - a hooks directory with more than 200 direct children fails closed on every comparison, changed or not: one `check_error` naming that directory with class `git_hook`, and the git probes marked skipped. The listing stops reading after 201 entries;
  - Moved to M22.30: harness config and hooks, the roadmap policy files, other leaves' registry entries, `work/reviews/` files, shell startup files, `env_bin` and symlinks.
  Paths compare project-relative the way `zone_matches` does, and one real path is stored once.
- **After each turn, ordering matters:** `close_turn` compares the git-steering snapshot before any post-turn git command. On a change it records the finding and marks the post-turn git probes skipped, so `git status` never runs under a changed `core.fsmonitor` or hooks. An unreadable input, a special file or a timeout records a `check_error` naming the path and class and also skips the probes; with no snapshot from the turn's start it fails closed the same way. It never aborts the turn and never passes silently. Otherwise it runs the existing git probes. Each change is one `steering_file` finding (`path`, `class` `git_hook` or `git_config`, `before`, `after`) that replaces any porcelain or `committed_outside_zones` finding for the same path.
- **Runner order:** the inspection runs on `worker_runner`'s finalization path before READY is parsed: the check runs before `fresh_ready`, and a READY that cannot be parsed (invalid UTF-8 included) is a completion error of the turn, not an exception, so the turn still ends with exactly one `post_run_check` holding the git-steering findings.
- **Sticky flag and reconcile:** the sticky `steering_changed` worker flag shows in `worker status --json` `flags` and `handoff status --json` `workers[].flags` (text handoff status is unchanged; review_cli.py stays out of zones). A clean turn leaves it set; `worker reconcile <id>` without `--dismiss` prints one `path class before after` line per `steering_file` finding recorded while it was set, then clears it.
- Moved to M22.31: the refusal at finish.
- Moved to M22.32: the Claude Code launch and resume denies.
- **Out of scope:** OS-level isolation, signing, the M20 posture model and doctor probes, and restoring a changed file. This leaf detects and refuses.

## Redesign (2026-11-07, maintainer approved)

About seven review rounds each found another git-config edge case in `specy_road/git_config_text.py`, because the leaf reimplements git's config parsing. Stop modelling the config. Let git report it, and make post-turn git unable to run anything the config names. This section replaces the "read from the filesystem only" and "before any git probe" rules above.

- **One hardened runner.** Every git command the toolkit runs between the end of the executor's turn and the verdict goes through one helper: clean environment (no `GIT_*` from the worker, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`), `-c core.fsmonitor=false -c core.hooksPath=/dev/null`, `--no-optional-locks`, and a timeout. `_append_usage` and the probes use it, so ordering stops being the safety property. A test fails if a post-turn path calls git any other way.
- **Git reports its own config.** The snapshot is the raw bytes of `git config --local --includes --show-origin --null --list`, plus the same for `--worktree` when `extensions.worktreeConfig` is on, run through that helper. Compare bytes, never decode. Delete `git_config_text.py`. This runs no fsmonitor or hook, and keeps non-UTF-8 include paths exact (probed on git 2.43).
- **Hooks.** The directory comes from the snapshot's last `core.hooksPath`, else the common and worktree hooks directories. Sorted direct children with sha256, non-recursive. The 201-entry cap applies to every directory, `/` included, with no exemptions.
- **One bounded rule for the unexpected.** Non-zero exit, timeout (a FIFO include hangs git), unreadable hook, special file, or no start-of-turn snapshot: one `check_error` naming the class, and the turn fails closed. No per-shape handling.
- **Stated limits, in the docstring and docs:** a git binary swapped on PATH, system and global config (outside the worktree threat model; the worker's turn can reach them only outside its zones), and changes reverted before the turn ends. The coordinator's own later git is protected by the finding and sticky flag, not by this runner.
- **Unchanged:** findings, sticky `steering_changed`, reconcile, the READY-with-bad-bytes turn ending, and the M22.30 to M22.32 split.

Acceptance lines keep their meaning. Tests add: a hostile `core.fsmonitor` through a non-UTF-8 include is detected and never runs; a FIFO include fails closed; `/` as hooksPath fails closed; and no post-turn git call bypasses the helper.
