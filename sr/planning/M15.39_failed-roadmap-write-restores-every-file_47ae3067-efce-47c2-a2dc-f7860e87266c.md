## Intent

When `add-node` failed after the chunk write (the Errno 36 that M15.38 removes), the new node was already in `sr/roadmap/phases/*.json` and stayed there. Its planning sheet did not exist, so `validate` failed until someone removed the node by hand. Every roadmap mutation is meant to be all or nothing. This leaf makes that true when a write fails, as well as when validation fails (rc4 fix, maintainer 2026-11-05).

## Approach

- Root cause (`roadmap_chunk_atomic.AtomicWritePlan`): `write()` replaces each pending file in turn with `os.replace`, and sets `_staged = True` only after the loop. `commit()` calls `write()` outside its `try`, so the `try` covers only `validate()`. If the chunk (staged first) has already been replaced when the planning sheet write raises, the exception passes through `commit()` without a rollback, and `rollback()` would do nothing anyway because `_staged` is still False. `write_node_update` (edit-node) stages the chunk before the sheet rename, so it has the same gap.
- Fix it in the plan, not in each caller: mark the plan as staged once the snapshots are taken, put `write()` inside the `try`, and clean up any temporary file left by a failed `os.replace`.
- `cmd_add` catches only `ValueError` today, so an `OSError` prints a traceback. Report it as one `error:` line.
- Depends on M15.38 because both change `roadmap_crud_ops.py`. Also, after M15.38 a long title no longer reproduces the failure, so the tests inject it another way (a file in place of the planning/ directory, a read-only directory, or a plan staged with a too-long name).
