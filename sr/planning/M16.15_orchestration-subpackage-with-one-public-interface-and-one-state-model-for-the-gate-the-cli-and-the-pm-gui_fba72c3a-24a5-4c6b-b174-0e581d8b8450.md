## Intent

Workers and orchestration are canonical specy-road (maintainer, D1). They are 12k lines across 65 modules with no boundary, and the 0.3.2 PM GUI will show orchestration and worktree state. Defining the interface and state model first lets M16.16-M16.19 move code behind it one sub-area at a time.

## Approach

- Interface first, then readers switch to it, then (in later leaves) modules move.
- The snapshot is read-only; writes stay where they are until their sub-area moves.
- Field names are part of the interface; version the snapshot with a `schema` integer.
- Revision 1: a fixed state table replaces the 'orphaned' rule, which would have classed every fresh manual claim as abandoned (Sol 5, Grok 1); the field list is a committed fixture so reviews cannot invent fields (Grok 10, Sol 6).
- Status vocabulary, fixed before pickup: claimed (manual, no worker), running, exited_ok, exited_failed, abandoned (M15.26's rule), unknown.
- The 0.3.2 GUI work (phase M17, M17.1) reads tests/fixtures/orchestration_snapshot_v1.json and starts after this leaf and M16.42 merge; it does not import worker_* or gui_app_routes_workers internals.
- Depends on: M16.40. The last acceptance line is an informational line-change estimate, not a gate; report `scripts/lean_metrics.py --check` deltas in READY once M16.2 has landed.
- Behaviour-preserving: the parity harness (M16.0) and the review-gate decision table (M16.1) stay green; no function rises above its merge-base complexity; docstrings and comments that explain intent are kept or improved, never cut to save lines.
