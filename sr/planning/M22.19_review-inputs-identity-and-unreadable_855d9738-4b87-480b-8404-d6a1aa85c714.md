## Intent

rc4 final review (§3.2, 2026-11-06), items deferred to rc5: inputs the review gate and filing read.

1. **READY identity.** READY authorship and reviewer model ids are compared as written. A case variant, or a roster alias of the executor's model, escapes the READY-author exclusion (policy-sol F2, the normalization part).
2. **Acceptance presence.** The acceptance presence check runs outside the unreadable boundary. A `PermissionError` on its parent escapes as a traceback, and a dangling `POLICY-ACCEPTED.yaml` link reads as absent (policy-sol W1).
3. **Worker record.** The caller check reads `work/.workers/<id>.yaml` with a blocking `read_text`, so a FIFO there hangs `review record` (records-sol WARNING).
4. **Case-variant names.** `write_rejected` and `write_human_approval` skip `write_review`'s case-variant unlink. `unreadable_rejected_lines` globs `REJECTED-*.md` case-sensitively (records-grok WARNING).

Out of scope: authenticating READY authorship, deferral decisions or policy acceptance (policy-sol F1, F3, F4). These stay honour-system, as docs/orchestration-review.md:83 states.

## Approach

- **One normalization** for READY authors and reviewer ids in `review_eligible`: case-fold, then map a roster harness or profile alias to the roster `api_id`. An id that maps to more than one roster entry keeps the gate closed with a named problem.
- **`review_policy_pin.read_acceptance`:** do the `lstat` presence check inside the unreadable boundary. Absent means no entry. A dangling link or an unreadable parent is an invalid acceptance (a gate problem, no traceback).
- **`review_caller` / `worker_state.load_record`:** open with `O_NONBLOCK`, `fstat` must show a regular file, then read; otherwise `CallerError` at once.
- **Shared case-variant unlink:** `write_rejected` and `write_human_approval` use the unlink `write_review` uses, which never follows a link after M21.38. `unreadable_rejected_lines` matches case-insensitively.

## Tier

trust boundary: READY-author normalization decides which reviews count toward approval (the executor's own review is excluded).

## Done but wrong

- The exclusion covers one side only: the case-variant and alias rows are run with the variant on the READY side and, separately, on the review record's model id; the executor's review is excluded both ways.
- Normalization merges too much: in the same fixtures, a review by a different roster model still counts and the gate opens.
- The FIFO refusal only looks prompt: the FIFO row has no writer on the other end, and the CLI returns with the CallerError text well inside the 5 s timeout.

## If this fails

Most likely to break: real rosters share a harness or profile alias across entries, so the ambiguity rule closes gates that open today. List the affected aliases; the maintainer decides whether harness names stop counting as aliases.
