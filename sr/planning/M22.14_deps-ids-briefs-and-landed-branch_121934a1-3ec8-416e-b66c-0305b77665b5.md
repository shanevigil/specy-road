## Intent

Three low defects in roadmap editing and in pickup/finish bookkeeping, from the rc4 real-harness checks (pre-release evidence 2026-11-05).

- D10 (Notes app). `set-dependencies M2.4 --deps "M2.2 M2.1"` failed with "error: invalid dependency node_key 'M2.2'", while `add-node --dependency` and `add-dependency` accept display ids. `edit-node --set dependencies=…` uses the same parser.
- D12 (calculator §5.10). After finishing or aborting from linked worktrees, `work/brief-M2.1.md` and `work/brief-M2.3.md` stayed untracked in the main (coordinator) checkout. Pickup writes the brief there, and finish removes only the worktree's copy.
- D13 (ToDo app, note). After `finish-this-task` in merge mode, the checkout stayed on the feature branch with no word of it. This is by design: both landing paths check the feature branch out again (M22.10 keeps that). But the user is left on a branch that has already landed and is not told what to do next.

Fix: `set-dependencies` resolves display ids the way `add-dependency` does. Finish and abort run from a linked worktree also remove the main checkout's untracked brief and prompt for the leaf. A finish that leaves the checkout on the landed feature branch says so and gives the next step.

Out of scope: storing display ids (node_keys stay the stored form); tracked work files; switching branches automatically after a landing; landing logic.

Overlaps checked (2026-11-05): M21.19 (rc4) edits roadmap_crud_dependency_ops.py; this leaf only imports `resolve_dependency_refs` from it. M21.28 (rc4) and M22.5 also edit finish_task.py. M22.10 edits docs/git-workflow.md and the landing modules (this leaf adds only the closing message in finish_task.py). M22.11 edits docs/roadmap-authoring.md, which this leaf does not touch.

## Approach

- D10: `edit_node_set_pairs` (roadmap_crud_ops.py), which has the repo root and is shared by the CLI and PATCH /api/nodes/{id}, maps each `dependencies` token through `resolve_dependency_refs` (roadmap_crud_dependency_ops.py:55) before `_parse_dependency_keys` applies it: a node_key is taken as given, and a display id becomes its key. Archived keys, empty clears, de-duplication, self/cycle refusals and the all-or-nothing write are unchanged. An unknown token is refused with the existing sentence `dependency 'X' is neither a node id nor a node_key in the roadmap`. Update the help in roadmap_crud_argparse.py:272 and cli_usage.py:91 ("KEY or ID …").
- D12: when the current worktree is a linked worktree, `cleanup_work_artifacts` (finish_work_artifacts.py:156) and `_remove_pickup_work_files` (abort_task_pickup.py:144) also remove `<prefix>work/brief-<ID>.md` and `<prefix>work/prompt-<ID>.md` in the main worktree (the project's work/ via `project_prefix`) when each is a regular file git does not track there. Each removal is printed. A symlink, a symlinked work/ directory, a tracked copy and a file whose tracking git cannot establish are left alone (`remove_work_file` resolves symlinks, so it is not reused as is). Finish removes them only after the landing succeeded.
- D13: after a merge or auto landing that succeeded and left the feature branch checked out (not `--delete-branch`), finish prints `[ok] this checkout is still on <feature> (landed into <ib>); next: git switch <ib>`, only when the current branch is `<feature>` (`do-next-available-task` refuses on a feature branch, so it is not offered). Add one sentence under `merge` in docs/git-workflow.md.
