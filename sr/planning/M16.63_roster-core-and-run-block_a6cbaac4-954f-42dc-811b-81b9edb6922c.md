## Intent

A roster entry is 19 flat keys, and for every entry but `human` most of them are harness configuration: 11 of the toolkit's 16 entries carry a `channels.cli` template, and the vendor CLIs those keys describe change every release. The review gate reads into that configuration to decide whether an approval's family is known (`routing_problem`). Kestra (task type plus a nested typed taskRunner), GitHub Actions (runs-on/uses plus per-action validated `with:`) and Vibe Kanban (executor plus named variants) all separate what an entry is for from how it runs, with a typed sub-block chosen by a discriminator. Revision 2 (maintainer, 2026-11-05) restores the split that revision 1 dropped from M16.17.

## Approach

- Two groups. **Core** (who the entry is and what it may do; the gate, eligibility and the local overlay read only these): id, family, roles, may_process, public_key, available, paused_until, unavailable_until, `family_pinned` (today's `pinned`), class and subagent_family_lock. **`run:`** (how it is launched; absent for humans and manual reviewers), chosen by `run.harness` (claude-code, codex, cursor, generic): harness_bin, harness_model, profile, routing, billing_route, channels, preflight, and cursor_force for cursor (M16.69).
- Revision 4 (plan review, 2026-11-05) (Sol): class and subagent_family_lock are eligibility inputs, so they are core, and check_assignment reads core fields only (maintainer to confirm). Roster writers emit the file's version; a new file is version 2. A roster_add entry is version 2 when it has `run:`. Module paths in the zones resolve through M16.17's destination list (Grok).
- Field names inside `run:` keep today's names; only `pinned` is renamed. Fewer renames make a smaller migration.
- The file's `version` selects the form: 1 is today's flat entry, 2 is core plus `run:`. One loader returns one entry model whichever form it read, so no reader branches on the version.
- The gate's family attestation (today's `routing_problem`) becomes a function of `specy_road.orchestration`, the interface M16.15 defines: `family_pinned` first, else the run block's routing, harness, `channels.cli` `--model`, harness_model and the profile's `api_id`, exactly as today. The gate imports nothing from the run model.
- Per-harness field table: filled by the planner before dispatch (Revision 4 (plan review, 2026-11-05)) from the adapters and role_prompt (which run fields each harness reads). A harness's schema branch accepts those fields and refuses any other with a message naming the field and the harness. Every entry in the two parity rosters must fit its branch.
- The local overlay keeps its rule: `roster:` patches set only availability; `roster_add` entries are whole entries in either form during the window.
- Out of scope: named reusable run profiles (`run: {use: ...}`, Vibe Kanban's variants) go to the post-M16 intake if adopters need them; renaming usage fields to OpenTelemetry names; any change to eligibility (M16.47's check_assignment reads the entry model).
- The old form leaves only through the alias window: M16.33 lists it, and M16.62 removes the version-1 reader and its notice after the M16.61 gate.
- Depends on: M16.47, so the split edits one eligibility reader, not five; M16.14 and M16.15 come earlier in the serial chain. The last acceptance line is an informational line-change estimate, not a gate; report `scripts/lean_metrics.py --check` deltas in READY once M16.2 has landed.
- Behaviour-preserving: the parity harness (M16.0) and the review-gate decision table (M16.1) stay green; no function rises above its merge-base complexity; docstrings and comments that explain intent are kept or improved, never cut to save lines.
