## Intent

0.3.1 is tagged at the end of M16 (maintainer, 2026-11-05), after one final pass that uses the toolkit as an adopter would, and a round of feedback and fixes. M16 moved most of the code; this pass checks the whole product once more before the tag.

## Approach

- Run from a wheel built from the branch head in a clean virtual environment, never from the editable checkout, so packaging gaps show up.
- Record each checklist step's result in `sr/work/M16.8.4-e2e-results.md` (pass, fail, or not run with the reason), with the harness logins the maintainer has and every intake entry. This sheet is the plan the pass is judged against; the executor does not edit it.
- Findings become intake entries with a disposition. A fix before 0.3.1 is a new M16 leaf that the planner adds and that M16.8.9 depends on; anything else goes to the post-M16 intake. This leaf changes no product code.
- Human-led: worker and reviewer runs need the maintainer's harness logins, and the feedback round is the maintainer's.
- Depends on: see the node (the M23.3 dependency was removed on 2026-11-08). The last acceptance line is an informational line-change estimate, not a gate.
- rc4 fixes from now on go into this leaf's feedback-and-fix intake, not M15 (maintainer, 2026-11-05): each is an intake entry in `sr/work/M16.8.4-e2e-results.md` with a disposition, and a fix before 0.3.1 becomes a new M16 leaf that M16.8.9 depends on.

## Tasks / checklist

The planner wrote this checklist before the pass (2026-11-11). `$V` is a clean virtual environment with the wheel installed; every step runs that environment's `specy-road`, never the editable checkout. Each step's result goes to `sr/work/M16.8.4-e2e-results.md`.

- [ ] E0 Build and provenance. Commands: `python -m build --wheel` at the branch head; `python -m venv $V`; `$V/bin/pip install dist/specy_road-*.whl`; `$V/bin/python -c "import specy_road; print(specy_road.__file__)"`. Expected: the path is under `$V`'s site-packages, and the results file names the wheel file and the branch-head commit it was built from.
- [ ] E1 Install. Commands: `specy-road --version`, `specyrd --help`. Expected: both exit 0; the version is the checkout's `project.version`.
- [ ] E2 New project. Commands: in an empty temp git repo, `specy-road init project`, then `specy-road validate`, `specy-road export --check` and `specy-road digest --check` (after one `export` and `digest`). Expected: each exits 0; no traceback.
- [ ] E3 Leaf loop. Commands: the M16.1.1 leaf-loop sequence (`do-next-available-task`, an edit inside the leaf's zones, implementation summary and READY, `review-packet`, a review by a second session, `mark-implementation-reviewed`, `finish-this-task`), once with `on_complete: merge` and once with `on_complete: pr`. Expected: merge lands the leaf on the integration branch and marks it Complete; pr leaves the branch and prints the `gh pr create` command; `validate` passes after each.
- [ ] E4 Upgrade. Commands: `specy-road upgrade --dry-run`, then `specy-road upgrade`, on an rc3-shaped repo and on an rc5-shaped repo (the tests/parity rc3 consumer fixture copied out, and a repo from E2 built with the rc5 wheel). Expected: the dry run writes nothing (`git status` unchanged); the real run's report lists what it changed, including the roster migration where it applies; `validate` passes afterwards.
- [ ] E4a In-flight claim across the upgrade. Commands: in the rc3-shaped repo, with the rc3 wheel installed, claim a leaf with `do-next-available-task` (`specy-road --version` shows the rc3 version); install the new wheel; `upgrade`; finish that leaf with `finish-this-task` (`specy-road --version` shows the new version). Expected: the claim finishes under the new wheel with no manual registry edit.
- [ ] E5 Workers and reviewers. Commands: for each of claude-code, codex and cursor that the maintainer has a login for, `specy-road worker delegate <LEAF> --harness <h>` and `specy-road review delegate <LEAF> --model <roster id on h>`; then `specy-road worker list`. Expected: the worker reaches READY or a recorded stop with a reason, and the review files a REVIEW record bound to the commit; for a harness without a login, the results file has one line saying so.
- [ ] E6 Grind and cleanup. Commands: `specy-road grind-session --plan --repo-root <copy of the dogfood fixture>`, then one `grind-session` cycle there; `specy-road doctor --prune` (dry run) then apply. Expected: the plan names ready leaves; the cycle picks up, or stops with its documented exit code and reason; the dry run lists items and changes nothing, and the apply removes exactly the listed items.
- [ ] E7 PM GUI, read-only. Commands: `specy-road gui --read-only --port <p>` in the E2 repo; `curl` GET `/api/health`, `/api/roadmap`, `/api/roadmap/fingerprint`, `/api/workers`, `/api/git-workflow-status`, `/api/grind-status`; a POST to any write route. Expected: each GET answers 200 with JSON; the POST answers 403.
- [ ] E8 Roadmap gates. Commands: `specy-road validate`, `specy-road export --check` and `specy-road digest --check`, run from the checkout root (sr/) and with `--repo-root tests/fixtures/specy_road_dogfood`. Expected: each exits 0.
- [ ] E9 Feedback round. Every failure above and every item the maintainer collects is an intake entry in the results file with disposition `fix-before-0.3.1` or `after`.

Outside the agentic sandbox, each result is labelled `not sandbox: no MCP, reset or egress check`, and those items stay open until a sandbox run.
