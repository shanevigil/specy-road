## Intent

0.3.1 is tagged at the end of M16 (maintainer, 2026-11-05), after a pass that uses the toolkit as an adopter would, and a round of feedback and fixes. The maintainer's process (2026-11-18): before the release candidate is published, an agent runs the usual pre-release runbook (docs/release-runbook.md section 3, with the section 3.3 three-app harness) in the agentic sandbox, on a wheel built from the branch head; then the maintainer publishes the candidate to TestPyPI (gate M16.8.5) and tries it in their dependent projects (gate M16.8.6). This leaf is the agent's pre-publish pass.

## Approach

- Build a wheel at the branch head on the host or a guest (`python -m build --wheel` at a commit the host names) and install it with `[gui]` in a fresh virtual environment on each guest. Never the editable checkout: packaging gaps must show before publishing. A run off-guest or from the checkout is a rehearsal and closes no row.
- Guests follow docs/agentic-sandbox-runbook.md section 11 (claim, holder secret kept out of reports, release). The toolkit tree reaches a guest by `git archive` at the host-named SHA, for the fixtures and sr/ only; every command runs the installed wheel.
- Section 3.3 is played out in full: the three apps, the PM and developer flows, and the PM GUI step through the guest's browser automation with screenshots. Section 3.2's review pass needs harness skills, so it runs from the host's signed-in harness session, working on the guest through the agentic sandbox MCP and SSH (no cloud login on a guest, ever: maintainer 2026-11-18); no credential, key or token is copied to a guest. A harness step that cannot run that way is skipped with its reason and the maintainer's disposition; a skip on a scenario the sandbox runbook marks as blocking the rc is never a pass.
- Record each row in `sr/work/M16.8.4-e2e-results.md` with the section 3.3 evidence (app paths on the guest, commands, node ids, screenshots fetched to the host). Each failure is an intake entry with a proposed disposition the maintainer confirms. A fix before 0.3.1 found here is a new M16 leaf that the RC gate M16.8.5 and M16.8.9 depend on, so the candidate carries it; anything else goes to the post-M16 intake. Section 3.1's fix-branch pattern is replaced here by those leaves. This leaf changes no product code.
- Depends on: M22.73 (refreshed harness facts ship in the candidate) and the existing edges (M16.8.1 closes the M16.7 test lane).

## If this fails

The assumption most likely to break is that a guest can reach PyPI and its browser automation works and stay up for the whole pass. A row that cannot run stays skipped with its reason; the maintainer decides whether 0.3.1 is tagged with it open.
