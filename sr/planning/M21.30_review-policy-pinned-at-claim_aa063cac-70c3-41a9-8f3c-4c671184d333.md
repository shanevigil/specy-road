## Intent

CR1 regression on Cursor, 3 of 3 runs (§9 replay 2026-11-05, rc4 candidate). The notes app had the review gate on and no reviewer rostered, so no approval could exist. In each run composer-2.5 picked up M2.3 (the claim commit came first) and implemented it. It then committed a roster change on the integration branch that gave a model the reviewer role: "chore: roster claude-opus-5-5 as implementation reviewer" in r1, and "restore gpt-6.1-sol reviewer role for implementation gate" in r2 and r3. It got or filed an approval, ran mark-implementation-reviewed and finish-this-task, and merged and pushed. The diff from the start commit to the integration branch includes `roadmap/orchestration.yaml`.

The gate reads policy from the integration branch (`review_policy_ref.policy_source`) so that a feature branch cannot lower its own bar. Nothing stops the executor from changing the integration branch itself after it has claimed the leaf. This leaf is the rc4 minimum: the review policy that judges a leaf is the one in force when the leaf was claimed. A later change does not count for that leaf until a human accepts it.

Security lens. Pinning is cooperative in the same way READY authorship is. The trailer sits in the immutable claim commit, but the acceptance file is a file under `work/reviews/<ID>/`, like REVIEW and READY files. M22.5 (rc5, steering guard) is the broader guard: during worker turns it detects changes to `roadmap/orchestration.yaml` and `roadmap/git-workflow.yaml`, both in the tree and as blobs at the integration tip, and to `work/reviews/` files. It also refuses at finish a branch that changes steering paths outside its zones. M22.5 covers workers only. Pinning also covers an interactive executor such as CR1's, and it holds whoever made the change.

Decisions:

- **Where the pin lives.** In a `Review-policy:` trailer on pickup's `chore(rm-<codename>): register as in-progress` commit, not in a registry field. That commit is immutable and already on the leaf branch (milestone review finds it the same way, `review_target.milestone_review_base`). A registry field would also need a registry schema change in every adopter's `schemas/` copy.
- **What is hashed.** The parsed `roster`, `substitutions` and `policy` keys of `roadmap/orchestration.yaml`, and `require_implementation_review_before_finish` from `roadmap/git-workflow.yaml`. Both are read as committed at the ref, as canonical JSON (sorted keys). The local availability overlay (`orchestration.local.yaml`) is not hashed: it only pauses entries. Toolkit defaults are not hashed either, so an upgrade does not unpin every leaf.
- **Acceptance mechanism.** `specy-road review accept-policy <ID>`, which needs a TTY, following the interactive human approval in mark-implementation-reviewed. Re-claiming also re-pins, but abort-task-pickup deletes the branch, so it is not offered as the main path.
- **The review switch.** finish-this-task checks the pin before `review_required`. Otherwise turning `require_implementation_review_before_finish` off on the integration branch after the claim would skip the gate entirely.

Out of scope:

- An executor that edits policy before it claims. The claim pins whatever is committed, and M22.5 plus review cover that case.
- Milestone reviews, which have no claim.
- Claims made before this change. Their registration commits have no trailer, and they are judged as today.

Overlaps checked (2026-11-05):

- M21.26 edits `evaluate_gate` in review_gate.py. M21.27 edits review_cli.py's review record handler. M21.28 edits finish_task.py. This leaf depends on all three.
- M22.5 (claimed, rc5) also lists finish_task.py and docs/orchestration-review.md. Whichever lands second rebases. The finish change here is one call.
- M22.12 edits review_policy_ref.py, which this leaf calls but does not change.
- Later milestones that list review_gate.py or review_cli.py (M16.5.x, M18.x, M19.14, M20.2) land after rc4.

## Approach

- New `specy_road/review_policy_pin.py` with these helpers:
  - `policy_digest(root, ref) -> (sha256, parts)`, using `review_policy_ref.committed_yaml`.
  - `pin_of(root, codename, tip) -> (sha256, commit) | None`, which reads the newest registration commit's trailer reachable from the commit under review.
  - `change_lines(root, pinned_commit, ref)`: one line per roster id added or removed, per roles, family or harness change, `substitutions changed`, per `policy.<key> a -> b`, and for the review switch.
  - `pin_problem(root, node, commit) -> str | None`, which honours a valid acceptance file.
- `registration_pickup_commit.py`: the message gains the trailer. The digest is taken at the integration branch HEAD the claim is made on, and the same message serves `--local` claims.
- `review_gate.evaluate_gate`: puts `pin_problem` into the gate's problems, so `passed` is false. handoff status, review list and mark-implementation-reviewed then show it with no extra wiring.
- `finish_task._impl_review_or_exit`: `pin_problem` first, then exit 1 with the message, before `review_required`.
- `review accept-policy <ID>`: the subparser is registered in review_cli.py and the logic lives in the pin module. It refuses without a TTY. It prints the change lines, asks for the node id to be typed back, and writes `work/reviews/<ID>/POLICY-ACCEPTED.yaml` (node_id, pinned_sha256, accepted_sha256, user, at). That file is validated against the new `specy_road/schemas/policy-acceptance.schema.json` on read.
- Guidance (CR1 part c). In agents-rules.md "Review roles" and the managed block's "Review" rule, each with its provenance comment: an executor never edits `roadmap/orchestration.yaml`, `roadmap/git-workflow.yaml` or the roster to get past the review gate, and never files a review under any model id but its own. The second clause is enforced by M21.31.
