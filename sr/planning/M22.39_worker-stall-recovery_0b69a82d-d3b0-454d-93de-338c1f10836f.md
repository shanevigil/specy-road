## Intent

`sweep_stalled` flags a silent worker, but only when someone runs `worker sync` or `list`, it never acts on the flag, and a worker that never produced output is skipped. So a stall waits until a person or a coordinator's own script notices. The maintainer treats that as a toolkit bug: an unattended run should not depend on outside watchers.

## Approach

Keep it a one-shot command, because principle 5 rules out a daemon: `worker recover` is called by a person, a coordinator or `grind-session`'s own loop. Build on `sweep_stalled`, `sweep_dead_wrappers` and `worker resume`. Bound retries through policy. After M22.20 (terminate) and M22.6 (queued messages), which change the same worker paths.

## Tier

behavioural: a one-shot recovery that ends and relaunches workers; tests can pass while a busy worker is ended or the retry count resets between calls.

## Done but wrong

- A working worker is ended: a worker that wrote output within the stall window is not flagged, and `worker recover` leaves it running.
- The limit resets between calls: separate `worker recover` processes count toward one limit, and the call past it stops with "needs a person" and names the last output.
- Work is lost: a stalled worker's commit and an uncommitted file in its worktree are still there after recovery.

## If this fails

Most likely to break: silence means stalled. Some harnesses print nothing for long stretches while working, so they would be ended. Then set the window per harness; the coordinator decides the default and the maintainer any new policy key.
